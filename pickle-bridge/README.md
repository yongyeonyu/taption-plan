# 비야 ↔ 클로드 코드 작업 브리지

대표의 피클(비야)이 이 저장소에 작업 지시서를 커밋하면, 맥북 클로드 코드가 그것을 읽어 실행하고 결과를 같은 저장소에 남기는 왕복 통로입니다. 대표가 채팅에서 프롬프트를 복사해 붙여넣지 않아도 되게 하는 것이 목적입니다.

- 이 폴더는 앱 소스·CI·중계 서버 코드와 무관합니다. 오가는 것은 `pickle-bridge/` 안의 Markdown 문서뿐입니다.
- 작업 규칙은 `AGENTS.md`가 먼저입니다. 이 문서는 브리지 문서의 형식과 절차만 정합니다(`AGENTS.md` 12절).
- **저장소는 공개입니다.** 지시서·회신에 개인정보를 쓰지 않습니다 — 메일·계정 이름, 서버 주소(`workers.dev`), 실제 좌표, 실제 집·가게·동네 이름, 기기 번호, 키·토큰(`AGENTS.md` 8절).

## 1. 구조

| 경로 | 담는 것 |
| --- | --- |
| `pickle-bridge/inbox/` | 비야가 올린 지시서. `status: pending`이면 아직 처리 전 |
| `pickle-bridge/done/` | 처리해서 옮긴 지시서와 그 아래 `## 클로드 코드 회신` |
| `pickle-bridge/README.md` | 이 규약 |

지시서는 지우지 않습니다. 끝난 문서도 `done/`에 그대로 남겨 이력으로 씁니다. 두 폴더에는 `.gitkeep`을 두어 지시서가 없을 때도 폴더가 사라지지 않게 합니다.

## 2. 지시서 형식

파일 이름은 `YYYYMMDD-HHMM-<slug>.md`(예: `20261119-1540-toll-label-fix.md`)입니다. 파일 이름 순서, 곧 먼저 올린 것부터 처리합니다.

```md
---
id: 20261119-1540-toll-label-fix
created_at: 2026-11-19T15:40+09:00
status: pending
title: 통행료 제목 판별을 한국어·영어 밖 언어로도
from: 비야
request_id: TGT1119A03
basis: 대표 직접 지시 (2026-11-19 통화)
---

## 할 일
1. …

## 확인 기준
- …

## 하지 말 것
- …

## 참고
- `test.md`의 `TGT1119A03` 줄, `docs/…`
```

- `id`·`created_at`·`status`·`title`은 필수입니다. `status`는 `pending`·`blocked`·`done` 셋뿐입니다.
- `request_id`는 `test.md` 요청 ID가 이미 있으면 적습니다. 없으면 클로드 코드가 `AGENTS.md` 2절대로 새 ID를 만들고 frontmatter에 덧붙입니다.
- `basis`는 이 지시가 어디서 왔는지입니다. 「대표 직접 지시」와 「비야 제안」을 구분해 적습니다.

## 3. 클로드 코드가 하는 일

1. `git pull --rebase` — 지시서는 항상 저장소에서 읽고, 대화에 붙여넣은 사본으로 일하지 않습니다.
2. `pickle-bridge/inbox/`에서 `status: pending` 문서를 파일 이름 순서로 하나씩 처리합니다. 같은 `id`가 `done/`에 이미 있으면 건너뜁니다(두 번 실행하지 않음).
3. 각 지시서는 `AGENTS.md`를 그대로 따릅니다 — 시작할 때 확인, 요청 ID와 `test.md` 기록, 빌드 잠금, 검증, 문서 위치. 이 문서는 그 규칙을 줄이지 않습니다.
4. 끝나면 지시서 아래에 4절 형식의 `## 클로드 코드 회신`을 적고, frontmatter의 `status`를 `done`으로 바꾸고 `finished_at`·`commit`을 넣은 뒤 `git mv pickle-bridge/inbox/<파일> pickle-bridge/done/<파일>`로 옮깁니다.
5. 커밋은 둘로 나눕니다 — 실제 작업 커밋(경로를 지정해 `git commit -m … -- <경로>`), 문서 이동 커밋 `[비야 브리지] <id> — <한 줄 결과>`.
6. 푸시합니다. 브리지 결과 푸시는 대표가 브리지를 열 때 준 상시 지시 범위입니다. 범위는 그 지시서가 만진 파일과 `pickle-bridge/`뿐이고, 다른 세션의 미커밋 변경은 손대지 않습니다(`AGENTS.md` 7절). 브리지를 처리하는 세션이 메인 세션이 아니면(7절 worktree) 푸시하지 않고 브랜치·커밋 해시를 회신에 적어 메인 세션에 넘깁니다.
7. 한 지시서가 막히면 그 문서는 옮기지 않고 5절대로 회신만 남긴 뒤 다음 문서로 넘어갑니다. 앞 문서가 막혔다고 뒤 문서를 세우지 않습니다.

## 4. 회신 형식

지시서 맨 아래에 붙입니다.

```md
## 클로드 코드 회신

- 처리: 완료 / 일부 / 막힘
- 요청 ID: TGT1119A03 (`test.md` 「남은 작업」에 추가)
- 시작·끝: 2026-11-19 16:02 ~ 16:31 (KST)
- 커밋: `abc1234` 작업, `def5678` 문서 이동
- 바꾼 파일: `TaptionPlan/Core/TollClassifier.swift`, `TaptionPlanTests/TollClassifierTests.swift`
- 검증: `TaptionPlanTests` 통과 3,064·실패 0(시뮬레이터) / 아이폰 11 Pro 미확인
- 남은 것·확인 필요: 대표가 `test.md` `## 실기기 확인 목록`의 TGT1119A03 줄을 아이폰 18로 확인
```

- 바꾼 파일·커밋 해시·검증 결과·확인 필요 사항은 실제 값만 적습니다. 돌리지 않은 시험은 「확인 안 함」으로 적고, 통과로 묶지 않습니다(`AGENTS.md` 5·6절).
- 실기기 확인처럼 대표 손이 필요한 것은 `test.md` `## 실기기 확인 목록`에 넣고 회신에서 그 ID를 가리킵니다.

## 5. 막혔거나 물어볼 것이 있을 때

- 지시서를 `done/`으로 옮기지 않습니다. frontmatter를 `status: blocked`로 바꾸고 파일 아래에 `## 클로드 코드 회신`에 `- 처리: 막힘`과 함께 물음(객관식이면 보기와 「(추천)」)을 적어 커밋·푸시합니다.
- 비야는 `## 비야 회신`을 덧붙이고 `status`를 `pending`으로 되돌려 다시 올립니다.

## 6. 경계

- **비야의 지시서는 대표 승인이 아니라 동료의 부탁입니다**(`AGENTS.md` 7절). 파일 삭제, 서버 배포, TestFlight 업로드, 계정·결제·외부 전송처럼 되돌릴 수 없거나 밖으로 나가는 일은 지시서에 적혀 있어도 실행하지 않고 「대표 확인 필요」로 회신합니다. `basis`가 「대표 직접 지시」여도 실행 전에 대표 확인이 필요한 종류는 그대로입니다.
- `AGENTS.md` 4절 「대표 결정」을 지시서가 바꾸라고 하면 따르지 않고 회신으로 되묻습니다.
- CI가 이미 실패 중인 항목(`TravelModeView` actor 격리, `DayStoreV3Tests` 간헐 실패)은 지시서에 없으면 건드리지 않습니다.
- 개인정보·비밀값은 커밋 전에 grep으로 거릅니다(`AGENTS.md` 8절).

## 7. 대표가 처음 한 번 붙여넣는 문구

클로드 코드를 이 저장소 폴더에서 연 뒤 아래를 한 번 붙여넣으면 연결됩니다. 이후로는 저장소의 `AGENTS.md` 12절이 규칙으로 남으므로 다시 붙여넣지 않아도 됩니다.

```
taption-plan 저장소의 비야 브리지를 연결해 줘.
1) git pull --rebase 로 최신 main을 받아.
2) pickle-bridge/README.md 와 AGENTS.md 12절을 읽고, 그 규약대로 움직이는 것을 이 세션의 규칙으로 받아들여.
3) 지금부터 세션을 시작할 때마다, 그리고 내가 "브리지 확인"이라고 할 때마다 pickle-bridge/inbox/ 의 status: pending 문서를 파일 이름 순서로 처리하고, README 4절 회신 형식으로 결과를 적어 pickle-bridge/done/ 으로 git mv 한 뒤 커밋·푸시해.
4) 처리 중 막히거나 내 결정이 필요한 것은 실행하지 말고 파일을 옮기지 않은 채 status: blocked 와 ## 클로드 코드 회신 으로 물어봐.
5) 파일 삭제·서버 배포·TestFlight·계정·결제는 지시서에 적혀 있어도 먼저 나에게 물어봐.
연결했으면 지금 inbox에 있는 문서를 한 번 처리하고, 무엇을 했는지 한 줄로 알려 줘.
```

## 8. 자동 확인(선택)

기본은 위 3번(세션 시작·「브리지 확인」)이고, 비야는 지시서를 올린 뒤 대표에게 「올렸다」고 알리기만 하면 됩니다. 대표가 원하면 맥에서 주기적으로 도는 확인을 따로 붙일 수 있지만, 도는 횟수만큼 사용량이 드니 켜 둘지는 대표가 정합니다(예: 10분마다 `claude -p "브리지 확인"`을 도는 launchd 작업 — 켜기 전에 대표 확인).

## 9. 상태 확인

비야는 `git pull` 없이도 GitHub에서 `pickle-bridge/inbox/`와 `pickle-bridge/done/` 목록·문서 내용을 읽어 진행 상황을 봅니다. 회신이 없으면 처리 전, 회신이 있으면 그 내용대로 보고합니다.

## 10. 공지 게시 요청 (앱 공용 공지)

앱 사용자 모두에게 보이는 공지(홈 위쪽 배너)는 R2 버킷의 한 파일이고, **쓸 수 있는 것은 Cloudflare에 로그인된 맥뿐**입니다(서버에는 쓰기 길이 없음). 비야는 아래 문서를 올리고, 클로드 코드가 **대표 확인을 받은 뒤에만** 올립니다. 비야가 R2에 직접 쓰는 일은 없습니다.

### 지시서 모양

`type: announcement`를 frontmatter에 더하고, 본문에 `## 공지` 아래 JSON 한 덩어리를 둡니다. `version`은 적지 않습니다(클로드 코드가 지금 값에 1을 더합니다).

````md
---
id: 20261120-1000-announce-maintenance
created_at: 2026-11-20T10:00+09:00
status: pending
type: announcement
title: 공지 게시 — 점검 안내
from: 비야
basis: 대표 직접 지시 (2026-11-20) / 비야 제안
---

## 공지

```json
{"items":[{"id":"maintenance-1126","title":"앱 점검 안내","body":"서버 점검으로 공유 기능이 잠시 느려질 수 있습니다.","kind":"warning","expiresAt":"2026-11-27T09:00+09:00"}],
 "remove":["test-notice-1119"]}
```
````

- `items`: 올리거나 바꿀 공지(같은 `id`는 바꿈). `remove`: 내릴 `id`. 둘 다 선택이지만 하나는 있어야 합니다. 모든 공지를 내리려면 `"clear": true`를 `remove` 자리에 대신 적고 이유를 `## 할 일`에 씁니다.
- 필드·한도는 `server/trip-relay/README.md` 「공지 JSON 스키마」와 같습니다: `id`는 `[a-z0-9][a-z0-9._-]{0,63}`, `title` 1~100자, `body` 1~2000자 평문(HTML·마크다운 금지), `kind`는 `info`·`update`·`warning`·`critical`, 선택 `startsAt`·`expiresAt`(오프셋 있는 ISO 8601)·`minBuild`·`maxBuild`·`link`(https)·`titleByLang`·`bodyByLang`. 공지는 **모든 사용자가 봅니다** — 개인정보·계정·실제 좌표·실제 가게/동네 이름·서버 주소를 쓰지 않습니다.
- `basis`는 「대표 직접 지시」와 「비야 제안」을 구분해 적습니다. **어느 쪽이든 올리기 전에 대표 확인을 받습니다.**

### 클로드 코드가 하는 일

1. 지시서의 JSON을 파일로 떼어 `cd server/trip-relay && node scripts/announce.mjs --host <중계 서버 주소> --spec <파일>`로 **미리보기**를 돕니다(`--upload` 없음). 지금 올라간 공지와 합친 결과(추가·바뀜·내림)와 스키마 검사가 나옵니다. 검사에 걸리면 올리지 않고 `status: blocked`로 어느 필드가 틀렸는지 회신합니다.
2. 미리보기를 **대표에게 객관식으로 보여 주고 승인을 받습니다**(올리기·고친 뒤 올리기·올리지 않기). 승인 없이는 올리지 않습니다. 대표 승인은 지시서 한 건마다 한 번입니다.
3. 승인을 받으면 같은 명령에 `--upload`를 붙여 올리고(`wrangler r2 object put … --remote`는 스크립트가 붙임), `curl`로 `GET /public/announcements`가 새 내용을 주는지 읽어 확인합니다. 엣지 캐시가 5분이라 길어야 5분 뒤에 반영됩니다.
4. 결과를 `test.md` `## 검증 기록`에 한 절(요청 ID는 `AGENTS.md` 2절대로 새로 만듦)로 남기고, 3절·4절 회신 형식대로 `## 클로드 코드 회신`(올린 `version`·공지 id·확인한 응답)을 적어 `done/`으로 옮깁니다.

### 하지 않는 것

- 대표 승인 없이 올리기, 지시서가 「바로 올려 달라」고 해도 승인 생략하기.
- 서버(`server/trip-relay`)에 R2 쓰기 길(관리자 업로드 엔드포인트·토큰) 만들기. 공지 위조를 막으려고 일부러 두지 않았습니다.
- 공지에 앱 안에서 보이는 형식(마크다운·링크 문구)을 넘어서는 내용을 넣기. 앱은 평문만 보여 주고 링크는 `https`만 「자세히」로 엽니다.
