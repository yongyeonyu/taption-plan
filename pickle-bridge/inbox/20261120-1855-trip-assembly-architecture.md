## 0. 이 문서의 지위

**처리 순서(브리지 공통, 2026-11-20 점검)**: 파일 이름 순서로 **가장 마지막** 문서이고, 그 자체로 실행할 문서가 아니라 설계도입니다. 그래서 **이 문서를 읽고 바로 코드를 쓰지 않았습니다**(0절). 실행은 이미 올라간 `FLT1120A01`·`TRN1120A01/A02`·`STAY1120A01`·`AUTO1120A01`·`RUL1120A01`·`ADM1120A03`이 맡고, 이 문서는 그것들 사이의 경계(카드 칸 이름·조립 규칙·팩 배포)만 정합니다. 그 지시서들이 이 설계와 **칸 이름·보류·좌표 규칙에서 어긋나는 곳**을 2·6절에 표시해 두었습니다 — 실행할 때는 **지시서의 실제 코드 이름이 이 문서의 개념 이름보다 우선**합니다.

## 1. 큰 그림 — 다섯 층

```
L5  여행 껍데기      여행(기간·이름·도시)          ← AUTO1120A01
L4  조립기          계획 슬롯에 카드를 배치         ← 이 문서의 핵심(일본)
L3  카드 소스       (a) 알림 자동: 항공·숙박·기차·버스·배·결제
                   (b) 도시 팩: 숙소·식당·관광지·정류장  ← 일본 먼저
                   (c) AI 대화 / 사용자 직접 입력
L2  카드(항목)      종류·시각·장소·금액·출처·링크
L1  저장·배포       기기 로컬(개인 일정) / R2(공용 팩) / D1(규칙·템플릿)
```

핵심 원칙 넷:
1. **개인 일정은 기기에, 공용 자료는 팩으로.** 도시 팩에는 누구의 일정도 들어가지 않습니다.
2. **일본과 그 밖은 같은 그릇, 다른 채움.** 카드 종류·저장 구조·화면은 하나이고, **채우는 방법만** 다릅니다(일본=팩 조립, 그 밖=알림+AI+수동).
3. **알림으로 정해지는 것은 앱이 묻지 않는다.** 기간·출발·도착·금액은 예약에서 확정(AUTO1120A01).
4. **앱이 하지 않는 일**: 예약·결제·가격 표시(트립닷컴 등 제휴 **링크로 넘김**), 대량 크롤링.

## 2. L2 — 카드는 하나의 모양

지금 `TravelTripItem`(`Packages/TaptionPlanStore/Sources/TaptionPlanStore/Snapshot/AppFeatureSettings.swift:569~`)이 이미 종류(`kind: String`)·시작·끝(`start`·`end` Date)·제목(`title`)·메모(`note`)를 갖고 있습니다. **새 카드 타입을 만들지 않고** 다음 칸을 더합니다.

> **이름은 실제 코드를 따른다(2026-11-20 점검)** — 아래 `TripItem`은 **개념 모양**이고, 실제 `kind` 값은 이미 있는 12종(`flight·lodging·meal·cafe·sight·shopping·activity·photo·rest·sleep·transfer·other`, `TravelPlanColumns.allKinds`)에 FLT1120A01 D-1-3가 더하는 `train·bus·ferry`를 합친 것이다. 그러므로 **`stay`는 `lodging`, `shop`은 `shopping`** 이다. `memo`는 **새 kind를 만들지 않고** `note`를 쓰거나 `activity`로 둔다. `status`는 지금 `booked`·`tentative` 두 값만 쓰고 **계획(미정)는 nil**이다(`status` 주석) — `planned`를 새 값으로 넣지 않는다.

```
TripItem
  kind        flight | train | bus | ferry | lodging | meal | cafe | sight | shopping | activity | …
  title       표시 이름(자동이면 「숙소명」·「식당명」, 사용자가 고칠 수 있음)
  startAt / endAt      시각 또는 날짜(숙박은 체크인~체크아웃 — H-2)
  place       { name, area, lat?, lng? }   ← 좌표는 팩에서 왔을 때만
  cost        { amount?, currency?, source?, expenseID? }   ← 정본은 지출(C-3)
  source      alert | pack | ai | manual
  packRef     { city, packID, itemID } | nil
  external    { link?, provider? }   ← 예약 링크(트립닷컴 등), 표시용
  status      booked | tentative | nil(계획)   (지금 코드 그대로 — 새 값 planned를 만들지 않는다)
```

- `source`가 이 설계의 핵심 칸입니다. 「자동 추가됨 · 문자+알림」·「도시 팩 · 라쿠텐」·「AI 제안」·「직접 입력」을 사용자에게 그대로 보여 줍니다.
- 좌표는 세 곳에서만 온다: ⑴ 팩 항목의 좌표(공개 자료·사람 검수), ⑵ 역·터미널·공항·항구 카탈로그 좌표(FLT1120A01 D-1-3처럼 알면 핀을 찍는다), ⑶ 사용자가 장소를 고르거나 AI가 지도 검색으로 확정한 좌표. **없으면 핀을 찍지 않고 목록에만 둡니다**(추측 좌표·주소 지오코딩으로 만든 핀 금지).

## 3. L3-(a) 알림 자동 — 모든 나라 공통

이미 정한 것(C·D·E·F·H·I절)을 그대로 씁니다. 이 설계에서 추가로 못 박는 것만 적습니다.

1. **유입 3종**: 문자(SMS) · 카카오톡 알림톡(복사/공유) · 앱 알림. 어느 나라 예약이든 같은 통로.
2. **해외 결제 문자도 같은 규칙**: 통화가 다르면 `currency`를 그대로 두고 원화 환산은 표시에서만(환율은 기존 `fx` 경로). 금액을 임의로 원화로 바꿔 저장하지 않습니다.
3. **해외 숙박·항공은 알림이 정본**: 일본 밖(예: 방콕·다낭)은 도시 팩이 없으므로, 알림으로 들어온 항공·숙박·결제가 그 여행의 뼈대가 됩니다.
4. **판정 근거는 D1**(F-4-6) — PostHog 아님.

## 4. L3-(b) 도시 팩 — **일본 먼저**

### 4-1. 왜 일본인가 (확인한 사실)

- **라쿠텐 트래블(楽天トラベル) 신버전 API** — `Travel/SimpleHotelSearch/20260731`·`Travel/HotelDetailSearch/20260731`·`Travel/KeywordHotelSearch/20260731`. 구버전(`20170426` 등)은 2027-01-18 폐기 예정. **일본 국내 숙소만**, 호텔명·위치·가격대·평점·빈방까지 온다. 라쿠텐 웹서비스는 **현재 무료**이고, 앱 등록(`applicationId` + `applicationSecret`, 호스트 `openapi.rakuten.co.jp`)과 **라쿠텐 트래블 링크·출처 표기** 조건이 있다. (확인: 2026-11-17)
- **핫페퍼 구루메 서치 API**(リクルートWEBサービス, `webservice.recruit.co.jp/hotpepper/gourmet/v1/`) — 상점명·장르·예산·영업시간·교통·사진·개인실/금연/영어메뉴, **반경 검색(lat/lng/range)**. 무료·하루 1,000회·키 필요·일본 전용. (확인: 2026-11-17)
- **관광지** — 무료 공식 API가 마땅치 않아 **사람이 검수한 시드**(도시당 30~60곳: 이름·카테고리·좌표·한 줄 설명·소요시간·출처). OSM은 ODbL 조건 때문에 기본 소스로 쓰지 않는다. (대표 결정 2026-11-17)
- **예약·가격 표시는 하지 않는다.** 앱은 트립닷컴 **링크로 넘긴다**(대표: 「예약은 링크로 넘기는데 되는 건 트립닷컴밖에 없다」).

### 4-2. 팩의 모양과 배포 (시즌 팩과 같은 방식)

```
packs/trip/<city>/<version>/index.json      카탈로그(항목 목록·해시·크기·생성일·출처)
packs/trip/<city>/<version>/items.json      카드 후보(숙소·식당·관광지·정류장/역)
packs/trip/<city>/<version>/images/…        썸네일(선택)
```

- 서버가 API를 **한 번 받아 가공**해 팩을 만들고 R2에 올립니다(앱이 매번 API를 때리지 않는다 — 한도·약관·속도).
- 앱은 **시즌 팩과 같은 다운로드·검증·캐시 경로**를 씁니다(새 배포 체계를 만들지 않는다). 서명 번들 검증 규칙도 같게.
- 도시 하나가 곧 한 팩. 전국·전 세계 일괄 배포 금지(용량·배터리).
- 항목에 반드시 `source`(rakuten_travel|hotpepper|seed)·`sourceURL`·`fetchedAt`을 넣어 출처 표기를 앱에서도 할 수 있게 합니다.
- **API 응답은 저장소에 커밋하지 않습니다.** 라쿠텐·핫페퍼 같은 API에서 받은 자료를 git에 두면 그 서비스의 저장·재배포 조건과 부딪힙니다. 저장소에는 **사람이 직접 조사한 시드만** 두고, API 보강분은 서버가 받아 **R2 팩 안에만** 둡니다(원본 응답을 별도 저장하지 않음 — 팩이 유일한 사본).

### 4-3. 1차 도시

- **후쿠오카급 한 도시**를 끝까지(팩 생성 → 앱 표시 → 조립) 해 보고 문제점을 본 뒤 도쿄·오사카로 넓힙니다. (2026-11-17 범위 결정)
- 도시 목록·우선순위는 대표가 일본 일정을 정할 때 확정합니다. 이 문서는 **후쿠오카를 기본 예시**로만 씁니다.

### 4-4. 테마 층 (선택, 2차)

`theme: [미식, 온천, 쇼핑, 의료·약국, 애니메…]` 태그를 팩 항목에 두고, 테마를 고르면 그 태그만 걸러 조립합니다. **처방이 필요한 의약품**(예: 비만·당뇨 치료제 계열)은 **처방 필요·반입 주의 안내만** 넣고 구매 경로(구매처·가격·직구 방법)를 안내하지 않습니다(2026-11-17 기록). **약 이름 예시를 저장소·팩에 특정 제품명으로 적지 않습니다** — 공개 저장소이고, 특정 약을 찾는 사람의 관심이 드러날 수 있습니다.

### 4-5. 사람이 조사한 시드 — 팩의 본체 (대표 지시 2026-11-20 18:56)

대표 지시: 「내가 수기로 다 조사해 갖고 숙박·음식점·커피숍·관광지·쇼핑·병원·약국·놀이공원·테마파크·렌터카 이런 거를 조사해서 올리기로 했잖아. 그거를 서버에서 다운받아서 사람들이 쓸 수 있게.」

**결론: 팩의 본체는 사람이 조사한 시드이고, 라쿠텐·핫페퍼는 그것을 채우고 갱신하는 보조다.** API가 덮지 못하는 분야(카페·쇼핑·병원·약국·테마파크·렌터카·관광지)는 시드가 유일한 소스다.

1. **카테고리(대표가 든 것 전부)**: `stay`(숙박) · `restaurant`(음식점) · `cafe`(커피숍) · `sight`(관광지) · `shop`(쇼핑) · `hospital`(병원) · `pharmacy`(약국) · `themepark`(놀이공원·테마파크) · `rentcar`(렌터카) · 그리고 기존 `bus_stop`·`rail_station`·`airport`·`port`. 새 카테고리를 앱 코드에 박지 말고 **팩이 선언**하게 한다(모르는 카테고리는 목록에서 제외 — 시즌 팩의 「모르는 열쇠는 무시」 규칙과 같게).
2. **항목 형식(한 항목)**: `{ id, category, name(현지어), nameKo, area, address, lat, lng, phone?, hours?, priceHint?, tags[], note(한 줄), source: "seed", sourceURL?, checkedAt, checkedBy, photo? }`.
   - `checkedAt`·`checkedBy`는 **필수**다. 언제 누가 확인한 정보인지가 이 팩의 신뢰도다. 다만 **`checkedBy`는 비식별 표기**(예: `대표`, `비야` 같은 역할·애칭)만 쓰고 실명·계정·연락처를 팩·저장소에 넣지 않는다. `phone?`은 **업소·기관 대표번호만**이고 개인 휴대전화는 넣지 않는다.
3. **서버에 올리는 길**: 시드 원본은 저장소 `seed/trip/<city>/`(JSON·CSV)에 두고, 팩 생성 스크립트가 API 보강분과 합쳐 `packs/trip/<city>/<version>/`을 만든다. **원본과 팩을 따로 관리하지 않는다**(시즌 팩의 「매니페스트 하나」 원칙과 같게). `seed/trip/`에는 **사람이 직접 조사한 항목만** 두고, 라쿠텐·핫페퍼 응답·스크랩을 그대로 커밋하지 않는다(4-2).
4. **사람들이 내려받아 쓴다**: 팩은 공용이라 한 번 올리면 모든 사용자가 같은 도시 팩을 받는다. 개인 일정과 섞이지 않는다(7절).
5. **사진·글**: 직접 찍은 사진 또는 재배포가 허용된 것만 넣는다. 남의 사진·설명문을 그대로 옮기지 않는다(저작권). `photo`가 없으면 목록에 글자만 보인다.
6. **병원·약국은 안전 정보로 다룬다**: 응급 연락·영업시간은 **확인일을 화면에 같이** 보이고, 확인일이 90일을 넘으면 「오래된 정보 · 확인 필요」로 표시한다. 처방 필요 의약품의 구매 경로는 안내하지 않는다(4-4).
7. **갱신**: 시드가 바뀌면 `version`을 올려 새 팩으로 올린다. 앱은 시즌 팩과 같은 「새 버전만 받기」 규칙을 따른다.
8. **비어 있는 도시가 정상**: 시드가 없는 도시는 팩이 없고, 그 도시는 6절(알림·AI·수동)로 동작한다. 빈 팩을 만들어 「0건」을 배포하지 않는다.

## 5. L4 — 조립기 (일본)

### 5-1. 조립이란

여행 껍데기(L5)의 기간 안에, 이미 확정된 카드(항공·숙박·이동)를 **고정점**으로 놓고, 그 사이 빈 시간에 팩의 후보(식당·관광지)를 **결정적 규칙으로** 배치해 한 장의 계획표를 만드는 일입니다.

### 5-2. 규칙 (AI 없이도 나와야 한다)

1. **고정점 우선**: 항공 출발·도착, 숙박 체크인·체크아웃, 예약된 기차·버스는 절대 옮기지 않습니다.
2. **하루 골격**: 아침·점심·저녁 식사 3칸(식당 후보에서), 오전·오후 관광 2칸(관광지 후보에서, 소요시간 합계 ≤ 그 구간 길이).
3. **거리 순서**: 같은 날 후보는 **이동 거리 합이 최소**가 되게 정렬합니다(팩 좌표가 있을 때만. 없으면 순서 고정하지 않음).
4. **중복 금지**: 같은 팩 항목을 한 여행에서 두 번 넣지 않습니다.
5. **빈칸은 비워 둔다**: 후보가 없거나 확신이 없으면 **억지로 채우지 않습니다.** 「비어 있음」이 정상 상태입니다(AI가 채우자는 제안은 가능).
6. **결정적**: 같은 입력이면 같은 계획이 나옵니다. AI는 **나중에 조정**하는 층(5-3)이고, 조립 자체를 AI에 맡기지 않습니다.
7. **한 번에 다 하지 않는다**: 「자동으로 채우기」를 누르면 **하루치씩** 채우고, 사용자가 지우거나 옮기면 그 자리는 다시 자동으로 채우지 않습니다(`autoFilled` 플래그).

### 5-3. AI가 하는 일 (조립 뒤)

1. 사용자의 말로 조정: 「둘째 날 오후는 쇼핑으로 바꿔」, 「여기서 가까운 라멘집」.
2. 후보 설명·추천 이유 한 줄(팩에 없는 사실을 만들지 않는다 — 팩 값만 인용).
3. 일정 충돌·이동 시간 부족 경고.

## 6. L3-(c) 일본 밖 — 알림 + AI + 수동

1. **뼈대는 알림**(3절). 항공·숙박·결제가 자동으로 들어오고, 여행 껍데기는 I절대로 자동 생성됩니다.
2. **나머지는 두 길**: ① AI에게 말해 추가(「셋째 날 오전에 왕궁 넣어 줘」) ② 직접 입력(지금의 일정 추가 화면).
3. **도시 팩이 없는 나라에서 하지 않는 것**: 자동으로 관광지를 채우지 않습니다. 팩이 없는데 채우면 지어낸 것이 됩니다.
4. **좌표**: 사용자가 장소를 고르거나 AI가 지도 검색으로 확정한 경우에만 핀을 찍습니다. 추측 좌표 금지.
5. **환율·통화**: 여행지 통화 칸은 기존 지갑 설계(TVM1111A01)를 그대로.

## 7. 개인정보·약관 (설계에 박아 둔다)

1. **팩은 공용**이다 — 개인 일정·지출·위치·예약번호가 팩에 절대 섞이지 않습니다. 팩 생성은 서버에서 공개 API 응답만으로 합니다.
2. **알림 원문은 기기 안**(E-7·F-7). 서버로는 확정된 필드만.
3. **출처 표기**: 라쿠텐 트래블·핫페퍼의 표기·링크 조건을 앱 화면과 팩 `source`에 넣습니다. 조건을 못 지키면 그 출처는 빼는 쪽으로 판단합니다.
   - **순서를 못 박는다**: 표기 조건 원문(로고·문구·링크 위치·고지 문장)을 **구현 전에 해당 서비스 약관에서 직접 읽어** `docs/`의 한 절에 옮겨 적고(출처 URL·확인일 포함), 그 절이 없으면 그 출처를 팩에 넣지 않습니다. 기억·추측으로 표기 문구를 만들지 않습니다 — 출처 표기 누락은 약관 위반이고, 앱 전체를 내려야 하는 사유가 됩니다.
4. **API 키는 워커 시크릿**. 팩·앱·이 문서에 값이 없습니다. 한도(핫페퍼 1,000/일 등)는 서버 캐시로 지킵니다.
5. **알골리아(10절)도 같은 선**: 팩 검색 색인에는 공용 팩 필드만, 개인 기록 색인은 사용자 동의 + 시군구까지만. 국외 이전(미국 리전)이므로 2단계를 켤 때 고지 문구와 동의를 같은 커밋에 넣고, 끄면 즉시 삭제합니다.
5. **크롤링 금지**: 팩은 공개 API + 사람 검수 시드로만 만듭니다.

## 8. 단계 (순서 고정)

| 단계 | 내용 | 끝났다고 보는 기준 |
|---|---|---|
| 0 | 이 설계 확정(대표 확인) | 대표가 「이대로」 |
| 1 | 카드 모델 확장(L2: `source`·`packRef`·`external`) | 기존 시험 통과 + 새 칸 없이 열리는 저장본 |
| 2 | 도시 팩 파이프라인(후쿠오카): 서버 생성 스크립트 → R2 → 앱 다운로드·캐시 | 앱이 팩 목록을 받아 보여 줌(빈 일정에서도) |
| 3 | 조립기(5-2 규칙 1~7) | 후쿠오카 2박 3일이 규칙만으로 채워짐 |
| 4 | AI 조정(5-3) | 말로 한 칸 바꾸기·추천 한 줄 |
| 5 | 도쿄·오사카 확장 | 같은 파이프라인에 도시만 추가 |
| 6 | 일본 밖(6절) | 알림만으로 만든 해외 여행에 AI·수동 추가가 동작 |

**1~3단계가 「일본 먼저」의 최소 완성선**입니다. 4단계는 3단계가 안정된 뒤.

검색 색인은 **2단계 끝에** 붙입니다(10절): 팩이 R2에 올라간 뒤 같은 파이프라인이 알골리아 색인을 갱신하고, 앱은 그 색인으로 팩을 찾습니다.

## 9. 회신에 적어 주실 것

1. 이 설계에서 **지금 코드로 이미 되는 것 / 새로 만들어야 하는 것** 목록(파일·줄 근거).
2. `TravelTripItem` 확장이 마이그레이션 없이 되는지, 안 되면 무엇이 막는지.
3. 시즌 팩 다운로드 경로를 여행 팩에 **그대로 재사용**할 수 있는지(재사용 불가면 이유와 대안).
4. 라쿠텐·핫페퍼 앱 등록에서 대표가 해야 할 일(키 발급 절차·심사 여부·표기 조건 원문) — **키 값은 적지 말고 절차만.**
5. 1단계 착수 가능 시점과 예상 순서. 막히면 `status: blocked`로 이유와 보기(추천 먼저).

### 10-2. 1순위 — 도시 팩 검색 (개인정보 없음)

팩은 공용 자료(7-1)라 알골리아에 올려도 개인정보가 섞이지 않고, 한 번 색인하면 모든 사용자가 같은 색인을 씁니다. 사용자마다 색인을 만들지 않습니다.

1. **색인**: `trip_packs_v1` 하나. 팩 항목 1건이 레코드 1건이고, `city`·`version`을 속성으로 두어 필터로 최신 버전만 조회합니다(현재 쓰는 도시는 1~3개라 색인을 도시별로 쪼개지 않음).
2. **레코드 값**: 4-5-2의 항목 형식을 그대로 씁니다 — `name`·`nameKo`·`category`·`area`·`tags`·`hours?`·`priceHint?`·`lat`·`lng`·`source`·`checkedAt`·`photo?`. `address`·`phone?`은 검색에 필요 없으므로 색인하지 않습니다(앱은 팩에서 직접 읽음).
3. **쓰기 경로**: 팩 생성 스크립트가 R2에 새 버전을 올린 **뒤**(단계 2) 워커가 알골리아 Write API로 배치 색인합니다. 쓰기 키는 **워커 시크릿**에만 두고 앱·저장소·문서 어디에도 값으로 적지 않습니다(7-4와 같은 원칙).
4. **읽기 경로**: 앱은 **Search API Key(공개용, 앱 탑재 가능)** 만 갖습니다. 가능하면 Secured API Key로 `filters=city:… AND version:…`과 `validUntil`을 걸어 발급하고, 앱에 관리 키를 넣지 않습니다.
5. **갱신·삭제**: 새 버전을 색인한 뒤 이전 버전 objectID를 지우고(`batch delete`), 팩이 없어진 도시는 그 도시 objectID를 전부 지웁니다(`deleteBy`). 시드가 없어 팩을 만들지 않는 도시는 색인도 만들지 않습니다(4-5-8).
6. **검색 품질**: 오타 보정, 한국어·일본어·영어 동의어(예: ラーメン ↔ 라멘 ↔ ramen), 카테고리·태그 필터. 다국어 동의어는 알골리아 인덱스 설정에 두고 **앱 코드에 사전을 박지 않습니다**.
7. **좌표 — 이 절의 유일한 금지선**: 알골리아 geo-search(`aroundLatLng`)는 **사용자의 현재 좌표를 알골리아로 보내는 일**입니다. `AGENTS.md` 4절 좌표 예외 다섯에 없으므로 **대표가 예외를 승인하기 전에는 쓰지 않습니다**. 그때까지 거리 정렬은 기기에서 팩 좌표로 계산합니다(현재 위치는 기기 밖으로 나가지 않음). 대표가 승인하면 4절 예외에 한 줄을 추가하고 그때 켭니다.
8. **의료·약국**: 색인에는 그대로 두되, 화면 표시는 4-5-6 그대로 — `checkedAt`이 90일을 넘으면 「오래된 정보 · 확인 필요」. 처방 필요 의약품의 구매 경로는 검색 결과에도 넣지 않습니다(4-4).

### 10-3. 2단계(옵션) — 개인 하루 기록 검색

기본값은 **끔**입니다. 사용자가 데이터 보호 설정에서 「기록 검색」을 직접 켜고 국외 이전 고지에 동의했을 때만 색인합니다(PHG1120A01의 「직접 누르고 동의했을 때만」과 같은 선).

1. **색인 필드 최소**: `날짜(YYYY-MM-DD)`·`장소명`·`시군구`·`카테고리`·`짧은 메모(사용자가 쓴 30자 이내)`. **원본 GPS·지출 금액·일기 원문·사진·예약번호는 넣지 않습니다.** 위치는 시군구까지만이고 동·번지·좌표는 넣지 않습니다.
2. **분리**: 사용자마다 인덱스를 만들지 않고 `userKey`(기기에서 만든 임의 해시, 계정 ID 아님) 속성으로 나눕니다. 앱이 받는 검색 키는 Secured API Key로 `filters=userKey:…`를 걸어 발급합니다.
3. **삭제**: 토글을 끄면 워커가 그 `userKey`의 objectID를 **즉시 전부 삭제**합니다. 앱에서 기록·여행을 지울 때도 같은 경로로 지웁니다(색인 삭제 API).
4. **비용**: 이 색인만 사용량이 사용자 수에 비례해 Free/Grow 한도에 가장 먼저 닿습니다. 그래서 1순위가 아니라 2단계입니다.

### 10-4. 하지 않는 것 (경계)

- 알골리아를 **정본으로 쓰지 않습니다**. 팩 정본은 R2, 개인 기록 정본은 기기 SQLite이고 알골리아는 검색용 파생입니다. 알골리아가 응답하지 않으면 앱은 로컬(팩 파일·SQLite) 검색으로 폴백합니다.
- **알골리아에 보내는 것은 위 두 색인의 필드뿐**입니다. 좌표(10-2-7 예외 승인 전), 지출 금액, 일기 원문, 예약번호, 계정 식별자는 보내지 않습니다.
- 팩 원본·라쿠텐·핫페퍼 API 응답을 알골리아에 그대로 밀어 넣지 않습니다 — R2 팩이 유일한 사본이고(4-2), 알골리아에는 팩에서 고른 필드만 갑니다.
- 앱·저장소·문서에 Write/Admin 키를 두지 않습니다. 키 값은 대시보드에서 대표가 워커 시크릿으로 넣습니다.

### 10-5. 실행 순서
