## A. 중계 서버 (`server/trip-relay`)

### A-1. 없는 것만 채운다

1. **국내선 출발·도착 시각 (핵심).** 지금 행에는 `time` 하나뿐이라 앱이 도착을 거리로 어림한다. 행에 **선택 필드 셋**을 더한다(없으면 `null`, 기존 필드 의미·이름은 그대로): `departureTime`(출발 공항 현지 `HH:mm`)·`arrivalTime`(도착 공항 현지 `HH:mm`)·`durationMinutes`(정수).
   - `direction: "dep"` 행의 `time`은 **출발**, `arr` 행의 `time`은 **도착**(앱 계약: "조회한 공항의 현지 시각"). 지금 `FIELD.time`이 출발·도착 칸 이름을 한 목록에 섞어 두었으므로(59~62행) **방향별 우선순위로 나눈다**.
   - 상류에 두 시각이 다 있으면 `time`과 함께 셋을 채우고, 둘 다 있을 때만 `durationMinutes`를 계산한다(자정을 넘기면 `+1440`).
   - 칸 이름은 문서로 확인되지 않았다(README 132행). 키가 있으면 먼저 `scripts/flights-probe.mjs`로 실제 칸 이름을 찍어 `SOURCES`·`FIELD`만 고친다. 키가 아직 없으면 픽스처로 끝내고 「상류 칸 이름 미확인」을 회신에 남긴다(필드가 비어 오면 앱은 어림으로 되돌아간다 — 안전한 실패).
2. **국내 모든 공항 커버리지.** 한국공항공사 계열 소스로 **GMP·PUS·CJU·TAE·CJJ·KWJ·MWX·RSU·USN·KPO·HIN·KUV·WJU·YNY 14개**를 덮는다. 인천 ICN은 국내선이 없어 이 소스 대상이 아니다(기존 분기 그대로). 국제선(ICN) 동작은 바꾸지 않는다.
3. **`/flights/status` 범위 — 인천만 유지(결정).** 국내 공항 실시간은 별도 서비스·키가 필요하고 대표 요구(편명·출발·도착 시각 조회)에 들지 않는다. 국내는 지금처럼 `{ available:false, flights:[], source:"season" }`. 앱은 국내선에서 이 경로를 부르지 않는다(B-7). 나중에 넓히면 `available:true`·`source:"status"`로 주는 것만으로 앱이 「실시간 운항 반영」으로 표시한다 — 계약을 바꾸지 않고 넓힐 수 있다는 것만 README에 한 줄.
4. **캐시 30분.** 정기 스케줄 TTL을 1800초로(대표 지시 10~30분). 키는 `airport`+`date`+`direction`(편명·항공사 필터는 응답 뒤 거르므로 키에 넣지 않는다). 운항현황 90초 유지. 회신에 **상류 하루 호출 추정치**를 숫자로: `(공항 14 × 방향 2 × 조회 날짜 수) × 페이지 수`, 예산 `FLIGHT_DAILY_CALLS`(기본 400) 대비 비율.
5. **키는 비밀값으로만.** `ICN_API_KEY`·`KAC_API_KEY`를 코드·문서·커밋·로그에 평문으로 쓰지 않는다. 없으면 `503 {"error":"flight_key_missing"}`(앱 `keyMissing`), 상류 오류 원문(키가 섞일 수 있음)은 돌려주지 않는다.
6. **오류·한도.** 400 `bad_query` · 422 `date_out_of_range`(status만) · 429 `flight_daily_limit` + `Retry-After` · 502 `upstream_failed` · **404는 내지 않는다**. `/flights/` 한도 분기는 기존 자리(571·614행) 그대로.
7. **크기.** 행 상한 `MAX_FLIGHTS`(800) 유지. 큰 공항·날짜(예: CJU)로 실제 응답 바이트를 재서 회신에 적는다(600KB 아래, 넘으면 상한을 낮춘다).
8. **시험(`test/flights.test.mjs` 확장, 픽스처는 익명).** ⑴ dep·arr의 `origin`/`destination`이 방향에 맞다 ⑵ `departureTime`·`arrivalTime`·`durationMinutes`가 채워지고 23:50→00:20이 30분 ⑶ arr 행의 `time`이 도착 칸에서 온다 ⑷ 캐시 적중 시 상류를 다시 부르지 않고 30분 TTL ⑸ 503·400·429·502. **`npm test` 전체 실행 수·실패 수를 실제 값으로 적는다**(기존 수치를 옮겨 적지 않는다).

### A-3. 배포 — **대표님이 지금 승인했다 (2026-11-20 18:1x 통화, 「100% 그냥 바로 하라고」)** → 즉시 production 배포

`AGENTS.md` 8절은 배포를 대표 손으로 두지만, 이번 건은 대표가 직접·즉시 실행을 지시했으므로 클로드 코드가 배포한다. 승인 날짜·대표 발언을 `test.md` `## 검증 기록`에 남긴다.

```

git pull --rebase
git log --oneline -- src/ | head -20        # 마지막 배포(11-19 19:26 이후)에 들어간 서버 변경 확인
npx wrangler deploy --dry-run --config wrangler.local.toml --outdir /tmp/relay-dry   # 바인딩 확인

```
- **알아 둘 것**: 배포는 워커 전체를 올린다. 11-19 19:26 이후 머지된 서버 변경(예: `CRV1120A01` 11-20 09:59 `53bb8157` — AI 규칙 보호·상류 fetch 502·쓰기 직렬화)도 함께 살아난다. 배포 전후 `git log`로 목록을 확인해 회신에 한 줄 적는다(되돌릴 수 없는 배포이므로 무엇이 함께 나가는지 남긴다).
- **되돌릴 지점을 먼저 적어 둔다**: 배포 전 `npx wrangler deployments list --config wrangler.local.toml`의 **맨 위(직전 배포) 버전 id·시각**을 기록한다(비밀 아님 — 회신 가능). 코드만 되돌릴 때는 `npx wrangler rollback --config wrangler.local.toml`(직전 배포로)을 쓰고, **migration은 되돌리지 못한다**는 점을 같이 적는다(`v3-realtime-room`이 함께 나가면 적용된 뒤에는 지울 수 없다 — RTA1120A02 8절).
- 배포 명령이 실패하면 실패로 적고(로그 마지막 20줄) `status: blocked`로 회신한다. 성공을 추정하지 않는다.
- **비밀값 등록은 대표 몫**(A-4의 503이면 이 등록만 남은 상태다): `npx wrangler secret put KAC_API_KEY --config wrangler.local.toml`(국내선, 한국공항공사) · `npx wrangler secret put ICN_API_KEY --config wrangler.local.toml`(인천, 인천국제공항공사). 키 값은 회신·문서·로그에 쓰지 않는다.
- **D절 열차 라우트도 이번 배포에 함께 나간다(D-2).** `TAGO_SERVICE_KEY`는 이미 바인딩돼 있고(버스정류소 중계), **같은 키로 열차·고속·시외가 다 된다**(실측 2026-11-20 — 새 시크릿 등록 불필요). 그래서 **`wrangler secret put`을 새로 할 것이 없다.** 배포 뒤 `/trains/schedule?from=서울&to=부산&date=<내일>`을 한 번 불러 **200과 80~90편 규모**(실측 기준값 **89편**)인지 확인해 회신에 적는다. `TRAIN_DAILY_CALLS` 기본값 300·캐시 1800초로 둔다(항공과 같은 정책).

### A-4. 배포 직후 라이브 실측 (회신에 숫자로)

1. `GET /flights/schedule?airport=GMP&date=<내일>&direction=dep` → **상태 코드**, `flights` 개수, 앞 3편의 `flight`·`time`·`destination`·`arrivalTime`(있으면), 응답 바이트.
2. `GET /flights/schedule?airport=CJU&date=<내일>&direction=arr` → 같은 값(도착 시각이 `time`으로 오는지).
3. `GET /flights/status?airport=GMP&date=<내일>&direction=dep` → **200**과 `available:false`인지(404가 아니어야 한다).
4. **503 `flight_key_missing`이면 배포는 성공한 것이다.** 실패로 적지 말고, 「경로는 살아났고 키만 없다 — 대표님이 공공데이터포털 키를 받아 위 두 `wrangler secret put`으로 등록하면 조회가 된다」를 한 줄로 남긴다.
5. **`GET /trains/schedule?from=서울&to=부산&date=<내일>`** → 상태 코드와 `trains` 개수, 앞 3편의 `trainNumber`·`trainType`·`departureTime`·`arrivalTime`, 응답 바이트(D-2·A-3). **실측 기준값은 89편**이다(2026-11-20 TAGO 열차, 내일 서울→부산) — 크게 다르면 상류 칸 이름·폴백을 확인한다. `503 train_key_missing`이면 항공과 같은 방식으로 「배포 성공·키 대기」로 적는다.
5-1. **`GET /buses/schedule?from=서울경부&to=부산&date=<내일>&type=express`** → 상태 코드·`buses` 개수·앞 3건의 `serviceNumber`·`departureTime`·`arrivalTime`·`serviceName`·`fare`·응답 바이트. **`TAGO_SERVICE_KEY`가 이미 있으므로 200이 나와야 하고, 실측 기준값은 56편**이다(2026-11-20 고속버스, 내일 서울경부→부산). 503 `bus_key_missing`이면 바인딩 이름이 바뀐 것이다(새 시크릿을 만들지 않았는지 확인). 같은 호출을 `type=intercity&date=<내일>`로 한 번 더 해 `available:false`·`note:"intercity_today_only"`인지 본다.
6. 404면 배포가 반영되지 않은 것(캐시·계정·도메인 확인), 502면 상류 칸 이름·서비스 주소 문제(probe로 확인)로 구분해 적는다. 1~5 중 하나라도 404면 배포 미반영으로 본다.

## B. 앱 (`TaptionPlan`) — 스카이스캐너·구글 플라이트형 검색 화면

지금 `FlightPickerSheet.swift`는 iOS `Form`의 Picker·TextField·Section 목록이다(20·39·41·60·236·257·269·297행). **조회 조건 카드 + 결과 리스트** 구조의 전용 화면으로 다시 짠다. **국제선(출국·귀국)과 국내선이 같은 화면을 쓴다**(국제선은 기존 `date`/`direction` 계약 그대로). **가격 데이터는 서버에 없으므로(예약·가격은 범위 밖) 가격 자리를 만들지 않는다** — 그 자리에 소요 시간과 직항 배지를 둔다.

### B-1. 상단 검색 카드 (구글 플라이트의 검색 바)

- **출발·도착 공항을 좌우로 나란히 둔 두 버튼.** 왼쪽=출발, 오른쪽=도착. 각 버튼은 `공항 코드(크게)` + `한글 이름(작게)`, 누르면 **공항 검색 시트**(B-2)가 뜬다.
- 가운데 **⇄ 버튼**: 두 공항을 맞바꾼다. 국내선은 코드만, 국제선은 출국↔귀국이 뒤집히는 것과 같은 결과가 되게 한다(한국 공항은 그대로, 상대 공항이 바뀐다).
- 그 아래 **날짜 스트립**(가로 스크롤): **어제 ~ +7일(9칸)**, 각 칸에 요일(짧게)과 일자, 선택일 강조. 여행 날짜(첫날·마지막 날)가 범위 안이면 그 칸에 작은 점을 찍어 찾기 쉽게 한다.
- **방향 3지선다**(출국편 / 귀국편 / 국내선). **국내선일 때는 이 컨트롤을 숨긴다**(대표 지시). 다만 그대로 숨기면 국내선에서 나올 길이 없어지므로, **공항 버튼에서 국외 공항을 고르면 국제선으로 돌아와 컨트롤이 다시 보이게** 하고, 국내선일 때는 검색 카드 모서리에 「국내선」 표시를 남긴다(이 해석이 다르면 회신에 적고 대표께 묻는다).
- 「시각표 불러오기」 대신 **조건이 바뀌면 자동 조회**(공항·날짜·방향 변경 시 디바운스 300ms, 「다시 시도」는 수동). 지금의 수동 단추는 결과가 없을 때의 재시도로만 남긴다.
- 공항 선택 규칙: 국내선은 양쪽 다 `FlightAirportCatalog.korea`에서 **인천 ICN만 뺀 14개**, 도착 목록에서 출발 공항 제외. 국제선은 왼쪽(출발)=한국 15개·오른쪽(도착)=전 세계(귀국편이면 반대).

### B-2. 공항 검색 시트

- 코드·한글 이름·영문 이름으로 찾는다(`FlightPlacement.searchAirports`가 이미 그 일을 한다, `FlightAirportCatalog.search`).
- **최근 사용 공항을 상단에 고정**(최대 4개, `@AppStorage`에 코드만 저장 — 서버로 보내지 않는다).
- 목록 행: 코드(모노스페이스)·한글명·영문명·나라. 선택하면 시트를 닫고 검색 카드에 반영.
- 접근성 식별자: `flightAirportFrom`·`flightAirportTo`·`flightSwap`·`flightAirportSearch`.

### B-3. 결과 리스트 (스카이스캐너 목록 행)

행 하나의 배치(한 줄, Dynamic Type에서 두 줄로 접혀도 깨지지 않게):

| 왼쪽 | 가운데 | 오른쪽 |
|---|---|---|
| 출발 시각(큰 글씨, 모노스페이스) / 그 아래 출발 공항 코드 | 소요 시간(`1시간 10분`) / 그 아래 얇은 비행선 그림(직항은 곧은 선, 끝에 작은 원) | 도착 시각(큰 글씨) 위·도착 공항 코드 아래 / 그 옆 **직항 배지** · 항공사 코드·편명 |

- 자정을 넘기면 도착 시각에 `+1`. 도착 시각을 어림했으면 `08:15 어림`처럼 **출처를 숨기지 않는다**(어림 배지는 흐린 색).
- `codeshare`·`master` 행은 국내선 목록에서 **제외**하고, 제외 수가 있으면 리스트 아래에 `직항 12편 · 공동운항 3편 제외`처럼 건수만.
- 행을 누르면 기존 `add(row)` 경로로 카드가 생기고 **시트가 닫힌다**(B-6). 실패하면 기존 `didFail` 문구.

### B-4. 정렬·필터 바

- 정렬: **출발 빠른 순(기본)** / 도착 빠른 순 / 소요 시간 짧은 순.
- **직항만 토글**(국내선 기본 켬, 국제선 기본 끔), 상태는 `@AppStorage`로 기억.

### B-5. 상태

- **로딩**: 결과 자리에 스켈레톤 행 3~5개(회색 막대, 높이는 실제 행과 같게).
- **결과 없음**: 「이 조건에 맞는 편이 없어요. 날짜나 공항을 바꿔 보세요.」
- **404(경로 없음)**: 「조회 서버에 항공편 경로가 아직 없어요.」 + 「다시 시도」
- **503 `keyMissing`**: 「항공편 조회 키가 아직 등록되지 않았어요.」 + 「다시 시도」
- **429 `limited`**: 「오늘 조회 한도에 도달했어요.」 + 「다시 시도」 · **400/422 `outOfRange`**: 지금 문구 유지
- **중계 호스트 없음**: 「중계 서버 주소가 없어 조회할 수 없어요.」
- 어떤 실패에서도 **하단에 「직접 넣기」·「항공사 알림 붙여넣기」가 남는다**(오류 화면 금지 — 지금 원칙 유지).
- 404를 사유로 보여 주려면 `FlightLookup.decode`(72행)에 `case 404:` → 새 `Failure.routeMissing`을 더하고 쓰는 곳(시험 포함)을 함께 고친다.

### B-6. 조회 — 국내선은 dep·arr 양쪽에서 받아 합집합

1. 국내선: `schedule(dep, airport=출발)` + `schedule(arr, airport=도착)`, 같은 날짜. 국제선: 지금처럼 `schedule`+`status` 병렬, 그리고 `FlightLookup.merged`를 그대로.
2. 거르기: dep 결과에서 `destination == 도착`, arr 결과에서 `origin == 출발`.
3. **편명 기준 합집합**: 키는 편명 하나. 양쪽에 있으면 한 행으로 — `출발 = dep.time`, `도착 = dep.arrivalTime → arr.time → 어림(estimatedMinutes)`. arr에만 있는 편은 `departureTime`이 있으면 그것, 없으면 `arr.time - 소요`로 어림하고 표시. 같은 편명 다른 노선은 다른 행.
4. 국내선에서는 `.status`를 부르지 않는다(A-1-3): `merged(schedule:status:nil)`이 스케줄을 그대로 돌려준다.
5. 조건이 바뀌면 이전 조회 결과는 버린다(늦게 온 옛 응답이 새 조건 결과를 덮지 않게 — 요청에 토큰을 붙여 최신 것만 반영).

### B-7. 카드 삽입

- `add(row)`(269행) → `save(draft)` → 성공 시 `onAdded(id)` + **`dismiss()`**(297행)가 이미 있다. 국내선도 **같은 경로**를 쓰고, 시트가 닫혀 여행 모드에 새 카드가 보이는지 시험으로 고정한다.
- 도착 시각이 어림이 아니게 되도록 초안에 알려진 도착 시각·소요 시간을 넘긴다(`FlightPlacement.leg(from:day:direction:durationMinutes:)` 35행, `draft(for:)` 68행의 `isEstimated` 계산).

### B-8. 디자인·접근성

- 기존 토큰만 쓴다: `TaptionType`(8단계 글자), `TaptionCorner`(모서리), `TaptionSpacing`·`TaptionControl`(간격·누름 영역), `TaptionShadowLevel`, `Color.tpReference*`(`Theme.swift`). **새 색·새 글자 단계를 만들지 않는다.** 비행선 그림은 `Shape`로 그리고, 색은 `tpReferenceGray`/`tpReferenceBlue` 안에서.
- 다크 모드·Dynamic Type(최대 크기)에서 시각·코드·배지가 겹치지 않게. 가로 스크롤 날짜 스트립은 큰 글자에서 잘리지 않게 높이를 글자에 맞춘다.
- 접근성 식별자 유지·추가: 기존 `flightDirection`·`flightLoad`·`flightPickerSheet`·`flightAddManual`·`flightPasteAlert`는 그대로, 새로 `flightSearchCard`·`flightDateStrip`·`flightSort`·`flightDirectOnly`·`flightRow-<편명>`.
- 문구는 한국어·영어 + 기존 12개 언어 규칙(`scripts/l10n` `source.json` → `check.py` → 메인 세션 `generate.py`).

### B-9. 범위 밖

예약·가격·좌석·항공사 로고 이미지(저작권)는 다루지 않는다. 알림 파서·지구본·지도·당일 배너는 건드리지 않는다.

- 「그리고 그렇게 문자나 앱의 알람을 자동화로 받아오면, 이게 항공권인 거를 알 수 있잖아. 그러면 그 항공권을 바로 여행 일정에다가 추가하는 걸로 시작하자고. 그것도 넣으라고.」

- 「그리고 카카오톡 알림. 카카오톡 알림도 이렇게 단축어로 복사하면은 그 내용을 받을 수 있잖아.」

### C-2. 항공권 결제인지 어떻게 아는가 (규칙 → AI → 표시)

1. **1차는 규칙(무료·결정적).** 금액·통화·승인일시·가맹점명에서 항공사를 인식한다. 지금 `LedgerCapture.cards`(`LedgerCapture.swift:15`)는 **카드사** 목록이라 항공사가 없고, `FlightAlertParser.airlineName`(`Packages/TaptionRouteEngine/Sources/TaptionRouteEngine/Travel/FlightAlertParser.swift:364`)은 머리표 `[대한항공]`만 읽는다 → `FlightAirportCatalog` 옆에 **항공사·OTA 표 하나**를 더한다(이름 → IATA 두 글자). 최소: 대한항공 KE · 아시아나 OZ · 제주항공 7C · 티웨이 TW · 진에어 LJ · 에어부산 BX · 에어서울 RS · 에어프레미아 YP · 이스타 ZE, OTA: 마이리얼트립 · 야놀자 · 트립닷컴 · 스카이스캐너 · 하나투어 · 모두투어 · 노랑풍선 · Expedia · Booking. **단, 이 OTA 이름만으로 「항공권」이라 정하지 않는다** — 야놀자·트립닷컴·마이리얼트립·Booking·Expedia는 항공권과 숙박을 같이 판다. 문구에 편명·탑승·출발/도착 공항이 있을 때만 항공권이고, 숙박 단서가 있으면 **H절(숙박)** 이다 — **숙박 단서 목록의 정본은 H-3 하나**이고(체크인·체크아웃·투숙·n박·객실·숙소·호텔·펜션·리조트), 여기서 따로 늘리지 않는다. 둘 다 없으면 C-2-3(표시만)으로 둔다.
2. **2차는 AI.** 규칙으로 확실하지 않으면 `AITaskQueue.enqueue(.paymentText, text:, day:, context: ["entryId": 지출 id, "ruleHint": "flight_fare"])`. AI가 돌려주는 길은 **새 명령 case를 만들지 말고** 이미 있는 확장점을 쓴다: `AssistantCommand.Action.operation(AssistantParsedOperation)`(`Packages/TaptionAssistant/Sources/TaptionAssistantProtocol/AssistantCommand.swift:89`) + 동작 등록부 `AssistantOperations.all`(`AssistantOperations.swift:10`). 등록할 동작 하나: 지출 id를 「항공권 결제/아님」으로 판정하고(필요하면 같은 결제 두 건의 병합 여부도 함께), 앱은 그 결과를 **되돌릴 수 있는 로컬 반영**으로만 적용한다.
3. **3차는 표시만.** 신뢰도가 낮으면 지출에 「항공권일 수 있음」 한 줄만 붙이고 카드에는 **자동으로 붙이지 않는다**.
4. AI 연결이 없거나 응답이 없으면 아무것도 지우거나 붙이지 않고 「확인 필요」(`LedgerReviewStore`, `TaptionPlan/Core/LedgerReview.swift:32`)에 둔다. **조용히 지우는 길은 만들지 않는다.**

### C-3. 가격 칸 — `TravelFlightFields`에 4개 추가

1. `fareAmount: Int?`(그 통화의 정수, 반올림) · `fareCurrency: String?`(기본 `KRW`) · `fareSource: String?`(`paymentText`·`receipt`·`manual`) · `fareExpenseID: String?`(`LedgerEntry.id` UUID 문자열, `Packages/TaptionLedgerCore/Sources/TaptionLedgerCore/LedgerCore.swift:34`).
2. `TravelFlightFields`(`AppFeatureSettings.swift:719`)와 **같은 칸을 가진 `TravelTripItem`도 함께** 늘린다 — init(`:604`), `apply(_ flight:)`(`:635`), `clearFlight()`(`:645`). 넷 다 옵셔널이라 **마이그레이션 없이** 기존 저장본이 nil로 열린다.
3. 기존 시험 `TaptionPlanTests/FlightPlacementTests.swift:30`이 `TravelFlightFields(...)`를 **전체 값으로 비교**한다 → 새 칸 기본값 nil로 그대로 통과해야 한다(시험을 고치지 않는다).
4. 카드에는 `₩89,000 · 결제 문자`처럼 **출처를 함께** 보이고, 누르면 그 지출로 이동한다. 원화가 아니면 `₩` 대신 그 통화(`₩` 대신 `USD 65`).
5. 금액의 정본은 언제나 **지출 기록**이다. 카드의 `fareAmount`는 사본이고, 지출이 바뀌거나 지워지면 따라간다(C-4-⑥).

### C-4. 매칭 규칙 (카드 ↔ 지출)

1. **① 편명 일치가 최우선.** 문자에 편명이 있으면 그 편명·날짜의 카드(`FlightCardMapping.cardID` = `tripID|itemID`)에만 붙인다.
2. **② 같은 날짜·같은 금액의 미연결 결제.** 그 결제에 아직 `fareExpenseID`가 없을 때만 후보.
3. **③ 항공사명 일치.** ①·②가 비었을 때만.
4. **④ 왕복 결제 한 건은 카드 두 장에 중복으로 붙이지 않는다.** 한쪽(또는 두 카드를 묶은 자리)에만 붙이고 「왕복 결제」로 표시한다. 사용자가 나눠 달라고 하면 그때만 나눈다.
5. **⑤ `fareExpenseID`가 잠금이다.** 한 지출은 한 카드에만. 반대로 한 카드에 지출 둘이 붙는 것은(왕복·좌석 추가) ④의 묶음 표시로만.
6. **1:1로 정해지지 않으면 자동으로 붙이지 않는다.** 카드 상세에 「연결」 후보 목록을 보이고 사용자가 고른다(`FlightIngest.Confirmation`(`FlightIngest.swift:41`)과 같은 꼴).
7. 지출이 지워지면 `fareExpenseID`·`fareAmount` 연결을 푼다(`LedgerBook` 삭제 경로에서). 카드는 남고 금액만 사라진다.

### C-5. 금액을 믿어도 되는가

1. 문자 원문에 「취소」·「부분취소」·「할부」가 있으면 카드 금액 대신 **그 상태**를 보인다(이미 `Draft.isCancel`(`LedgerCapture.swift:92~101`)·`LedgerEntry.canceledAt`(`Packages/TaptionLedgerCore/Sources/TaptionLedgerCore/LedgerCore.swift:58`)이 있다 — 새로 만들지 않는다).
2. 부분취소는 금액을 고치지 않고 「부분취소 · 카드사 확인」으로 둔다.
3. 카드 상세에 한 줄: 「카드사에 찍힌 금액은 실제 항공권 금액과 다를 수 있어요.」
4. 환불·취소로 지출이 취소되면 카드 금액도 같이 「취소됨」으로.

### C-6. 개인정보

1. 문자·알림 **원문은 기기 안에만**(`PaymentInbox`·`FlightInbox`·`FlightShareStore` 모두 기기 안).
2. 서버로는 **금액·통화·분류·항공사 코드**만. AI로 보낼 때도 `AITaskQueue.mask`로 카드·계좌·전화번호를 가린다.
3. 예약번호·이름은 여전히 밖으로 나가지 않는다 — `pnrLocal`(`AppFeatureSettings.swift:601`)·`FlightCardMapping.Log`(`TaptionPlan/Core/FlightCardMapping.swift:9`) 규칙 그대로, `FlightPickerSheet.swift:170`의 약속과 같다.

### C-7. 시험 6건 (앱)

1. 대한항공 결제 문자 → 항공권으로 판정 → 그 날짜 카드에 금액이 붙는다.
2. 애매한 문자(항공사만 있음) → AI 판정을 맡기고 **카드에 붙이지 않고** 확인 대기.
3. 왕복 한 결제 → **한 카드에만**, 「왕복 결제」 표시.
4. 「취소」·「부분취소」·「할부」 문구 → 금액 대신 상태.
5. 다른 여행의 결제(호텔·렌터카)가 엉뚱한 항공권 카드에 붙지 않는다.
6. 지출을 지우면 카드의 가격 연결이 풀린다(카드는 남는다).

자리: `TaptionPlanTests/FlightFareTests.swift`(새 파일) + 기존 `TaptionPlanTests/LedgerTests.swift`·`FlightIngestTests.swift`는 깨지지 않아야 한다.

### C-8. 범위 밖 (지시서 전체에 적용)

1. **검색 결과 목록에 실시간 가격을 띄우지 않는다.** 가격 API가 없고, 무료 API는 국내선을 덮지 않는다. `/flights` 응답에 가격 필드를 더하지도 않는다.
2. 가격은 **실제로 결제한 항공편 카드**에만 붙는다. 안 산 항공편·검색 결과에는 붙지 않는다.
3. 항공권 가격 비교·최저가 알림은 이번 범위가 아니다.

### C-9. 결제 문자·알림만으로 여행 일정에 카드 자동 추가 (순서 고정)

**이 순서를 바꾸지 않는다.** 각 단계는 앞 단계 결과 위에서만 돈다.

#### C-9-1. 유입 — 문자와 앱 알림이 **둘 다** 들어온다

1. 새 수집 경로를 만들지 않는다. 위 C-1 표의 통로에 그대로 합류시킨다. 앱이 아직 안 떠 있으면 `FlightInbox.stash`(`FlightIngest.swift:253`)·`FlightShareStore.enqueue`가 받아 두고 앱이 열릴 때 처리한다(`FlightIntentRunner.run`(`FlightIntents.swift:27`)·`SharedTextIntentRunner.run`(`:60`)·`FlightInbox.drain`(`:261`)).
2. **지금 구멍**: 「BOKKI 결제」 자동화는 트리거 낱말(원·승인·출금·취소·입금·결제·일시불·할부, `BokkiShortcutsGuide.swift:87`)에 걸린 글만 넘긴다. 항공사 **예약 확정 알림톡**은 「원」이 없으면 결제 자동화로 오지 않고, 와도 `isPaymentCandidate`가 아니면 `delegateToAI`(`LedgerIntents.swift:149~152`)로 흘러 항공편 카드가 되지 않는다 → `process`에서 결제 후보가 아닌 글을 버리기 전에 `FlightIngest.looksLikeFlightAlert`(`:97`)를 먼저 본다.
3. 예약 알림톡도 자동으로 잡히게 **「항공 알림 넣기」 쪽 트리거 낱말**(예약·예약번호·탑승·편명·출발)을 단축어에 더한다. **낱말 목록은 한 벌만 두고 같이 고친다** — 여기(항공) + D-3-5(기차·승선·버스·터미널·항구) + H-1(숙소·체크인·체크아웃·투숙·n박·객실)이 **같은 목록**이고, 결제 자동화의 트리거 낱말(`BokkiShortcutsGuide.swift:87`의 원·승인·출금·취소·입금·결제·일시불·할부)과는 **다른 목록**이다(그 둘을 한 목록으로 합치지 않는다). 링크판 단축어는 `scripts/shortcuts/build.py`로 다시 만들고 ID는 `AppSecrets.local.xcconfig`(커밋 금지)에 둔다. 낱말 목록과 만든 단축어가 어긋나지 않게 `triggerWords` 주석을 함께 고친다.
4. **실기기 확인 항목**: 카카오톡 알림톡이 「알림 › 앱 푸시」로 잡히는지. `FlightIntents.swift:4~6` 주석이 이미 그렇게 적어 두었다 — 「카카오톡 알림톡이 「알림 › 앱 푸시」로 잡히는지는 기기에서 확인하는 항목이고, 안 되면 복사 → 붙여넣기 배너나 공유로 넣는다.」 결과를 회신에 적는다.

#### C-9-2. 중복 판정·병합 (핵심)

1. 지금 있는 것: 같은 **글**은 2분 안에 한 번만(`PaymentTextCapture.repeated`(`LedgerIntents.swift:60`), `repeatWindow` 120초) / 같은 **금액·통화·10분**이면 같은 결제(`LedgerReview.isSamePayment`(`LedgerReview.swift:104`), `duplicateWindow = 600`) → `duplicateVerdict`(`:114`)가 `.same`이면 **버리고** 「이미 가계부에 넣은 결제예요」로 끝낸다. `LedgerCapture.isDuplicate`(`LedgerCapture.swift:81`)는 정의만 있고 쓰는 곳이 없다(시험만 있다, `LedgerTests.swift:1183`).
2. **버리는 것이 문제다.** 문자와 알림은 문구가 달라 2분 중복에 안 걸리고, `.same`으로 버려진 쪽에만 있던 편명·구간이 사라진다. C-9는 **합친다**: 같은 금액 + 같은 통화 + 승인 시각 수 분 이내(±10분) + 같은 항공사/가맹점이면 **한 건**. 필드는 **합집합**(정보가 많은 쪽을 남기고 빈 칸만 채운다 — `FlightAlertMerge.fill`(`Packages/TaptionRouteEngine/Sources/TaptionRouteEngine/Travel/FlightAlertMerge.swift:221`)과 같은 방식). 표시는 「문자+알림 합침」.
3. 판단은 AI가 한다(대표: 「그걸 AI가 판단해서 중복된 건 하나 지울 거야」). 규칙으로 4개 키가 다 맞으면 규칙이 합치고, **하나라도 어긋나면**(이름 다름·시각 3~10분·금액 다름) C-2의 `paymentText` 판정으로 보낸다. AI가 「같다」고 하면 하나로, 「다르다」면 둘 다 둔다.
4. AI가 없으면 **둘 다 두고** 「중복일 수 있음」을 「확인 필요」에 띄운다. 자동 삭제 금지.
5. 결과는 **지출 1건 · 카드 1장**.

#### C-9-3. 결제 날짜·구간 추출

1. 병합된 건에서 **탑승일**·출발지·도착지·편명(있으면)을 뽑는다. **예약일과 탑승일은 다르다** — 승인일이 아니라 문자에 적힌 탑승일을 기준으로 해석한다. 연도가 없으면 `FlightAlertDate.resolved`(`FlightAlertParser.swift:24~32`, 받은 날 기준 60일 규칙)를 그대로 쓴다.
2. 탑승일이 없으면 지출일로 대신하지 않는다. AI 판정을 거치고, 그래도 없으면 사용자에게 묻는다(카드 만들지 않음).

#### C-9-4. 노선으로 항공편 조회

1. `GET /flights/schedule?airport=<출발>&date=<탑승일>&direction=dep`(필요 시 `arr`). 서버는 `flight`·`airline` 인자로 좁혀 주고 시각 순으로 돌려준다(`server/trip-relay/src/flights.js:225~244`). 앱 쪽 인자는 `FlightLookup.query`(`TaptionPlan/Core/FlightLookup.swift:64`)에 이미 있다.
2. **지금 구멍**: `FlightIngest.createFromLookup`(`FlightIngest.swift:216`)이 **공항을 `"ICN"`으로 고정**하고 dep·arr만 돈다. 국내선·김포·제주가 안 된다 → 출발 공항을 문자에서 읽어 넘기게 고친다(공항을 모르면 조회하지 않는다).
3. 편명을 알면 `flight=`로 좁힌다. 모르면 그 구간·그날 목록에서 **금액대·시간대·항공사**로 후보를 좁히고 AI가 고른다. 후보 1건이면 확정, 여러 건이면 「이 편인가요?」(`FlightIngest.Confirmation`), 0건이면 C-9-7.

#### C-9-5. 여행 일정에 **미리** 넣기

1. 확정된 편으로 **자동으로 비행 카드를 만든다**. 경로는 새로 만들지 않고 `FlightIngest`의 기존 길: `FlightIngest.plan` → `createTripFlight`(`FlightIngest.swift:182`) → `addTripItem`(kind `.flight`). 편명·출발/도착 공항·출발/도착 시각은 서버 값에서(`FlightPlacement.draft`(`TaptionPlan/Core/FlightPlacement.swift:68`)), 금액은 C-3의 네 칸으로.
2. **여행 묶기**: 그 날짜를 덮는 여행이 있으면 그 여행(`FlightIngest.trip(on:)`(`FlightIngest.swift:85`), 앞뒤 하루 봐 줌). 지출에 이미 `tripID`가 있으면(`LedgerEntry.tripID`, `Packages/TaptionLedgerCore/Sources/TaptionLedgerCore/LedgerCore.swift:47`) 그 여행을 먼저 본다.
3. **여행이 없으면 I절(`AUTO1120A01`, 대표 지시 2026-11-20 18:49)을 따른다.** I절이 이 항목을 **대체**한다 — 예약이 확정된 카드면 자동 이름(「도착지 + 〇박 〇일」)으로 여행을 만들고, 확신도가 낮은 카드만 `FlightInbox`「미지정」 보류로 남긴다(최대 20건·30일, 기기 안).
4. 카드 표시: 「자동 추가됨 · 문자+알림」 + 금액(출처 포함).

#### C-9-6. 되돌리기

1. 자동으로 넣은 카드는 표시와 **한 번에 취소** 단추를 준다(카드 지우기 = `clearFlight()`(`AppFeatureSettings.swift:645`) + 일정 칸 삭제 경로, 금액 연결은 C-4-⑦).
2. 같은 결제로 다시 처리돼도 카드는 **한 장**이다(지출 id 잠금 + `fareExpenseID`).
3. 되돌린 결제를 다시 자동 추가하지 않는다(사용자가 취소한 것을 앱이 되살리지 않는다) — 취소한 지출 id를 기기 안에 기록해 둔다.

#### C-9-7. 실패할 때

1. 서버가 404·503(`keyMissing`)·429(`limited`)면 **카드를 만들지 않는다**(`FlightLookup.Failure`, `FlightLookup.swift:50`). 보관함에 두고 「항공편 확인이 안 돼 나중에 넣을게요.」로 답한다. 키가 없는데 어림으로 카드를 만들면 안 된다.
2. 시간표에 그 편이 없으면(0건) 카드를 만들지 않고 지출만 남긴다. 「직접 넣기」·「알림 붙여넣기」는 늘 남긴다(B-5 원칙 그대로).
3. 실패를 쌓아 두었다가 키가 등록되면 다시 시도한다(보관함 drain).

#### C-9-8. 확신도 3단계 (한 표로 못 박는다)

| 확신도 | 조건 | 하는 일 |
|---|---|---|
| ① 자동 | 편명 + 탑승일이 둘 다 뽑힘 | 카드 생성 + 금액, 「자동 추가됨」, 되돌리기 |
| ② 초안 | 편명 없음, 항공사·노선은 있음 | 카드 초안 + 「추가할까요?」 확인(확인 전에는 일정에 넣지 않는다) |
| ③ 표시만 | 노선도 모호 | 가계부에만 두고 아무것도 만들지 않음(필요하면 「항공권일 수 있음」 표시) |

「판단이 안 되면 AI가」는 **판정 단계**(C-2)에 적용한다. 일정에 카드를 만드는 것은 언제나 되돌릴 수 있게 한다.

#### C-9-9. 개인정보

1. 서버로 가는 것: 편명·노선·시각·금액. **예약번호·이름·전화번호는 기기 밖으로 나가지 않는다**(`FlightPickerSheet.swift:170`과 같은 약속).
2. AI로 보내는 판정 요청도 `AITaskQueue.mask`를 거친다. 판정 결과 문구·로그에 원문을 남기지 않는다.

#### C-9-10. 시험 8건 (C-9)

1. 편명이 든 결제 문자 → 비행 카드 자동 생성 + 금액 표시.
2. 같은 문자를 다시 처리해도 카드가 두 장 생기지 않는다.
3. 편명 없는 문자(항공사·노선만) → 초안 + 확인 대기, 일정에는 아직 안 들어감.
4. 모호한 문자(노선도 모름) → 카드 미생성, 지출만.
5. 같은 결제가 문자+알림 2건으로 들어오면 **지출 1건·카드 1장**으로 병합.
6. 한쪽에만 편명이 있을 때 병합 결과에 편명이 살아 있다(버려지지 않는다).
7. 탑승일 기준으로 그 구간 편을 조회해 카드가 생긴다(승인일 기준이 아니다).
8. 503(키 없음)일 때 카드를 만들지 않고 보관함에 남는다.

### C-10. 카카오톡 알림톡 경로

근거는 이미 코드에 적혀 있다 — `FlightIntents.swift:4~6`: 「단축어 자동화 「메시지를 받을 때」(SMS)나 「알림 › 앱 푸시」에 걸어 쓴다. **카카오톡 알림톡이 「알림 › 앱 푸시」로 잡히는지는 기기에서 확인하는 항목이고, 안 되면 복사 → 붙여넣기 배너나 공유로 넣는다.**」

1. **경로 ①(기본·확실): 복사 → 공유/단축어.** 카카오톡에서 알림톡 본문을 복사해 ⑴ 공유 시트(`FlightShareStore.enqueue` → `FlightShareIntake`(`TaptionPlan/Core/FlightShareIntake.swift:10`)), ⑵ 「글을 일정으로 넣기」 단축어(`AddSharedTextIntent`, `FlightIntents.swift:43`), ⑶ 항공편 화면 「항공사 알림 붙여넣기」(`FlightPickerSheet.swift:153~163`) 가운데 아무 길로나. 셋 다 `ingestFlightAlert`로 모인다.
2. **경로 ②(자동 유입): 「알림 › 앱 푸시」 자동화에 카카오톡을 넣어 본다.** 되는지/안 되는지는 **실기기 확인 항목**으로 남기고(위 C-9-1-④), 안 되면 앱이 그 사실을 알고 **경로 ① 안내 문구**를 띄운다(「카카오톡은 복사해서 붙여넣거나 공유로 넣어 주세요」). 자동이 안 된다고 카드를 못 만드는 것은 아니다.
3. **알림톡 본문 파싱.** 정보성 알림톡은 `[대한항공]`·`[카카오페이]` 같은 머리표 + 본문에 예약번호·편명·금액·탑승일이 섞인다. 지금 파서는 머리표를 떼어 `marker`에 담기만 하고(`FlightAlertText.splitMarker`, `Packages/TaptionRouteEngine/Sources/TaptionRouteEngine/Travel/FlightAlertText.swift:52`) 광고인지 보지 않는다(`FlightAlertParser.parse`, `:171`).
4. **`(광고)` 마케팅 알림톡은 항공권 결제·예약으로 오인하지 않는다.** `markers`(`FlightAlertText.swift:19`)에 「광고」가 이미 있으니 `marker`에 「광고」가 있으면 `.unreadable`(또는 `.marketing`)로 끝낸다. 지출 쪽은 이미 `neverPayments`(`LedgerCapture.swift:42`, `"(광고)"`·`"[광고]"`)로 광고를 늘 뺀다 — **같은 잣대**를 항공 쪽에도 둔다.
5. **카드사·페이 결제 알림톡과 항공사 예약 알림톡을 구분한다.** 결제 알림톡(카드사·카카오페이·토스)은 금액·승인 중심(C-2 판정 재료), 예약 알림톡(항공사)은 편명·탑승일·구간 중심. **예약 알림톡만 있어도** 그 셋이 있으면 카드를 만들 수 있다(금액은 없어도 된다 — 나중에 결제 문자가 오면 붙는다).
6. **3중 유입 병합.** 같은 예약이 ⑴ 항공사 예약 알림톡 ⑵ 카드사 결제 문자 ⑶ 앱 푸시로 셋까지 올 수 있다. **결제성(금액·시각)은 1건으로 합치고, 예약성(편명·구간)은 그 결제 건에 정보를 보강하는 쪽으로 붙여 카드는 1장만** 만든다(C-9-2 확장: 키는 금액·통화·시각 + 편명·구간).
7. **개인정보.** 카카오톡 본문도 기기 안에서만. 서버로는 편명·노선·시각·금액만. 예약번호·이름·전화번호는 밖으로 나가지 않는다.
8. **시험 3건**: ⑴ `(광고)` 알림톡 → 무시(카드·지출 어느 쪽도 만들지 않는다) ⑵ 항공사 예약 알림톡 단독 → 편명·탑승일로 카드 생성 ⑶ 예약 알림톡 + 카드 결제 문자 → 카드 1장·금액 표시.

대표님이 2026-11-20 18:26 통화에서 「같은 방법으로 고속버스랑 배도 가능 하잖아」·「고속버스랑 시외버스도 되냐?」라고 범위를 넓히고, 이어 「이동 수단에 따라 자동으로 … 싹 정리해서 브릿지에 올려」(18:31)로 통합 정리를 지시했다. 앞 판의 D-7은 이것을 「조사만」으로 두었는데, **대표님이 진행을 승인했으므로 버스는 구현한다**(여객선만 D-9 스텁).

#### D-7-1. 확인한 사실 (공공데이터포털 원문, 2026-11-20)

- **국토교통부_(TAGO)_고속버스정보** — data.go.kr `15098522`, 무료·**이용허락범위 제한 없음**, JSON+XML, REST, 호출 주소 계열 `https://apis.data.go.kr/1613000/ExpBusInfo`.

- **국토교통부_(TAGO)_시외버스정보** — data.go.kr `15098541`, 같은 계열 `https://apis.data.go.kr/1613000/SuburbsBusInfo`. 파라미터 `terminalNm`·`cityCode`(터미널 목록), `depTerminalId`(예 `NAI0671801`)·`arrTerminalId`(예 `NAI3214401`)·`depPlandTime`(출/도착지기반), 시외버스등급·도시코드 목록.
  - **공식 설명에 「※ 현재 당일 배차정보만 제공하고 있습니다.(추후에 배차정보 기간을 연장할 예정)」이 명시되어 있다** — 다음 날 이후 일정에는 쓸 수 없다. 이 한계를 코드·문구·시험 셋 다에 박아 둔다(D-7-4). **터미널 목록에도 부천·김포·광명·안산·동서울이 없다**(2026-11-20 실측) — D-7-3-7.

#### D-7-2. 라우트 계약 — `/trains/schedule`과 **같은 모양**

`GET /buses/schedule?from=서울경부&to=부산&date=2026-11-21[&type=express|intercity]`

- `type` 생략 시 `express`. **두 종류를 섞지 않는다**(터미널 ID 체계·등급·요금이 다르고 시외는 당일만이다).
- `from`·`to`는 **역명이 아니라 터미널명 또는 터미널 ID**다(D-7-3).
- 응답(최상위 키·행 키 이름을 열차와 맞춘다):

```json
{
  "source": "tago", "updatedAt": "2026-11-20T19:02:11+09:00", "available": true,
  "type": "express", "viewDate": "2026-11-21", "resolved": true,
  "terminals": { "from": { "id": "NAEK010", "name": "서울경부" }, "to": { "id": "NAEK300", "name": "부산" } },
  "buses": [
    { "type": "express", "serviceNumber": "07:00 서울경부→부산", "serviceName": "우등",
      "origin": "서울경부", "destination": "부산", "originId": "NAEK010", "destinationId": "NAEK300",
      "departureTime": "07:00", "arrivalTime": "11:10", "durationMinutes": 250, "dayOffset": 0,
      "fare": 23800, "fareCurrency": "KRW", "grade": "우등", "routeId": "NAEK010-NAEK300-01" }
  ]
}
```

- `serviceNumber`: 버스에는 열차번호가 없으므로 **출발시각 + 터미널 쌍**으로 만든다(중복 잠금 키 D-6-3과 같은 값). `serviceName`·`grade` = 등급(일반·우등·프리미엄·심야·시외등급).
- `fare`는 **조회 시점 공식 운임**이다(실시간 최저가 아님). C-8의 「검색 결과에 가격 금지」는 **항공에만** 적용한다 — 버스는 API가 주는 공식 운임을 「공식 운임」 라벨로 보이고, 카드 금액의 정본은 여전히 지출 기록(C-3-5)이다.
- `durationMinutes`는 도착−출발(자정 넘김 `+1440`), `dayOffset`은 `arrivalTime < departureTime`이면 1.
- 앱 상한 **600KB**(`FlightLookup.maximumBytes`와 같은 값), 응답 헤더 `cache-control: private, max-age=60`.

#### D-7-3. 터미널 ID 해석 — 여행 장소명(「부천」·「부산」)에서 터미널 찾기

1. `from`/`to`가 이미 터미널 ID 꼴(`NAEK010`·`NAI0671801`)이면 그대로 쓴다.
2. 이름이면 **터미널 목록을 먼저 받아 캐시**한다: `caches.default`, 키 `https://buses-cache.invalid/terminals?type=&q=`, TTL **86_400초**(터미널 목록은 하루 한 번이면 충분하다 — `src/flights.js:194~203`의 `cached`/`keep`을 그대로 쓴다).
3. 대표님의 여행 일정 장소명은 「부천」·「부산」 같은 **도시 이름**이므로 다음 차례로 좁힌다:
   ① 정확 일치 ② 정규화(공백·「터미널」·「역」·「버스」 제거) ③ **별칭 표**(서울경부=센트럴시티, 부산=부산사상, 광주=광주유스퀘어, 동대구=대구, 인천=인천터미널, 부천=부천터미널 …) ④ 부분 포함(「센트럴」→「서울경부(센트럴시티)」) ⑤ `cityCode` 목록으로 같은 도시의 터미널을 모은다.
4. **후보가 2개 이상이면 고르지 않고 돌려준다**: 200 + `resolved:false` + `candidates:[{id,name,type,cityCode,cityName}]`(최대 8개) + `buses:[]`. 앱은 「어느 터미널인가요?」 목록을 띄우고 고른 ID로 다시 부른다. **새 실패 코드를 만들지 않는다**(`FlightLookup.Failure` 5종 그대로 — 후보는 실패가 아니라 선택이다).
5. 0개면 200 + `resolved:false` + `candidates:[]`. 앱 문구 「그 이름의 터미널을 찾지 못했어요. 가까운 터미널 이름으로 다시 찾아 주세요.」 + 「터미널 이름으로 찾기」.
6. 별칭 표는 **서버**(`src/buses.js`)와 **앱**(`BusTerminalCatalog`) 양쪽에 둔다. 공개 상호·지명만 넣고 사람 이름·주소·전화번호는 넣지 않는다. 표 맨 위 주석에 「대표님이 직접 추가·수정한다」를 적는다.
7. **실측 제약 — 시외버스 터미널 목록에 부천·김포·광명·안산·동서울이 없다**(2026-11-20 TAGO 시외버스 터미널 목록 조회). 그래서 ③의 `부천=부천터미널` 같은 별칭은 **고속버스·앱 검색용으로만** 의미가 있고, **시외(`type=intercity`)로 부천 출발을 물으면 상류에 터미널이 없어 0건**이 된다. 이때는 실패가 아니라 **정상 상태**로 다룬다: 200 + `resolved:false` + `candidates:[]` + 앱 문구 「그 터미널은 시외버스 조회에서 찾지 못했어요. 예약 알림의 시각으로 카드를 만듭니다.」(D-7-4·D-9와 같은 방식). **부천·김포·광명·안산·동서울 출발 시외는 다른 소스가 필요하다**는 사실을 `src/buses.js` 주석과 회신에 남긴다(이번에 새 소스를 붙이지 않는다).

#### D-7-4. 시외버스 「당일만」 — 실패가 아니라 정상 상태

1. `type=intercity`이고 `date`가 **KST 오늘**이 아니면 **상류를 부르지 않고** 200 + `{ available:false, resolved:true, note:"intercity_today_only", viewDate:<요청일>, type:"intercity", buses:[] }`를 준다.
2. 앱 결과 자리 문구: 「시외버스는 오늘 배차만 조회할 수 있어요. 내일 이후는 예약 알림의 시각을 씁니다.」 + 「오늘로 보기」 단추. 날짜 스트립에서 시외 모드일 때 **오늘 외의 칸은 흐리게**.
3. 오늘 판단은 **`Asia/Seoul` 고정**으로 한다(기기 시간대·서머타임과 무관).
4. 고속버스는 `depPlandTime`을 그대로 넘긴다(당일 제한 없음). 상류가 미래 날짜에 빈 목록을 주면 `available:true`·`buses:[]`로 두고 앱은 「그 날짜 배차가 아직 없어요」.

#### D-7-5. 캐시·한도·오류·키

1. 캐시 `https://buses-cache.invalid/schedule?type=&from=<id>&to=<id>&date=`, TTL **1800초**(고속)·**600초**(시외 — 당일 배차·잔여가 바뀐다).
2. 상류 하루 예산 `BUS_DAILY_CALLS`(기본 **300**): `ipState(...).call("countDaily", { name:"bus", limit: LIMITS.busPerIpDay, now, expire:true })` — `src/index.js:309~312`와 같은 자리. 넘으면 `429 bus_daily_limit` + `Retry-After`.
3. **인증 전 IP 제한 목록에 `/buses/`를 더한다**: `src/index.js`의 `limited(url.pathname.startsWith("/kakao/") || … || url.pathname.startsWith("/flights/") ? env.KAKAO_LIMIT : env.REQUEST_LIMIT, request)` 자리에 `/buses/`(와 E절의 `/ingest/`)를 넣는다. 인증 뒤에는 `authorized()`의 DO `admit`이 한 번 더 센다.
4. 오류: `400 bad_query`(date 형식·type 값·ID 형식) · `429 bus_daily_limit` · `502 upstream_failed`(상류 원문·키를 돌려주지 않는다 — `relayBus`(`index.js:240~249`)와 같은 방식) · `503 {"error":"bus_key_missing"}`(`!env.TAGO_SERVICE_KEY`). **404는 내지 않는다**(라우트는 배포와 함께 생긴다).
5. 키: **`TAGO_SERVICE_KEY`를 그대로 재사용**한다(버스정류소 중계 `index.js:218~226·252·275`). **새 시크릿 이름을 만들지 않는다.** 값은 코드·문서·커밋·로그·시험 픽스처 어디에도 쓰지 않는다.
6. 코드는 **새 파일 `src/buses.js`** 에 두고 `src/index.js`에 라우트·한도 분기를 더한다(항공 `flightsRoute`(`index.js:331`)·열차 라우트와 같은 자리).

1. `TaptionPlan/Core/BusLookup.swift`(새): `TrainLookup`과 같은 모양(요청 인자·`Failure` 5종·600KB·404 없음) + `resolved`·`candidates` 해석. `FlightLookup`을 복제하지 않는다.

#### D-7-7. 시험 — `test/buses.test.mjs` **최소 8건**(픽스처 익명, 아래 10건을 넣는다)

1. **서울경부→부산 고속**: `depTerminalId`·`arrTerminalId`·`depPlandTime`이 상류 쿼리로 나가고, 출발·도착 시각·등급·요금이 응답 행에 매핑된다.
2. **부천→인천 시외(당일)**: `SuburbsBusInfo` 쪽으로 나가고 행이 `type:"intercity"`로 표시된다. **픽스처로만 시험한다** — 실제 상류 터미널 목록에는 부천·인천 시외 터미널이 없어(2026-11-20 실측) 기기에서는 `resolved:false`가 정상이다(D-7-3-7).
3. **다음 날 시외**: 상류 호출 **0회**로 `available:false`·`note:"intercity_today_only"`(호출 카운터로 확인).
4. **터미널 해석 실패·모호**: 「부산」이 여러 후보면 `resolved:false`+`candidates`(≤8), 「없는이름」이면 후보 0개 — 둘 다 **200**.
5. **요금·등급 매핑**: `fare` 정수·`fareCurrency:"KRW"`, 등급이 `serviceName`·`grade`에 함께, 숫자가 아닌 요금은 `null`(문자열을 그대로 넣지 않는다).
6. **응답 없음·한도**: 상류 500 → 502 `upstream_failed`, 타임아웃 → 502, 한도 초과 → 429 `bus_daily_limit`(상류 미호출), 키 없음 → 503 `bus_key_missing`.
7. **응답 모양 일치**: `/trains/schedule`과 최상위(`source`·`updatedAt`·`available`)·행(`departureTime`·`arrivalTime`·`durationMinutes`) 이름이 같다(공용 모양 시험을 한 파일에서 돌린다).
8. **`TAGO_SERVICE_KEY` 재사용**: `env`에 `TAGO_SERVICE_KEY`만 넣고 `BUS_*_KEY` 같은 값이 없어도 200이 나고, `TAGO_SERVICE_KEY`를 빼면 503 — 새 시크릿 이름을 만들지 않았다는 증거.
9. **터미널 목록 캐시**: 두 번째 조회에서 상류 터미널 호출이 늘지 않는다(TTL 24시간).
10. **`_type=json`·XML 폴백**: 상류가 `_type`을 무시하고 XML을 주면 502가 아니라 XML 파서로 읽어 같은 모양으로 돌려준다.

### D-8. 시험 (`TRN1120A01`)

**기차 5건**
1. KTX 예약 문자 → 기차 카드 생성(열차번호·출발역→도착역·출발/도착 시각).

```json
  "senderType": "channel|bank|card|airline|rail|bus|ferry|unknown", "label": null }
```

- `text`는 **원문**이고, 서버는 이것을 저장하지 않는다(E-2-5). `label`은 사용자가 그 자리에서 고른 경우에만(`ledger`|`travel`).
- 링크판 단축어는 `scripts/shortcuts/build.py`로 다시 만들고 ID는 `AppSecrets.local.xcconfig`(커밋 금지)에 둔다.

#### E-2-5. 보안 요구 — 「사생활 문제」에 대한 구현 조건 (대표 지시 18:33)

1. **경계에서 즉시 폐기**: 화이트리스트에 안 걸리는 텍스트는 **요청 처리 함수 안에서 판정 후 메모리에서만 쓰고 버린다.** D1·R2·KV·Workers 로그·PostHog·에러 리포트 어디에도 원문을 남기지 않는다. 남길 수 있는 것은 `{수집시각(분 단위), 판정결과, 글자수, 매칭된 단서 개수}` 메타데이터 뿐이고, 이 값으로 원문 복원이 불가능해야 한다(순서·길이를 정밀하게 남기지 않는다 — 글자수는 10단위 버림).
2. **친구 대화는 애초에 안 들어온다**: 단축어가 카톡 대화를 직접 읽지 못하므로 서버가 받는 것은 **대표님이 직접 복사·공유한 텍스트뿐**이다(전체 대화 열람 경로 자체가 없다 — 이 구조적 한계가 1차 방어다). 다만 「복사해서 넘긴 친구 대화」는 1번 규칙으로 즉시 폐기한다.
3. **로그·분석 분리**: `PHG1120A01`과 충돌 없게 **전송 화이트리스트 방식**(허용 필드만 보냄)으로 설계하고, 새 필드의 기본값을 **전송 안 함**으로 둔다. 알림 원문·예약번호·금액·좌석·전화번호·이름은 PostHog·`DiagnosticsLog` 전송 대상에서 **코드 수준으로 제외**(`DiagnosticsLogPolicy`의 redact 목록에 알림 관련 키를 넣는다).
4. **보관·삭제**: 통과한 예약 정보만 저장하되, **예약번호는 해시 또는 마스킹(끝 4자리)** 후 저장하고 **원문은 저장하지 않는다**. 저장된 카드에도 「원문 보기」를 두지 않는다. 대표님이 삭제를 요청하면 **파생 카드·KV 항목까지** 함께 지우는 경로(`DELETE /ingest/items` + 앱 카드 삭제)를 만든다.
5. **접근 통제**: 수집 엔드포인트는 기존 Bearer 인증 그대로. **토큰 없으면 401로 본문을 읽기 전에** 거절한다 — `authorized()`(`src/index.js:559~566`)가 `bearer(request)` → `resolveKey(env.PLANS, token, now)`을 먼저 하고 본문은 핸들러에서만 읽는 지금 구조를 지킨다(새 라우트도 `ROUTES`에 넣어 이 경로를 타게 한다). 레이트리밋(분당 상한 `ALERT_PER_MINUTE`, 기본 30)과 **요청 크기 상한**(4KB)을 두어 대량 주입을 막는다.
6. **사용자 통제**: 앱 설정에 ⑴ 알림 수집 켜기/끄기 ⑵ 채널 화이트리스트 관리 ⑶ 수집된 항목 전체 삭제. **끄면 엔드포인트가 204로 조용히 무시**한다(오류도 로그도 남기지 않는다).
7. **점검 항목(시험 3건)**: ⑴ 친구 대화 텍스트를 보냈을 때 아무 것도 저장되지 않고 로그에도 남지 않는지 ⑵ 토큰 없이 보냈을 때 401이며 본문이 처리되지 않는지(본문 읽기 훅이 불리면 실패) ⑶ 삭제 요청 후 KV·D1에 잔여물이 없는지(전수 조회).

#### E-2-6. 위협 모델과 방어 — 「뚫려도 훔칠 게 없게」

| # | 공격 | 대응(위치) |
|---|---|---|
| 1 | 단축어→서버 구간 가로채기 | TLS만 사용(평문 HTTP 거절), 인증은 기존 Bearer, 토큰 없으면 **본문 파싱 전 401**(`src/index.js:559~566`) |

| 5 | 클라우드플레어 계정 탈취(가장 큰 위험) | **대표님이 직접 하는 조치**(아래 체크리스트): 계정 2단계 인증 확인 · API 토큰은 Workers Scripts/KV Edit + Account Read 최소 권한·1년 만료 · 안 쓰는 토큰 폐기 · 배포 권한과 데이터 읽기 권한 분리 검토 |
| 6 | 기기 탈취 | 아이폰 잠금으로 단축어·자동화 접근에 잠금 해제 필요, 앱에서 수집 끄기·삭제 즉시 반영 |
| 7 | **남는 위험(정직하게)** | 서버가 판정을 위해 원문을 **메모리에 잠깐** 들고 있는 순간과, 단축어가 넘기는 텍스트 자체는 막을 수 없다 — 구조적 한계다. 방어선은 **원문을 디스크에 쓰지 않는 것**. 「완벽 차단」이라는 표현은 쓰지 않는다 |

### E-3. 중복 병합 — 「버리지 말고 합친다」(C-9-2 재확인)

1. **지금 구조는 버린다.** `LedgerIntents.swift:182~184`: `duplicateVerdict(entry, in:)`가 `.same`이면 `return ("이미 가계부에 넣은 결제예요.", .duplicate)`로 **끝낸다**(저장하지 않는다).
2. **더 나쁜 구멍**: `LedgerReview.swift:114~115`의 `duplicateVerdict`가 `entries.filter { $0.source == .message && isSamePayment(...) }`라서 **앱 알림 출처는 중복 후보에 아예 안 들어간다**(`isSamePayment` 자체는 `:104~107`에서 금액·통화·종류·10분만 본다 — 출처를 보는 곳은 `duplicateVerdict` 쪽이다). 문자와 알림이 같은 결제를 두 번 넘기면 알림이 **별개 지출**로 하나 더 생긴다. `LedgerCapture.isDuplicate`(`:81~86`)는 문자 쪽에만 정의가 있고 쓰는 곳이 없다(시험만: `LedgerTests.swift:1183`).
3. **지시**: 판정 결과를 「버리기/살리기」가 아니라 **「합치기/보류/그대로」**로 바꾼다.
   - 같은 금액 + 같은 통화 + 승인 시각 ±10분 + 같은 가맹점·항공사/철도/터미널이면 **한 건**. 필드는 **합집합**(정보가 많은 쪽을 남기고 빈 칸만 채운다 — `FlightAlertMerge.fill`(`FlightAlertMerge.swift:221`)과 같은 방식). 표시는 「문자+알림 합침」.
   - 하나라도 어긋나면 AI 판정(`paymentText`, C-2-2)으로 보낸다: 「같다」→ 하나, 「다르다」→ 둘 다.
   - AI가 없으면 **둘 다 두고** 「중복일 수 있음」을 「확인 필요」(`LedgerReviewStore`, `LedgerReview.swift:32`)에 띄운다. **조용한 삭제 금지**.
4. **저장 위치**: 병합 결과는 지출 1건·카드 1장. 합친 근거(어느 출처끼리 합쳤는지)는 `fareSource`·카드 표시 문자열로만 남기고 원문은 남기지 않는다.
5. **실패 시**: AI 응답이 없거나 시간초과면 `.suspect`처럼 보류 — 어느 쪽도 지우지 않는다.

### E-4. 이동수단 판정 — 단서 표와 확신도 3단계

| 이동수단 | 관문 단서(원문) | 판정 규칙 |

| 항공 | 편명(`KE1201`·`7C###`) · 공항 코드/이름 · 탑승구·터미널 | 공항/항공사 단서가 있고 역명·터미널명이 없으면 항공(D-3-2) |
| 기차 | 열차번호(`KTX 101`·`SRT 301`·`ITX-새마을 1001`·`무궁화 1201`) · `~역` · 특실/일반실 | 열차번호 접두 또는 역명이 있으면 기차 |

| 여객선 | 선명 · 「승선」·「출항」·「항차」 · 항구명(인천항·목포·완도·제주…) · 「결항」 | 승선/출항 낱말 + 항구명 |

| 확신도 | 조건 | 하는 일 | 화면 문구 |
|---|---|---|---|
| ① 자동 반영 | 수단이 정해지고 + 식별자(편명/열차번호/터미널 쌍+출발시각/선명)와 탑승일이 둘 다 있음 | 카드 생성 + 금액, 되돌리기 단추 | 「자동 추가됨 · 문자+알림」 |

### E-5. 시각표 조회 연결 — 파싱한 승차권에서 조회 파라미터 만들기

| 수단 | 엔드포인트 | 넘기는 파라미터 | 원문→파라미터 규칙 | 실패 시 |
|---|---|---|---|---|
| 항공 | `GET /flights/schedule` | `airport`(IATA)·`date`·`direction`·선택 `flight` | 출발 공항을 원문에서 읽어 넘긴다(모르면 조회하지 않는다 — `FlightIngest.createFromLookup`의 `"ICN"` 고정을 고친다, C-9-4) | 404/503/429 → 카드 미생성·보관 |
| 기차 | `GET /trains/schedule` | `from`·`to`(역명 또는 역코드)·`date`·선택 `train` | `~역`을 떼고 역명만. 역코드가 원문에 있으면 그 값 | 503 `train_key_missing`·429 → 「출발 시각 확인 필요」 |
| 버스 | `GET /buses/schedule` | `from`·`to`(터미널명 또는 ID)·`date`·`type` | 도시명→터미널 해석(D-7-3). **후보 2개 이상이면 자동 선택 금지** | `resolved:false` → 「어느 터미널인가요?」 / 503·429 → 카드 미생성 |
| 배 | `GET /ferries/schedule`(키 확보 후) | `from`·`to`(항구)·`date` | 항구명 그대로 | 키 없음 → 알림 시각 사용(D-9) |

1. **식별자가 있으면 좁혀서 부른다**(편명·열차번호). 없으면 **구간+날짜**로 후보를 받아 금액대·시각대·등급·항공사로 좁히고 AI가 고른다. 후보 1건이면 확정, 여러 건이면 「이 편인가요?」, 0건이면 카드 미생성(C-9-7).
2. **시외버스는 오늘만** — 내일 이후는 조회를 부르지 않고 알림 시각을 쓴다(D-7-4).
3. **지연·변경 보정은 실시간 정보가 있는 수단만**: 항공은 `/flights/status`(인천만 — A-1-3), 기차·버스는 이번에 실시간 소스가 없으므로 **계획 시각을 그대로 쓰고 지연을 지어내지 않는다.** 결항·변경 알림이 오면 상태만 바꾼다(D-5-3).

### E-6. 일정 카드 생성 — 필드와 보정 규칙

1. 카드 필드(저장은 `TravelRideFields`, D-1): `vehicleKind` · `serviceNumber`(편명/열차번호/버스 출발시각+터미널 쌍/선명+항차) · `serviceName`(등급·열차종류) · `originName`·`destinationName` · `originCode`·`destinationCode`(역코드·터미널 ID) · `boardingTime`·`departureTime`·`arrivalTime` · `fareAmount`·`fareCurrency`·`fareSource` · `status`.
2. **시각의 정본은 조회 결과**(조회가 성공했을 때), 실패하면 **원문 시각**. 둘 다 없으면 카드를 만들지 않는다.
3. **여행 묶기·되돌리기**는 C-9-5·C-9-6 그대로이고, 여행이 없는 날짜는 **I절에 따라 자동 생성**한다(보류가 아니다).
4. **표시**: 이동 줄에 놓고(`TravelPlanTable.isMove`), 지도 핀은 좌표를 알 때만. 카드에 「자동 추가됨 · 문자+알림」, 금액은 「₩23,800 · 예약 문자」처럼 출처 포함.

| 구간·시각·등급·수단·금액 | 기기 | 판정·조회에 필요한 범위 | **허용 필드만**(화이트리스트) |

1. **전송 화이트리스트**: `allowedTelemetryKeys = ["mode","kind","confidence","failure","lane","durationMs","byteCount"]` 같은 허용 목록을 만들고, 그 밖의 키는 **기본값 전송 안 함**. 새 필드가 생기면 허용 목록에 올리기 전까지 전송되지 않는다.
2. `PHG1120A01`의 진단 로그(`DiagnosticsLogPackageBuilder`)에 알림·예약 관련 키를 redact 목록으로 넣는다 — 원문·예약번호·금액·좌석·전화번호에 더해 **숙박(`stayLog`·투숙객 이름·숙소 예약번호)·이동(`rideLog`)** 키까지 같은 목록에 넣는다(PHG1120A01의 4.2·4.4와 같은 잣대 — 전송 화이트리스트 밖 키는 기본 전송 안 함).
3. `rideLog`는 **백업 파일 안에만**(`flightLog`와 같은 규칙) — 서버·AI·분석으로 나가지 않는다.
4. 앱 화면에서도 카드에 「원문 보기」를 두지 않는다(E-2-5-4).

## F. 선택 라벨 + 포맷(스켈레톤)만 전송하는 학습

대표 지시(2026-11-20 18:35): 「내용은 다 지우고 포맷만 딱 보내서 … 학습시킬 수 있게」. **원문 없이 포맷만 학습한다** — 이 수준을 정확히 지키고 「완전 익명」이라고 쓰지 않는다.

#### F-1. 라벨은 사용자 선택에서 얻는다

1. 같은 원문이라도 사용자가 **가계부**를 고르면 `ledger`, **여행 일정**을 고르면 `travel` 라벨이 붙는다. E-4 확신도 ②·③의 **확인 카드에서 고른 결과가 곧 라벨**이다(새 UI를 만들지 않는다 — 지금 카드의 두 단추가 라벨 단추가 된다).
2. **라벨 없는 알림은 학습에 쓰지 않는다**(자동 판정만). 라벨은 대표님 선택의 결과이지 추측이 아니다.
3. 라벨은 요청 필드 `label`(`ledger`|`travel`)로만 보내고, 그 선택의 시각·대상은 기기에서 정해진다.

#### F-2. 마스킹은 **기기**에서 — 서버로 원문을 보내지 않는다

`TaptionPlan/Core/AlertSkeleton.swift`(새)가 다음 규칙으로 스켈레톤을 만든다.

| 원문 | 스켈레톤 |
|---|---|
| 숫자 | `#`(연속 숫자는 자릿수 유지): 계좌 `###-###-######`, 금액 `#,###원`, 카드 `####-####-####-####`, 승인번호 `########` |
| 영문 대문자/소문자 | `A` / `a`(편명 `KE###`, `A###` — 자리 유지) |
| 한글 | `가`(일반 명사) / **보존 사전에 있는 것만 원형 유지**(은행·카드사·항공사·철도·터미널·역명 등 **공개 상호만**) |
| 날짜·시각 | `YYYY-MM-DD`·`HH:MM` 토큰(값은 유지하지 않고 자리만) |
| 공백·문장부호 | 유지(템플릿 구분에 필요) |

1. **보존 사전에 사람 이름·계좌주·주소·개인 휴대전화 번호는 절대 넣지 않는다** — **기관·공개 상호는 넣는다**(은행·카드사·항공사·철도·고속버스 예약채널 같은 공개 상호 — `publisher` 학습의 근거, F-8-2). 사전의 **실제 항목은 앱 코드·이 지시서에 다 적지 않고**, 서버 설정·앱 리소스로 두되 **공개된 상호만** 넣는다.
2. **잔존 검사**: 마스킹 뒤 **보존 사전에 없는 한글 연속 2자 이상이 남아 있으면 전송을 중단하고 그 요청을 기기에서 폐기**한다(지명·상호가 아닌 이름이 새는 것을 막는다). 중단 사유는 로컬 카운터만.
3. 스켈레톤에 원문이 섞일 길을 줄이기 위해, 전송은 **원문이 아니라 스켈레톤 문자열 하나**만 한다.

#### F-3. 전송 payload — 원문 필드는 스키마에 없다

```json
{ "label": "travel", "publisher": "대한항공", "skeleton": "[가가항공] 가가 가가 가가 ###-###-### (A##)\n출발 ###-###-## ##:## → 도착 …",
  "skeleton_hash": "<sha256 16진>", "char_len": 180, "sender_type": "airline", "sender_number_hash": "<sha256 16진>",
  "app_bundle_id": "com.example.air", "received_at": "2026-11-20T19:02Z", "device_locale": "ko_KR" }
```

- **원문·실제 숫자·실제 이름·전화번호·예약번호는 필드 자체가 없다.** 서버 스키마에서 원문 필드를 **정의하지 않는 것으로 강제**하고, 본문에 `text`·`raw`·`body` 같은 키가 오면 **무시가 아니라 400 `raw_field_forbidden`** 으로 거절한다.
- `publisher`는 보존 사전에서 맞힌 **공개 상호 원형**, `sender_number_hash`는 기관 대표번호의 해시(F-8-3). **개인 번호는 여기에도 담지 않는다.**
- `received_at`은 **분 단위 절사**, `skeleton_hash`는 기기에서 계산한 sha256(원문 복원 불가).

#### F-4. 서버 학습 — 템플릿 클러스터링과 k-익명성

1. `skeleton_hash`가 같으면 같은 포맷이다. 새 포맷이 **서로 다른 세션(설치)에서 N회(초기 3회) 이상 같은 라벨로** 관찰될 때만 템플릿 후보로 승격한다. 1~2회짜리 희귀 스켈레톤은 **저장하지 않고 버린다**. 클러스터 키는 **`(publisher, skeleton_hash)`** 다(F-8-2) — 같은 라벨이라도 A은행과 B항공은 다른 템플릿이다.
2. 승격된 템플릿은 카탈로그로 저장한다: `{template_id, publisher, label, skeleton_regex, fields:[{name, kind(money|date|code|station), position}], confidence}`. 이 카탈로그가 새 알림을 분류하는 규칙이 된다.
3. `publisher`도 보존 사전에 있는 공개 상호만. 카탈로그는 사용자별 KV/D1에 두고 전역 공유 통계를 만들지 않는다(초기에는 기기·계정 단위 학습).
4. **추출은 값이 아니라 자리로**: `fields.position` 으로 새 원문에서 금액·날짜·편명을 뽑고, 뽑은 값은 **기존 저장 정책(E-7·C-3-5)대로** 마스킹·해시·지출 대조.
5. **한계 명시**: 스켈레톤도 발신 기관·문구 배치로 어느 정도 추정될 수 있다. **「원문 없이 포맷 학습이 가능하다」**까지만 보장하고 「완전 익명」이라 쓰지 않는다.
6. **승격의 판단 근거는 우리 D1이지 PostHog가 아니다(대표 확인 2026-11-20 18:46 「판단 근거가 그거면 또 안 되는 경우가 생기는 거 아니야?」).** 세션 수·라벨 일치·`publisher` 클러스터는 승격 판정 시점에 **D1의 관찰 행을 직접 세어** 정한다. PostHog는 사본·관측용으로만 보내고, **PostHog가 막히거나 한도·보존 기간에 걸리거나 값을 못 읽는 상태에서도 승격·배포가 그대로 돌아야 한다**(PostHog 응답을 승격 조건·순서·집계 어디에도 넣지 않는다). PostHog에만 있는 신호로 만드는 규칙은 두지 않는다.

#### F-5. 사용자 통제

1. 앱 설정: ⑴ 학습 참여 on/off ⑵ 라벨별 학습 초기화(`DELETE /ingest/learning?label=`) ⑶ 카탈로그에 내 템플릿이 몇 개인지 보기.
2. **끄면 전송 자체가 없다**(요청을 만들지 않는다 — 서버에서 204로 무시하는 것과 다르다).
3. 삭제 요청 시 카탈로그·학습 카운터를 함께 지운다.

#### F-6. 시험 7건

1. 은행 입금 문자 → 가계부 라벨 → **원문 없이 스켈레톤만** 전송(요청 본문에 원문이 없다 — 키 목록으로 확인).
2. 항공 알림톡 → 여행 라벨 → 스켈레톤에 편명 자리(`A###`)가 남고 숫자가 없다.
3. 사람 이름이 든 문자 → 잔존 검사에서 **차단**(전송 0건, 로컬 폐기).
4. 희귀 스켈레톤 1회는 저장되지 않는다.
5. 같은 포맷이 서로 다른 3세션에서 관찰되면 템플릿으로 승격된다.
6. 원문 필드(`text`)를 넣어 보내면 **400 `raw_field_forbidden`**.
7. 학습 끔 상태에서 요청이 생성되지 않는다.

#### F-7. 즉시 삭제 — 「그리고 바로 삭제」(대표 지시 18:35)

1. **기기**: 스켈레톤 추출·전송이 끝나면 **원문을 메모리에서 즉시 폐기**하고 임시 파일·클립보드·UserDefaults에 남기지 않는다. 단축어가 남기는 입력 항목도 함께 지운다(`FlightInbox`·`PaymentInbox`의 보관 항목은 파싱 후 제거하고 `text` 필드를 보관하지 않는다 — 파싱 결과만 남긴다). 가계부·여행 카드로 확정된 뒤에는 **원문이 아니라 파싱된 필드(금액·일시·구간·수단)만** 저장한다.
2. **서버**: 요청 처리 중 원문이 메모리에 있는 구간을 최소화하고(파싱→판정→응답 직후 폐기), **D1·KV·R2·Workers 로그·PostHog 어디에도 원문을 쓰지 않는다.** 재시도·디버깅용 보관도 없다. 새 라우트는 `console.log`·`console.error`에 요청 본문을 찍지 않는다(지금 `src/index.js`도 본문을 기록하지 않는다 — 그 규칙을 유지한다).
3. **사용자 선택 뒤에도 보관하지 않는다**: 확인 카드가 원문을 다시 보여 줘야 하는 UX가 있으면 **그 세션 메모리에서만**(SwiftUI `@State`) 보여 주고 화면을 닫으면 사라지게 한다. `UserDefaults`·파일·`AITaskQueue` 본문에 남기지 않는다.
4. **삭제 확인 경로**: 앱 설정의 「수집된 항목 전체 삭제」가 **기기 캐시·KV 항목·파생 카드까지** 지우고 **지운 개수(`{deleted: n}`)를 돌려준다**.
5. **시험 3건**: ⑴ 전송 후 기기 임시 저장소(임시 디렉터리·UserDefaults·보관함)에 원문이 남지 않는지 ⑵ 서버 응답 후 서버 저장소·로그에 원문이 없는지(저장소 전수 조회) ⑶ 삭제 요청 후 잔여물 0인지.

#### F-8. 서버에는 **템플릿만** 저장된다 (대표 확인 18:36 「서버에는 그 템플릿만 저장이 돼야 돼」)

1. **저장되는 것 — 이것 빼고 없다**:

```json
{ "template_id": "tpl_...", "publisher": "대한항공", "skeleton_regex": "...", "label": "travel", "sender_type": "airline",
  "fields": [ { "name": "departure", "kind": "date", "position": 3 } ],
  "observed_count": 7, "first_seen": "2026-11-18", "last_seen": "2026-11-20",
  "confidence": 0.82, "engine": 3 }
```

2. **`publisher`는 필수 필드다 — 발신 기관은 학습한다**(대표 정정 18:37: 「누가 보냈는지는 학습해야 되는 거 아니냐. 신한은행이 보냈는지, 대한항공이 보냈는지」). 템플릿 키는 **`(publisher, skeleton_hash)`** 조합이고, `sender_type`·`label`과 함께 **「같은 기관의 다른 포맷」을 가르는 기준**으로 쓴다(같은 대한항공라도 예약확정·탑승안내·결항이 다른 템플릿). `publisher`는 스켈레톤 보존 사전(공개 상호)에서 온 원형이다(F-2).
3. **발신 번호는 보조 수단, 원형 저장 금지**: 기관 대표번호(`1544-XXXX`·`1588-XXXX`)는 `publisher`를 식별하는 보조 근거로만 쓰고, 저장은 **해시**(`sender_number_hash`)로 한다. 해시→`publisher` 매핑표만 두고 원번호는 어디에도 남기지 않는다. 개인 휴대전화 번호는 해시하지도 않고 **버린다**.
4. **저장 금지 목록(코드 리뷰 1순위)**: 원문 · 실제 금액/날짜/예약번호/이름 · **사용자별 전송 이력** · 요청 본문 스냅샷 · 기기 식별자 · 라벨별 개별 로그 · **사람 개인 식별자**(사용자 ID·기기 토큰·계좌주 이름·개인 번호·친구 카톡 발신자). 집계는 템플릿의 `observed_count` 하나뿐이다(사용자별 카운트를 따로 두지 않는다).
5. **개별 사용자 추적 금지 — 뜻을 분명히 한다**: **사람**은 연결하지 않는다(사용자 ID·토큰을 템플릿 행에 붙이지 않고, 토큰은 인증에만 쓰고 저장·로그하지 않는다). **기관·발신자명은 학습 대상**이다(위 2·3) — 이 둘을 섞으면 안 된다.
6. **k-익명성 카운트 방법**: 「서로 다른 세션 N회」를 세기 위해 일일 회전 salt로 `HMAC(salt, installID)`를 만들되 **salt와 해시는 그날 메모리에서만** 쓰고 승격 판정 뒤 버린다. 저장소에 남는 것은 `observed_count` 숫자뿐이다(개별 세션 목록을 저장하지 않는다).
7. **카탈로그 조회 API**: `GET /ingest/templates`는 **서명된 번들 형태**(G절 `SignedBundle`과 같은 형식)로만 돌려준다. **원본 전송분은 서버에 남기지 않는다**(재전송·재조회라는 개념 자체가 없다).
8. **삭제**: `DELETE /ingest/templates` · 라벨별 삭제 · 전체 삭제가 템플릿 행과 카탈로그 번들을 함께 지운다(F-5-3·F-7-4).
9. **시험**: ⑴ A은행 문자와 B항공 알림톡이 **같은 `travel` 라벨이어도 `publisher`로 분리 저장**되는지 ⑵ 발신번호가 **원형으로 저장되지 않는지**(해시만) ⑶ 개인 이름·개인 휴대전화 번호가 **저장되지 않는지** ⑷ 전송 몇 건을 처리한 뒤 **서버 저장소를 전수 조회**해 **템플릿 행(위 10개 키) 외에 아무 것도 없음**을 확인(원문·사용자 ID·요청 본문·기기 ID 전부 0건).

| `TaptionPlan/Core/LedgerCapture.swift` | 코드 내장 휴리스틱 — 결제 신호 검사(`hasPaymentSign`)·안내문 제외(`isNotice`)·금액 추출(`amount`와 잔액 제거)·통화 표(`messageCurrencies`) | `parse(_:now:calendar:)`(`:92`), `isPaymentCandidate`(`:66`), `isDuplicate`(`:81`) |

우선순위(주석 기준): **내가 정한 규칙 → 내 AI 규칙 → 공통 규칙 → 코드의 표.**

### G-1. 앱은 확정 포맷만 안다

1. 코드 내장 표(`LedgerCapture`)는 **지금 확정된 포맷만** 남긴다. 새 포맷은 앱에 하드코딩하지 않는다.
2. 새 포맷은 **공통 규칙 번들(서버 배포)** 로만 들어온다 — 앱 업데이트 없이 갱신된다.
3. 배포 주기: 지금은 하루 1회(`checkInterval 86_400`) — 그대로 유지하고, 대표님이 앱 설정에서 **「지금 확인」을 누르면 즉시**(기존 `sync(force: true)`, `:110`). 백그라운드 확인 주기는 유지.
4. 번들 스키마에 `label(ledger|travel)`·`sender_type`·`skeleton_regex`·`fields`를 넣어 **F-8 템플릿 카탈로그와 같은 파일**로 관리한다(두 벌로 나누지 않는다).

### G-2. 확정 안 된 것은 판별로 넘긴다

1. 내장 표·공통 규칙·AI 규칙 어디에도 안 걸리면 **AI 판별**로: `AITaskQueue.enqueue(.paymentText, text:, context: ["ruleHint": "classify_only"])` → **가계부 / 여행 / 버림** 판단 + 라벨.
2. AI가 정규식을 제안하면 지금 구조 그대로 **견본 검증**(`LedgerMessageRules.validated`, `:21`)을 통과해야 기기 저장(최대 20). 흐름: **판별 실패 → AI 정규식 제안 → 견본 검증 → 기기 저장**.
3. 라벨은 F-1의 사용자 선택이 항상 우선한다. AI 라벨은 확신도 ③ 표시용이다(사용자 선택을 덮어쓰지 않는다).

### G-3. 룰 파일은 앱 번들과 분리 배포

1. 번들은 앱 번들 밖(서버/R2)에서 내려오고, **서명 검증을 통과해야** 적용된다(지금 구조 그대로).
2. 스키마: `{ version, engine, rules: [ { id, label, sender_type, skeleton_regex, fields: [ { name, kind, position } ] } ] }` + `signature`. **견본 원문(`sample`)은 넣지 않는다** — 넣어야 하면 스켈레톤만.
3. `engine` 번호가 앱이 아는 범위를 넘으면 그 번들은 **적용하지 않는다**(앱 업데이트 필요 안내만).
4. 번들에 새 필드가 생기면 **기본값 적용 안 함**(허용 목록 방식).

### G-4. 롤백

1. 새 번들이 **서명·engine 검증에 실패하면 기존 번들을 그대로 유지**한다(지금도 그렇게 동작한다 — `verified`·`signedVersion`(`:79`·`:133`)).
2. 잘못된 규칙 **1건만 끄기**: `disabledIDs`(`:49`)에 넣으면 그 규칙만 무효(이미 있다 — 앱 설정에 노출).
3. 번들 단위 되돌리기: 기기에 **직전 번들 사본을 남겨** 「이전 규칙으로 되돌리기」를 둔다(서명이 유효한 것만 보관).
4. 서버에서 잘못된 번들을 내리면 다음 확인 때 이전 것으로 돌아간다(검증 실패 = 유지).

### G-5. 오프라인 — 완료 판정에 넣는다

1. 번들을 못 받아도 **내장 표 + 기기 AI 규칙**으로 동작해야 한다(현재 구조 그대로). 네트워크 실패는 「규칙 새로 받기 실패」 표시만 하고 파싱은 계속된다.
2. **완료 판정**: 비행기 모드(네트워크 끔)에서 결제 문자 파싱·카드 생성·기차/버스 예약 문자 카드가 그대로 된다.

### G-6. 즉시 삭제 — 규칙·기여에도 같은 잣대

1. 번들·규칙에는 **견본 원문을 넣지 않는다**(`skeleton_regex`·필드 자리만).
2. 기여(`contributeKey`)로 올라가는 것도 **스켈레톤·라벨·발신유형**뿐이다(원문 금지, `sentLimit 500` 유지).
3. 규칙이 적용된 뒤의 원문도 저장하지 않는다(F-7-1).
4. 삭제 요청 시 기기 캐시·**기여 대기열**·파생 카드까지 지운다(`{deleted: n}`).

### G-7. 시험 7건

1. 번들 없이 내장 표만으로 결제 문자를 파싱한다.
2. 새 번들을 받으면 **앱 업데이트 없이** 규칙이 적용된다(버전·엔진 메타데이터 확인).
3. 서명이 맞지 않는 번들은 **무시**되고 기존 번들이 남는다.
4. 번들 규칙이 견본과 맞지 않으면 **내장 표로 폴백**한다.
5. 확정되지 않은 포맷이 AI 판별로 넘어가 **라벨이 붙는다**.
6. 번들·기여 경로에 **원문이 없다**(스켈레톤만) — 요청 본문 키 목록으로 확인.
7. 번들에 **`channels`(화이트리스트)와 `templates`가 같이 실려** 앱 업데이트 없이 화이트리스트가 갱신되고, 자동 업데이트를 끄면 요청이 가지 않는다(G-8).

### G-8. 운영 방식 — 「수집은 전부, 판정은 나중, 배포는 내가 원할 때」 (대표 지시 18:38)

대표 발화 그대로: 「문자·카카오톡 알람·앱 알람을 전부 일단 받은 다음에, 화이트리스트 룰이 서버에서 계속 업데이트돼서 자동 배포가 될 수 있게, 내가 원하면.」

1. **수집은 전부 먼저**: 세 소스(문자 · 카카오톡 알림톡 · 앱 알림)를 일단 같은 수집 경로에 태우고, **판정은 나중에** 다음 순서로 한다: ① 채널 화이트리스트(E-2-2) ② 스켈레톤 템플릿 카탈로그(F-8) ③ 내장 표(G-0). 수집 단계에서 사용자 대화를 읽는 것이 아니라 **대표님이 넘긴 알림만** 들어온다는 한계는 그대로다(E-1-1).
2. **화이트리스트도 같은 서명 번들로 배포한다**: 채널 화이트리스트(발신 기관 `publisher` + 기관 대표번호 해시)와 스켈레톤 템플릿 카탈로그를 **하나의 서명된 번들**에 담아 앱 업데이트 없이 갱신한다. 번들 버전·`engine` 번호·서명 검증은 기존 `SharedRuleStore`(`SignedBundle`:8·`verified`:79)를 그대로 쓴다. 번들 스키마:

```json
{ "version": 42, "engine": 3,
  "channels": [ { "publisher": "<공개 상호>", "sender_number_hash": "<sha256>", "sender_type": "bank" } ],
  "templates": [ { "template_id": "tpl_...", "publisher": "<공개 상호>", "label": "ledger", "sender_type": "bank",
    "skeleton_regex": "...", "fields": [ { "name": "amount", "kind": "money", "position": 2 } ], "confidence": 0.8 } ],
  "signature": "<Ed25519>" }
```

3. **자동 배포는 대표님 스위치**: 켜면 ⑴ 하루 1회 자동 확인(`checkInterval 86_400`) ⑵ **앱을 열 때 즉시 확인**(`sync(force: true)`, `SharedRuleStore:110`); 끄면 **요청 자체를 보내지 않는다**. 화면 문구는 이 스위치가 곧 「내가 원하면」이라는 것을 그대로 적는다:
   - 켬: 「규칙 자동 업데이트 켬 — 앱을 열 때와 하루 한 번 새 규칙을 확인해요.」
   - 끔: 「규칙 자동 업데이트 끔 — 지금 확인을 누를 때만 받아요.」
4. **잘못된 번들 대비**: 서명 불일치·스키마 위반 번들은 **무시하고 기존 번들 유지**(G-4-1), 특정 규칙만 끄는 `disabledIDs`(`:49`) 유지, **롤백용 이전 버전 보관**(G-4-3).
5. **배포 파이프라인(사람이 개입하는 지점 표시)**:

| # | 단계 | 하는 것 | 사람 개입 |
|---|---|---|---|
| 1 | 승격 | 서버가 F-8 규칙(다른 세션 N=3)으로 템플릿 후보를 승격 | 없음(자동) |
| 2 | **검수·승인** | 대표님이 검수 화면(G-9)에서 `publisher`·라벨·스켈레톤·관찰 횟수를 보고 **켜기/끄기** | **대표님(필수 게이트)** — 승인 전에는 번들에 안 들어간다 |
| 3 | 번들 생성 | 화이트리스트 + **승인된** 템플릿으로 `version`·`engine` 올림 | 없음(자동) |
| 4 | 서명 | 오프라인 서명 키(Ed25519)로 `signature` 생성 | **대표님(또는 위임된 배포 절차)** — 번들에 무엇이 들었는지 확인 후 서명 |
| 5 | 공개 | R2/서버에 번들 올림(공개 저장소 아님) | 대표님 스위치(자동 배포 켬/끔) |
| 6 | 확인 | 앱이 주기·앱 열 때·「지금 확인」으로 받음 | 대표님이 끄면 없음 |
| 7 | 적용 | 서명·engine 검증 통과 시 적용, 실패 시 기존 번들 유지 | 없음(자동·되돌리기 가능) |

### G-9. 검수·승인 화면 — 후보는 대표님이 켜야 배포된다

약속(2026-11-20 18:38): 「그 자료는 서버 템플릿 카탈로그에 후보로만 쌓이고, 대표님이 승인한 것만 번들에 들어가 배포됩니다. 검수 화면에서 포맷과 관찰 횟수를 보고 켜고 끌 수 있게 하겠습니다.」

1. **위치**: 앱 설정 › 문자·알림 규칙 — **기존 `SharedRulesView`(`TaptionPlan/UI/SharedRulesView.swift:5`, 입구 `AssistantSafetyViews.swift:518` 「공통 규칙」)를 확장**한다. 새 설정 화면을 발명하지 않는다. 지금도 「운영자가 직접 확인해 승인한 것만 … 승인 전에는 아무에게도 가지 않아요」라고 적혀 있으니(`:33`) 그 문장을 이 구조에 맞게 다듬는다.
2. **목록 항목(한 줄)**:

| 칸 | 값 |
|---|---|
| `publisher` | 공개 상호(기관) — 가상 예: `○○은행` · `○○항공` |
| `label` | 가계부 / 여행 |
| 스켈레톤 | **마스킹된 포맷만** — 예: `[○○은행] ##:##:## ###,###원 출금 ###-##-##-######` |
| `observed_count` | 관찰 횟수(서로 다른 세션 기준) |
| `first_seen`·`last_seen` | 날짜만 |
| `sender_type` | bank·card·airline·rail·bus·ferry·channel |
| 상태 | **후보 / 승인 / 꺼짐** |

3. **동작**: ⑴ 개별 켜기·끄기 ⑵ 포맷 상세 보기(스켈레톤·필드 자리·관찰 횟수) ⑶ 삭제(`DELETE /ingest/templates`) ⑷ **신고**(「잘못 읽었어요」 — 그 템플릿을 즉시 `disabledIDs`로 옴기고 서버 후보에서 빼기) ⑸ 전체 초기화. **끈 항목은 `disabledIDs`(`SharedRuleStore.swift:49`)에 들어가 번들이 갱신돼도 적용되지 않는다.**
4. **승인 게이트(두 단계를 표로 명시)**:

| 판단 | 누가 | 기준 | 결과 |
|---|---|---|---|
| 승격(후보로 올리기) | **서버** | 서로 다른 세션 3회 이상·같은 라벨·같은 `publisher`(F-8-4) | 카탈로그에 **후보** 행 |
| 승인(배포에 넣기) | **대표님** | 검수 화면에서 켜기 | 번들에 포함되어 배포 |

5. **원문이 화면에 보이지 않게**: 스켈레톤만 보여 주고 **원문 미리보기 기능은 넣지 않는다.** 금액·날짜 예시도 실제 값이 아니라 `###,###원`·`##:##` 같은 **마스킹된 예시**로만. 화면 예시 문구의 기관명은 **가상 이름**(`○○은행`·`○○항공`)으로 쓴다 — 실제 채널명을 저장소에 쓰지 않는다.
6. **시험 3건**: ⑴ 후보가 목록에 뜨고 승인 전에는 **번들에 들어가지 않는다**(번들 직렬화 결과에 `template_id` 없음) ⑵ 승인하면 다음 번들에 들어간다 ⑶ **끈 항목이 번들 갱신 후에도 꺼진 채**로 유지된다(`disabledIDs` 재적용).

3. **취소·변경 알림**도 같은 통로로 온다. 금액·날짜를 고치지 말고 상태만 바꾼다(C-5와 같은 규칙).

### H-2. 카드 모양 — 시각 대신 기간

1. **기간 개념은 이미 있다 — 실제 이름으로 보면 이렇다.** ⑴ 여행 자체의 기간은 `TravelTrip.startDay`·`endDay`(`Packages/TaptionPlanStore/Sources/TaptionPlanStore/Snapshot/TravelTrips.swift:4~12`, `YYYY-MM-DD` 문자열이고 **당일치기는 둘이 같다**) — 새 기간 칸을 만들지 않는다. ⑵ 일정 한 칸은 `TravelTripItem.start`·`end`(`Date`)와 `startOffsetSeconds`·`endOffsetSeconds`이고, **종류 `kind`(String)에 「숙박」이 이미 있다** — `lodging`은 `TravelPlanColumns.allKinds` 12종 중 하나이고 기본 열 구성의 「숙소」 열(`["lodging","sleep","rest"]`)이 받는다(`TravelTrips.swift:64·70~75`). ⑶ 연박 길이의 기본값도 이미 있다(`TravelQuickEntrySheet.swift:136~138`이 `lodging`을 2,880분으로 둔다). ⑷ 숙소 준비물 카드 `TravelPrepItem`도 이미 `kind: "lodging"`·`refCode`(예약번호, 기기 안)·`validUntil`·`needsDateConfirmation`을 갖고 있다(`AppFeatureSettings.swift`의 `TravelPrepItem`) — **새 구조를 만들지 말고 이것을 쓰거나 늘린다.** 카드 칸: `stayName`(숙소명) · `stayArea`(지역·동네) · `checkIn`/`checkOut`(날짜, 시각은 있으면) · `nights` · `roomType`(있으면) · `stayChannel`(야놀자·트립닷컴·직접) · 금액은 C-3과 같은 방식(지출이 정본, 카드는 사본). `TravelTripItem`에는 `rideLog`(D-1)와 같은 방식으로 `stayLog` 한 칸(JSON, 기기 안)만 더한다.
2. **예약번호·투숙객 이름은 기기 안에만**(`stayLog`, 백업 파일 안에만). 서버·AI·분석으로 가지 않는다(C-6·D-6-7과 같다).
3. 일정 표시는 **연박 막대**다: 체크인 날 시작해 체크아웃 날 끝나는 한 줄(여러 날에 걸쳐 보임), 하루짜리 카드와 구분되는 모양. 지도·표 어느 쪽이든 **같은 기간을 쓴다**.

### H-3. 판정 — 이동수단과 서로 오분류하지 않게

1. OTA 이름은 판정 근거가 **아니다**(C-2-1 보강). 단서는 문구다: 숙박 단서(`체크인`·`체크아웃`·`투숙`·`n박`·`객실`·`숙소`·`호텔`·`펜션`·`리조트`) 대 이동 단서(`편명`·`탑승`·`출발`·`도착`·`열차`·`버스`·`터미널`·`항차`).
2. 둘 다 있으면(항공+호텔 패키지) **카드 두 장**(항공 1 + 숙박 1)이고, 결제가 한 건이면 C-4-4(왕복·묶음)와 같은 방식으로 **한 결제를 두 카드에 중복으로 붙이지 않고** 「패키지 결제」로 묶어 표시한다. 나누는 것은 사용자가 고를 때만.
3. 확신이 낮으면 카드에 붙이지 않고 「확인 필요」로(C-2-3·C-2-4와 같다).

### H-4. 병합·자동 생성·되돌리기

1. 병합 키: 예약번호가 있으면 그것, 없으면 `(숙소명, 체크인 날짜, 금액)`. 문자+알림톡+푸시가 같은 예약이면 **한 건**으로 합친다(C-9-2).
2. 자동 생성: **체크인 날짜** 기준 그 날짜를 덮는 여행에 카드를 만든다. 그 여행이 없으면 **I절(`AUTO1120A01`)대로 자동 생성**한다(이 문서의 I절이 「미지정」 보류를 대체했다 — H-4-2는 처음 쓸 때의 보류 규칙이 남아 있던 자리다).
3. 되돌리기: 한 번에 취소, 취소한 예약은 다시 자동 추가하지 않는다(기기 안 기억 — C-9·D-6-6과 같다).
4. 개인정보: 서버로는 **숙소명·지역·체크인/체크아웃·박 수·금액·채널**만.

### H-5. 시험 4건 (앱)

1. 야놀자 결제 알림톡(숙박 단서) → 숙박 카드, 연박 막대가 체크인~체크아웃에 걸친다.
2. 트립닷컴 알림(편명 + 호텔) → 카드 두 장, 결제 한 건은 「패키지 결제」로 묶여 두 번 붙지 않는다.
3. 같은 예약의 문자+알림톡 → 한 건으로 합쳐진다(중복 카드 0장).
4. 「취소」 알림 → 금액·날짜는 그대로, 상태만 취소.

### H-6. 이번에 하지 않는 것

1. 메일함에서 숙박 예약을 자동으로 긁어오는 일(연동·보관 정책 판단이 먼저다).
2. 숙소 가격 비교·최저가 알림.
3. OTA 계정 로그인·예약 조회 API 연동.

## I. 여행 카드 자동 생성 — 예약이 잡히면 여행이 따라 생긴다 (`AUTO1120A01`)

대표 지시 (2026-11-20 18:49 「항공이나 숙박 일정이 잡히면 자동으로 우리 여행 카드가 생성되게 해야겠네」). **앞서 이 문서가 정한 「새 여행을 만들지 않고 보류」를 이 절이 대체한다**(C-9-5·D-6-5·E-6-3·표의 해당 줄은 이 절을 따른다). 보류(`FlightInbox` 「미지정」)는 **자동 생성하지 않아야 하는 예외**에만 남긴다.

### I-1. 언제 만드는가

1. 항공·기차·버스·배·숙박 다섯 중 하나의 **예약이 확정되어 카드가 만들어지는 순간**, 그 카드의 날짜(숙박은 체크인~체크아웃)를 덮는 여행이 없으면 **여행 하나를 새로 만든다.** 결제만 있고 예약 정보가 없는 건은 만들지 않는다(C-2-3).
2. **규칙만으로 만든다** — AI·서버 호출 없이 결정적이다. 오프라인에서도 같다. 확신이 낮은 카드(「확인 필요」)는 여행을 만들지 않는다.
3. **자동 생성 스위치**: 설정 › 여행에 「예약 알림으로 여행 자동 만들기」 하나(기본 켜짐). 끄면 지금처럼 「미지정」 보류로 돌아간다.

### I-2. 이름과 기간

1. **기간**: 항공은 탑승일~같은 예약의 마지막 구간(왕복이면 귀국 도착일, 편도면 탑승일). 숙박은 체크인~체크아웃. 기차·버스·배는 승차일 하루. 뒤에 같은 여행에 붙는 예약이 있으면 기간을 **늘리기만** 한다(줄이지 않는다). 저장은 **기존 칸** `TravelTrip.startDay`·`endDay`(`YYYY-MM-DD`, 당일치기는 둘이 같음)에 한다 — 날짜 칸을 새로 만들지 않는다.
   - **기간의 정본은 예약이다 — 사용자에게 기간을 묻지 않는다**(대표 지시 2026-11-20 18:51 「예약했다 치면은 여행의 시작과 끝이 이미 정해지잖아」). 왕복 항공·숙박이 있으면 시작과 끝이 그 자리에서 정해지므로, 여행 생성·표시·이름(I-2-2의 박·일 계산)은 **묻지 않고 바로** 예약 값으로 채운다. 확인 화면을 새로 만들지 않는다.
   - **끝이 미정인 경우**: 편도만 있고 숙박도 없을 때처럼 도착·귀국 정보가 없으면 끝을 시작일로 두고 「끝 미정」으로 표시하며, 사용자가 기간을 늘릴 수 있게 열어 둔다. 그 상태에서도 여행은 만든다(보류하지 않는다).
2. **이름**: **「도착지 + 　박 　일」** (대표 지시 2026-11-20 18:50 「제목은 기본으로 도착지 플러스 몇 박 며칠」). 예: 「부산 2박 3일」·「제주 3박 4일」·「오사카 1박 2일」. 박·일 계산은 I-2-1의 기간에서: **박 수 = (체크아웃 또는 도착일) − (체크인 또는 출발일)**, **일 수 = 박 수 + 1**. 하루짜리(기차·버스·배·당일치기)는 「부산 당일」. 도착지가 여럿이면 마지막 도착지를 쓰고, 여러 나라에 걸치면 마지막 나라의 도시. 같은 도착지·같은 박 수의 여행이 이미 있으면 끝에 시각이나 「2」를 붙여 구분한다(이름이 겹쳐도 여행을 합치지 않는다 — I-4-3). **예약번호·편명·사람 이름은 이름에 넣지 않는다**(개인정보·서버 전송 금지).
3. 이름 칸은 **기존 `TravelTrip.title`** 이다(새 `name` 칸을 만들지 않는다). 자동 이름 여부는 `TravelTrip`에 **선택 칸 `nameIsAutomatic: Bool?`을 새로 더해** 기억한다(없으면 키를 쓰지 않아 예전 저장본 바이트가 그대로다 — `status`·`flightLog`와 같은 방식). 사용자가 `title`을 고치면 이 값을 `false`로 바꾸고, 그 뒤로 **자동 이름이 덮어쓰지 않는다.** 자동 이름으로 만든 여행에는 목록에 「자동 만든 여행」 배지를 단다.

### I-3. 중복·여러 예약이 한 여행으로

1. 새로 만들기 전에 **겹침 검사**를 한다: 새 기간이 기존 여행 기간과 **하루 여유(±1일)** 로 겹치면 만들지 않고 그 여행에 붙인다(C-9-5의 `FlightIngest.trip(on:)` 결과를 그대로 쓴다).
2. **한 예약으로 한 번만** 만든다 — 잠금 키는 D-6-3·H-4-1과 같은 예약번호(없으면 날짜+서비스). 같은 알림이 다시 와도 여행이 둘 생기지 않는다.
3. 왕복·숙박·기차가 따로 알림으로 와도 각각이 1의 겹침 검사로 같은 여행에 모인다(여행 하나에 항공+숙박+기차).

### I-4. 되돌리기·권한

1. 자동 만든 여행은 여행 삭제 한 번으로 없앤다. **지출 기록은 남는다**(C-4-7과 같다 — 여행만 사라진다).
2. 삭제한 예약은 다시 자동으로 여행을 만들지 않는다(기기 안 기억, C-9·D-6-6과 같다).
3. 여행 삭제·이름 변경은 **사용자만** 할 수 있다. 앱이 기존 여행을 지우거나 합치지 않는다(I-3-1은 「새로 만들지 않는다」이지 「합친다」가 아니다 — 기존 여행 두 개를 합치는 일은 사용자가 시킬 때만).

### I-5. 시험 4건 (앱)

1. 여행이 없는 날짜의 항공권 예약 알림 → 여행 하나 자동 생성 + 항공권 카드가 그 안에.
2. 같은 여행 기간에 숙박 알림 추가 → 새 여행이 생기지 않고 기간만 늘어난다.
3. 사용자가 이름을 고친 뒤 다른 예약이 붙는다 → 이름이 그대로 남는다.
4. 자동 만든 여행 삭제 → 지출은 남고, 같은 예약 알림이 다시 와도 여행이 다시 생기지 않는다.
