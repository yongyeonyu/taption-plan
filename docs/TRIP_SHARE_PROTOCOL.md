# 여행 공유 통신 규약 v1 (TSH1114A26)

여행 하나를 최대 10명이 함께 쓰는 「방」의 규약입니다. 1차 범위는 **계획 함께 쓰기, 여행 가계부·정산, 공지**입니다. 여행 중 동행 위치 공유는 21절에 따로 적었습니다(LOC1116S01, 서버 배포 전).
이 문서만 보고 앱을 구현할 수 있게 적었습니다. 서버 구현은 `server/trip-relay/src/share.js`, 시험은 `server/trip-relay/test/share.test.mjs`, 기기 쪽 참고 구현(Node)은 `server/trip-relay/test/share-client.mjs`입니다.

상태: 서버 구현·시험 완료, **배포 전**. 앱 구현 전. 배포 때 할 일은 20절.

## 1. 용어

| 말 | 뜻 |
|---|---|
| 방(room) | 여행 하나의 공유 공간. 서버의 Durable Object 하나 |
| 방 id(`roomId`) | 주인 기기가 만든 무작위 16바이트의 base64url(패딩 없음, 22자) |
| 링크 비밀 값(`linkSecret`) | 주인 기기가 만든 무작위 32바이트. **서버로 가지 않는다** |
| 비밀번호 | 주인이 정해 일행에게 따로 알려 주는 글자. **서버로 가지 않는다** |
| 뿌리 키·암호화 키·입장 증명 키 | 링크 비밀 값 + 비밀번호에서 기기가 만드는 키(3절) |
| 입장 증명(`proof`) | 입장 증명 키로 만든 32바이트 값의 base64url(43자). 서버는 이것의 SHA-256만 둔다 |
| 주인 열쇠(`ownerKey`) | 주인 기기가 만든 무작위 32바이트의 base64url(43자). 키체인에만 둔다. 서버는 SHA-256만 둔다 |
| 참여 토큰(`token`) | 서버가 입장 때 기기에 주는 무작위 32바이트 base64url(43자). 키체인에 둔다. 서버는 SHA-256만 둔다 |
| 참여자 번호 | 방 안에서 1부터 주는 정수. 주인은 항상 1. 나간 번호는 다시 쓰지 않는다 |
| 세대(`epoch`) | 키가 몇 번째인지. 1에서 시작, 비밀번호를 바꿀 때마다 +1 |
| 항목(item) | 암호화된 덩어리 하나(일정 하나, 지출 한 건, 공지 하나, 참여자 카드 등) |
| `rev` | 방 전체의 개정 번호(정수, 변경마다 +1). 항목의 `rev`는 그 항목 **내용**이 마지막으로 바뀐 때의 방 `rev` |
| `seq` | 항목이 마지막으로 **건드려진**(내용 또는 공지 확인) 때의 방 `rev`. 따라잡기의 기준 |
| 묘비 | 지운 항목의 자리. 암호문 없이 `deleted: true`만 남는다 |

시각은 모두 1970년부터의 밀리초(정수)이고 서버 시계 기준입니다. 응답·메시지의 `now`로 기기 시계와의 차이를 잽니다.

## 2. 링크

주인 기기가 `roomId`와 `linkSecret`을 만들고 링크의 **`#` 뒤**에 둡니다.

```
<앱이 여는 주소>#<roomId>.<linkSecret의 base64url 43자>
```

- `#` 뒤는 브라우저·앱이 서버로 보내지 않는 부분입니다. 앞부분(유니버설 링크나 앱 스킴)은 앱 단계에서 정합니다.
- 비밀번호는 링크에 넣지 않고 다른 길(말·다른 메신저)로 알립니다.
- `linkSecret`·비밀번호·`proof`·`ownerKey`·`token`은 **주소(경로·쿼리)에 넣지 않습니다.** 헤더와 본문으로만 보냅니다. 서버는 주소에 든 값을 읽지 않습니다.

## 3. 키 유도

모든 계산은 기기에서 합니다. 서버는 PBKDF2를 하지 않습니다(Workers의 PBKDF2는 반복 10만 번 상한과 무료 CPU 10ms에 걸립니다).

```
password  = 비밀번호를 유니코드 NFC로 정규화한 UTF-8 바이트
salt      = UTF8("taption-share-v1|" + roomId + "|") || linkSecret(32바이트)
root      = PBKDF2-HMAC-SHA256(password, salt, 반복 600000, 32바이트)
encKey    = HKDF-SHA256(ikm = root, salt = UTF8("taption-share-v1"), info = UTF8("enc"),  32바이트)
authKey   = HKDF-SHA256(ikm = root, salt = UTF8("taption-share-v1"), info = UTF8("auth"), 32바이트)
proof     = base64url( HMAC-SHA256(key = authKey, message = UTF8("join|" + roomId)) )   // 43자
```

- `roomId`는 base64url **글자 그대로**(22자의 ASCII) 넣습니다. 풀어서 넣지 않습니다.
- iOS: PBKDF2는 CommonCrypto `CCKeyDerivationPBKDF(kCCPBKDF2, …, kCCPRFHmacAlgSHA256, 600000, …)`, HKDF는 CryptoKit `HKDF<SHA256>.deriveKey(inputKeyMaterial:salt:info:outputByteCount:)`, HMAC은 `HMAC<SHA256>`. 시험 쪽은 Node WebCrypto(`PBKDF2`·`HKDF`·`HMAC`)로 같은 값을 냅니다.
- `encKey`는 항목을 잠그는 데만, `authKey`는 `proof`를 만드는 데만 씁니다. 서버는 `proof`만 봅니다. `proof`에서 `authKey`·`encKey`·`root`로는 거슬러 갈 수 없습니다.
- 세대는 유도에 넣지 않습니다. 비밀번호(또는 링크 비밀 값)가 바뀌면 키가 통째로 달라집니다.
- 반복 600000의 근거: 서버가 계산하지 않으므로 기기 성능만 봅니다. 링크가 새어 나갔을 때 비밀번호가 유일한 방어가 되므로 OWASP가 PBKDF2-HMAC-SHA256에 권하는 값을 씁니다. 입장·비밀번호 바꾸기 때 한 번씩만 계산하고 `root`는 키체인에 둡니다.
- 비밀번호 규칙(길이·글자 종류)은 앱 단계에서 정합니다. 규약은 NFC UTF-8 바이트면 무엇이든 받습니다.

## 4. 암호문 형식

```
cipher = base64url( 0x01 || nonce(12바이트) || AES-256-GCM 암호문 || tag(16바이트) )     // 패딩 없음
AAD    = UTF8("taption-share-v1|" + roomId + "|" + 항목 id + "|" + kind + "|" + epoch(십진수))
키     = encKey
```

- 첫 바이트 `0x01`은 형식 버전입니다. 서버는 이 바이트와 길이만 봅니다(1 + 12 + 16 = 29바이트 이상, 4096바이트 이하).
- nonce는 잠글 때마다 새 무작위 12바이트입니다. 같은 키로 같은 nonce를 두 번 쓰지 않습니다.
- AAD가 방·항목·종류·세대를 묶으므로, 서버가 암호문을 다른 항목 자리나 다른 종류로 옮겨 놓으면 풀리지 않습니다. 기기는 서버가 준 `id`·`kind`·`epoch`으로 AAD를 다시 만들어 풉니다. **풀리지 않는 항목은 버리고 화면에 내지 않습니다.**
- 평문은 UTF-8 JSON 객체이고 버전 칸 `"v": 1`을 둡니다(칸 순서는 뜻이 없습니다). 그 밖의 칸은 앱 단계에서 kind마다 정합니다(서버와 무관). 크기로 내용이 짐작되지 않게 JSON 뒤에 공백(0x20)을 붙여 길이를 64바이트 배수로 맞추기를 권합니다(공백은 JSON으로 읽을 때 무시됩니다).
- CryptoKit: `AES.GCM.seal(plain, using: key, nonce: nonce, authenticating: aad)`의 `ciphertext + tag`가 위의 「암호문 || tag」입니다.

## 5. 공통 규칙 (HTTP)

- 기본 주소는 기존 중계 서버와 같습니다. 본문과 응답은 JSON(`content-type: application/json`), 응답은 `cache-control: no-store`.
- 방 만들기만 **앱 등록 키**(`Authorization: Bearer <앱의 주인 키>`, 기존 `/register`로 등록된 것)로 인증합니다. 방 안의 요청은 **참여 토큰**(`Authorization: Bearer <token>`)으로 인증하고 앱 등록 키를 보내지 않습니다. 서버는 방과 앱 등록 키의 연결을 어디에도 적지 않습니다.
- 주인만 하는 일은 참여 토큰(참여자 1)에 더해 `x-share-owner: <ownerKey>` 헤더가 있어야 합니다.
- 본문은 64KB까지(키 교체만 2MB까지).
- 오류는 `{"error": "<코드>", …}`입니다.

| 상태 | 코드 | 뜻 |
|---|---|---|
| 400 | `invalid_json` | 본문이 JSON이 아님 |
| 401 | `unauthorized` | 토큰이 없거나 이 방의 것이 아님 |
| 403 | `removed` + `reason`(`kicked`\|`left`) | 내보내졌거나 나간 참여자의 토큰 |
| 403 | `owner_only` | 주인 열쇠가 없거나 틀림, 또는 참여자 1이 아님 |
| 403 | `wrong_password` + `remaining` | 입장 증명이 틀림. `remaining`번 더 틀리면 잠김 |
| 403 | `forbidden` + `index`, `kind` | 이 종류를 쓸 권한이 없음(10절) |
| 404 | `not_found` | 방이 없음(지워졌거나 기한이 지남) 또는 없는 경로 |
| 404 | `no_notice`, `no_member` | 확인할 공지·내보낼 참여자가 없음 |
| 405 | `method_not_allowed` | |

| 423 | `locked` + `locks` | 남이 잡고 있음. `locks`는 막은 잠금들 |
| 423 | `lock_required` + `names` | 쓰기 전에 잡아야 할 잠금 이름들 |
| 423 | `settlement_closed` | 정산이 마감되어 공유 지출을 쓸 수 없음 |
| 426 | `upgrade_required` | `/ws`에 WebSocket 업그레이드 없이 옴 |
| 429 | `rate_limited`, `join_locked`, `join_ip_limit`, `room_daily_limit` + `retryAfter`(초) | `Retry-After` 헤더도 같은 값 |
| 503 | `unavailable` | 서버에 방 기능이 아직 켜지지 않음 |

## 6. HTTP 경로

`<방>` = `/share/rooms/<roomId>`.

### 6.1 방 만들기 — `POST /share/rooms` (앱 등록 키)

```json
{ "roomId": "<22자>", "proof": "<43자>", "ownerKey": "<43자>", "expiresAt": 1765000000000 }
```

- `expiresAt`: 여행 끝 + 30일을 권합니다. 지금 + 1시간 이상, 지금 + 400일 이하.
- 201: `{ "roomId", "member": 1, "token", "epoch": 1, "rev": 0, "expiresAt", "limits": { "members", "itemBytes", "liveItems", "roomBytes", "batch", "locksPerMember", "leaseMs" } }`
- 오류: 401(등록되지 않은 키), 403(주인 범위가 아닌 키), 409 `room_exists`, 422 `bad_request`·`bad_expiry`, 429 `room_daily_limit`(한 앱 키가 하루 5개).
- 만든 기기가 주인(참여자 1)입니다. 이미 있는 방에 입장 링크를 더 만들거나 비밀번호를 바꾸는 일은 주인 열쇠로만 됩니다. 다만 참여자가 받은 내용을 **새 방**으로 올리는 것은 서버가 내용을 읽지 못해 가려낼 수 없으므로, 「참여자는 다시 공유하지 못한다」의 그 부분은 앱이 지킵니다(참여한 여행에는 공유 만들기 버튼을 내지 않음).

### 6.2 입장 — `POST <방>/join` (인증 없음)

```json
{ "proof": "<43자>" }
```

- 201: `{ "roomId", "member": 2, "token", "epoch", "rev", "closed", "expiresAt", "limits" }`
- 403 `wrong_password`(`remaining`), 429 `join_locked`(방 단위: 15분 안에 5번 틀리면 15분 잠금. 잠긴 동안은 맞는 증명도 받지 않음), 429 `join_ip_limit`(IP마다 하루 60번, 맞든 틀리든), 409 `room_full`, 404.
- 인원이 찼는지는 증명이 맞은 사람에게만 알립니다.
- 입장 뒤 기기는 자기 참여자 카드(`member-<번호>`, 6.6)를 올려 닉네임을 알립니다.

### 6.3 방 상태 — `GET <방>`

200:

```json
{ "roomId": "…", "you": 2, "owner": 1, "epoch": 1, "rev": 41, "closed": false,
  "createdAt": 0, "expiresAt": 0,
  "members": [ { "no": 1, "joinedAt": 0, "online": true }, { "no": 2, "joinedAt": 0, "online": false, "stale": true } ],
  "locks": [ { "name": "i:<항목 id>", "by": 1, "until": 0 } ],
  "counts": { "items": 12, "ids": 14, "bytes": 5310 }, "limits": { … }, "now": 0 }
```

`online`은 WebSocket이 붙어 있는지, `stale`은 비밀번호가 바뀐 뒤 아직 `rekey`를 하지 않은 참여자입니다.

### 6.4 따라잡기 — `GET <방>/changes?since=<seq>[&limit=<1..200>]`

200: `{ "rev", "epoch", "closed", "items": [항목…], "more": false, "next": 41 }`

- `seq`가 `since`보다 큰 항목을 `seq` 순으로 줍니다. `since=0`(처음 받기)일 때는 묘비를 빼고, 그 밖에는 묘비도 줍니다.
- `more`가 `true`면 `since=next`로 다시 부릅니다. `false`면 `next`는 방의 `rev`입니다. 한 번에 200개 또는 암호문 글자 합 256K까지.
- 절차는 9절.

항목의 모양:

```json
{ "id": "…", "kind": "plan", "rev": 7, "seq": 7, "epoch": 1, "cipher": "A…",
  "updatedAt": 0, "by": 2, "createdBy": 1, "group": "<있을 때만>", "acks": { "1": 0 } }
```

`acks`는 `notice`에만 있습니다(참여자 번호 → 확인한 시각). 묘비는 `{ "id", "kind", "rev", "seq", "deleted": true, "updatedAt", "by", "createdBy" }`.

### 6.5 잠금 — `POST <방>/locks`

```json
{ "acquire": ["i:<항목 id>", "g:<묶음 이름>"], "release": ["i:<다른 항목 id>"] }
```

- 200: `{ "locks": [ { "name", "by", "until" } ], "released": ["…"], "now" }` — `locks`는 이번에 잡은(또는 연장한) 것.
- 423 `locked`(`locks`: 막은 잠금들) — 하나라도 막히면 아무것도 잡지 않고 풀지도 않습니다.
- 422 `too_many_locks`(한 사람 20개), `bad_request`(이름 모양: `i:` + 항목 id 또는 `g:` + 1~64자의 `A-Za-z0-9_-`).
- 규칙은 8절.

### 6.6 쓰기 — `POST <방>/items`

```json
{ "epoch": 1, "writes": [
  { "id": "<새 id>", "kind": "plan", "baseRev": 0, "cipher": "A…", "group": "<선택>" },
  { "id": "<있는 id>", "kind": "plan", "baseRev": 7, "cipher": "A…" },
  { "id": "<있는 id>", "baseRev": 9, "delete": true }
] }
```

- `id`: `A-Za-z0-9_-` 8~64자. 무작위 16바이트의 base64url(22자)을 권합니다. `member-`로 시작하는 id는 참여자 카드만 씁니다.
- `baseRev`: 만들기는 0, 고치기·지우기는 내가 가진 그 항목의 `rev`.
- `kind`는 만들 때 정해지고 바꾸지 못합니다(고칠 때도 같은 값을 보냅니다. AAD에 들어가므로).
- `group`(선택): 서버가 보는 불투명한 묶음 이름(8절). 고칠 때 빼면 그대로, `null`이면 묶음에서 뺍니다.
- 한 번에 1~50건, **전부 되거나 전부 안 됩니다.**
- 200: `{ "rev": <방의 새 rev>, "items": [ { "id", "rev", "seq", "updatedAt" } ] }` — 쓰기 하나마다 방 `rev`가 1씩 오릅니다.
- 409 `conflict`: `{ "conflicts": [ { "index", "id", "current": <최신 항목 또는 묘비 또는 null> } ], "rev" }`. 이미 있는 id로 만들기, 없는·지운 항목 고치기, `baseRev`가 최신이 아닌 경우입니다. 기기는 `current`를 풀어 사용자에게 보이고 다시 고치게 합니다.
- 검사 순서: 모양(422·413) → 세대(409 `epoch_mismatch`) → 권한(403)·마감(423 `settlement_closed`) → 잠금(423 `locked`, 그다음 `lock_required`) → 충돌(409) → 방 한도(413 `room_full`).
- 공지(`notice`)를 고치면 그 공지의 확인(`acks`)이 비워집니다(내용이 달라졌으므로 다시 확인받음).

### 6.7 공지 확인 — `POST <방>/acks`

`{ "id": "<공지 항목 id>" }` → 200 `{ "id", "acks": { "<번호>": <시각> }, "seq", "rev" }`. 여러 번 눌러도 처음 시각 그대로입니다. 공지가 아니거나 지워졌으면 404 `no_notice`.

### 6.8 나가기 — `POST <방>/leave`

204. 내 토큰은 그 뒤 403 `removed`입니다. 서버가 내 참여자 카드를 묘비로 바꾸고 내 잠금을 풉니다. 주인은 409 `owner_cannot_leave`.

### 6.9 비밀번호가 바뀐 뒤 다시 증명 — `POST <방>/rekey`

`{ "proof": "<새 비밀번호로 만든 증명>" }` → 200 `{ "epoch", "rev" }`. 참여 토큰은 그대로 씁니다. 틀리면 입장과 같은 횟수 제한을 받습니다(403 `wrong_password`·429 `join_locked`·`join_ip_limit`).

### 6.10 주인만 (참여자 1의 토큰 + `x-share-owner`)

| 경로 | 본문 | 응답 |
|---|---|---|
| `POST <방>/kick` | `{ "member": 3 }` | 200 `{ "ok": true, "member": 3, "rekeyRecommended": true }` · 404 `no_member` |
| `POST <방>/close` | `{ "closed": true }` (정산 마감) 또는 `false`(다시 열기) | 200 `{ "closed" }` |
| `POST <방>/expiry` | `{ "expiresAt": … }` | 200 `{ "expiresAt" }` · 422 `bad_expiry`(지금 + 1시간 ~ 만든 때 + 400일) |
| `POST <방>/rotate` | `{ "rev", "proof", "items": [ { "id", "cipher", "group"? } ] }` (15절) | 200 `{ "epoch", "rev" }` |
| `DELETE <방>` | 없음 | 204. 방의 모든 것이 지워짐 |

내보낸 사람은 그때까지의 내용을 이미 가지고 있고 링크와 비밀번호를 압니다. 다시 들어오지 못하게 하려면 **내보낸 뒤 비밀번호를 바꿔야 합니다**(`rekeyRecommended`). 앱은 내보내기 뒤에 비밀번호 바꾸기를 권하는 화면을 냅니다.

### 6.11 실시간 — `GET <방>/ws`

WebSocket 업그레이드. 헤더 `Authorization: Bearer <token>`(iOS는 `URLRequest`에 헤더를 넣어 `webSocketTask(with:)`). 7절.

## 7. WebSocket

- 주소: `wss://<서버>/share/rooms/<roomId>/ws`. 한 참여자에 연결 2개까지, 세 번째가 붙으면 가장 오래된 것이 닫힙니다(4003).
- 메시지는 모두 JSON 글자입니다. 64KB를 넘거나 바이너리면 닫습니다(1009).
- 살아 있는지 확인: 글자 `ping`을 보내면 글자 `pong`이 옵니다(JSON이 아님. 서버를 깨우지 않음). WebSocket 프로토콜의 ping 프레임도 됩니다.
- 붙자마자 서버가 `hello`를 보냅니다. 기기는 `hello.rev`가 내가 가진 것보다 크면 9절대로 따라잡습니다.

### 기기 → 서버

모든 요청에 `id`(숫자나 글자, 응답에 그대로 돌아옴)와 `op`를 넣습니다. 본문 칸은 HTTP와 같습니다.

| op | 칸 | HTTP의 같은 일 |
|---|---|---|
| `lock` | `acquire`, `release` | 6.5 |
| `write` | `epoch`, `writes` | 6.6 |
| `ack` | `notice`(공지 항목 id) | 6.7 |
| `changes` | `since`, `limit` | 6.4 |
| `state` | | 6.3 |

예: `{ "id": 12, "op": "lock", "acquire": ["i:<항목 id>"] }`, `{ "id": 13, "op": "ack", "notice": "<공지 항목 id>" }`.

응답: `{ "t": "res", "id": <요청의 id>, "status": 200, …HTTP 응답의 칸들 }`. 실패하면 `status`가 4xx이고 `error`와 HTTP와 같은 칸이 옵니다.
소켓에서는 `id`가 요청 번호이므로, HTTP 응답에 `id` 칸이 있는 `ack`의 응답에서는 그 칸이 빠집니다(`acks`·`seq`·`rev`만).
주인만 하는 일·입장·나가기·rekey는 소켓으로 받지 않습니다(HTTP로).

### 서버 → 기기

| `t` | 모양 | 언제 |
|---|---|---|
| `hello` | 6.3의 방 상태 전체 + `"t": "hello"` | 붙은 직후 |
| `items` | `{ "rev", "items": [항목…] }` | 누가 쓰거나 지움(나간 사람의 카드 묘비 포함) |
| `locks` | `{ "set": [ { "name", "by", "until" } ], "clear": ["이름"], "by", "now" }` | 누가 잡음·연장함·풂·끊겨서 풀림 |
| `ack` | `{ "id": <공지 id>, "by", "at", "seq", "rev" }` | 누가 공지를 확인함 |
| `member` | `{ "event": "join"\|"leave"\|"kick"\|"online"\|"offline", "no", "now" }` | 입장·퇴장·연결 상태 |
| `room` | `{ "closed", "expiresAt", "epoch", "now" }` (+ 키 교체 직후 주인에게만 `"rekeyed": true`) | 마감·기한이 바뀜 |
| `bye` | `{ "reason": "kicked"\|"left"\|"rekey"\|"deleted"\|"expired"\|"replaced" }` 뒤에 닫힘 | 아래 닫힘 코드 |

- 소켓으로 보낸 요청의 결과는 **보낸 소켓에는 응답으로만**, 나머지 모든 소켓에는 방송으로 갑니다. HTTP로 한 일은 연결된 모든 소켓(내 것 포함)에 방송됩니다.
- 방 `rev`를 올리는 방송은 `items`(항목 수만큼)와 `ack`(1)뿐이고 둘 다 올린 뒤의 `rev`를 싣습니다. 기기가 가진 방 `rev`에 그만큼을 더한 값과 방송의 `rev`가 다르면(사이가 비면) 따라잡기를 합니다.
- 닫힘 코드: 4000 내보내짐, 4001 비밀번호가 바뀜(→ 새 비밀번호를 받아 `rekey` 뒤 다시 붙음), 4002 방이 지워짐·기한 지남, 4003 다른 연결로 바뀜, 1009 너무 큰 메시지.

## 8. 잠금

잠금은 「이름 → 참여자 번호 + 기한(`until`)」입니다. 이름은 두 가지입니다.

- 항목 잠금 `i:<항목 id>`: 일정 하나, 지출 한 건을 고치는 동안.
- 묶음 잠금 `g:<묶음 이름>`: 순서 바꾸기처럼 한 날의 여러 항목을 함께 쓸 때. 묶음 이름은 기기가 정하는 불투명한 글자입니다. 날짜가 서버에 보이지 않게 `base64url(HMAC-SHA256(encKey, "group|" + 날짜)의 앞 12바이트)`처럼 만들기를 권합니다. 항목의 `group` 칸에 같은 이름을 넣어 「이 항목은 이 묶음에 든다」를 서버에 알립니다.

상태 기계(이름 하나):

```
비어 있음 ──잡기(A)──▶ A가 잡음(until = 지금 + 2분)
A가 잡음 ──A가 다시 잡기(연장)──▶ A가 잡음(until = 지금 + 2분)
A가 잡음 ──A가 풀기 / until 지남 / A의 마지막 연결이 끊김 / A가 나감·내보내짐 / 키 교체──▶ 비어 있음
A가 잡음 ──B가 잡기──▶ 423 locked (변화 없음)
```

- 잡기가 막히는 경우: 남이 그 이름을 잡고 있음. 항목 잠금은 그 항목의 묶음 잠금을 남이 잡고 있으면 막힘. 묶음 잠금은 그 묶음에 든 항목을 남이 하나라도 잡고 있으면 막힘.
- **쓰기와의 관계**: 잠금을 보는 종류는 `plan`과 `expense-shared`뿐입니다(여럿이 고칠 수 있는 것). 고치기·지우기는 내가 그 항목의 `i:` 잠금 **또는** 그 항목이 든 묶음의 `g:` 잠금을 잡고 있어야 합니다(없으면 423 `lock_required`). 만들기는 잠금이 필요 없지만, 남이 잡은 묶음 안에는 만들지 못합니다. 항목을 다른 묶음으로 옮길 때도 옮겨 갈 묶음을 남이 잡고 있으면 막힙니다.
- 임대는 2분입니다. 고치는 화면이 열려 있는 동안 **60초마다 다시 잡아** 연장하고, 닫으면 풉니다.
- 기한이 지난 잠금은 서버가 따로 알리지 않습니다. 기기는 받은 `until`(서버 시각)이 지나면 풀린 것으로 그립니다.
- 「끊기면 해제」는 그 참여자의 **마지막** WebSocket이 닫힐 때 일어납니다. 신호가 갑자기 사라지면 서버가 끊김을 늦게 알 수 있고, 그때는 2분 기한이 상한입니다. HTTP로만 잡은 잠금(연결 없음)은 기한으로만 풀립니다.
- 누가 무엇을 잡고 있는지는 `hello.locks`와 `locks` 방송으로 모두가 봅니다(참여자 번호 → 카드의 닉네임으로 「○○가 고치는 중」).
- 잠금을 잡은 뒤 쓰기가 409 `conflict`면 잡기 전에 남이 고친 것입니다. `current`로 화면을 바꾸고 다시 고칩니다. 잠금을 잡은 직후 그 항목의 최신 `rev`를 가지고 있는지(방송을 다 받았는지) 확인하면 이 경우가 줄어듭니다.

## 9. 따라잡기 절차

기기는 방마다 「내가 반영한 마지막 순번」 `cursor`를 저장합니다(처음은 0).

1. `GET <방>/changes?since=<cursor>`.
2. 받은 항목을 `seq` 순으로 반영합니다: 묘비면 그 id를 지우고, 아니면 `epoch`이 방의 세대와 같은지 보고 풀어서 넣습니다. 같은 id가 이미 있으면 `seq`가 더 큰 쪽이 이깁니다.
3. `cursor = next`. `more`면 1로.
4. 응답의 `closed`·`epoch`도 반영합니다.

- 화면을 열 때: `GET <방>`(또는 소켓의 `hello`) → `rev`가 `cursor`보다 크면 따라잡기 → 소켓 방송을 받기 시작. 소켓을 먼저 붙이고 따라잡는 동안 온 방송은 모아 두었다가 `seq`가 `cursor`보다 큰 것만 반영합니다.
- 방송이 비었다고 의심되면(순번이 건너뜀) 따라잡기를 합니다. 따라잡기는 몇 번 해도 같은 결과입니다.
- 409 `rekey_required`를 받으면 15절의 「다른 참여자」 절차로.
- 인터넷이 없으면 **보기만** 합니다(1차 기본값). 기기에 저장한 마지막 내용을 보여 주고 고치기는 막습니다. 오프라인 편집을 쌓아 두었다가 합치는 일은 하지 않습니다.

## 10. 권한 표

| kind | 무엇 | 만들기 | 고치기 | 지우기 | 잠금 |
|---|---|---|---|---|---|
| `plan` | 일정 하나(시간 칸) | 누구나 | 누구나 | 누구나 | 필요 |
| `expense-shared` | 공유 지출(정산에 들어감) | 누구나, **마감 전만** | 누구나, 마감 전만 | 누구나, 마감 전만 | 필요 |
| `expense-own` | 개인(공개) 지출 | 누구나 | **만든 사람만** | 만든 사람만 | 없음 |
| `notice` | 공지 | 누구나 | 만든 사람만 | 만든 사람·주인 | 없음 |
| `member` | 참여자 카드(닉네임 등). id는 `member-<내 번호>` 하나 | 본인만 | 본인만 | 못 함(나가면 서버가 묘비로) | 없음 |
| `meta` | 여행 정보·예산·정산 설정·앱 없는 일행 이름 | 주인만 | 주인만 | 주인만 | 없음 |

- 「만든 사람」은 서버가 기억하는 `createdBy`(참여자 번호)입니다. 서버는 암호문 안의 「쓴 사람」을 모르므로 이것으로 강제합니다.
- 「주인」은 참여자 1입니다(`meta` 쓰기는 주인 열쇠 없이 참여자 1의 토큰으로 됩니다. 소켓으로도 쓸 수 있게).
- 공유 ↔ 개인을 바꾸려면 kind가 바뀌므로 **지우고 새로 만듭니다**(새 id).
- 개인(비공개) 지출은 서버에 올리지 않습니다.
- 「내 지출 전부 공유」 스위치는 기기의 설정입니다(켜면 새 지출을 `expense-shared`로 올림). 여행 기본값은 `meta`에 둡니다.
- 송금 완료 표시는 보낸 사람의 `member` 카드 안에 둡니다(본인만 쓰므로 마감과 상관없이 고칠 수 있음).

## 11. 공지와 확인

- 공지는 `notice` 항목입니다. 글·시각 칸(「3시까지」)·장소는 암호문 안에 있습니다.
- 확인은 `acks`(6.7)이고 서버가 압니다: **누가 어떤 공지 id를 언제 확인했는지**. 내용이 아니므로 서버가 알아도 되는 최소 사실로 두었습니다. 보낸 사람은 `acks`와 `GET <방>`의 `members`를 견줘 누가 아직인지 봅니다.
- 다시 알리기(확인 안 한 사람에게 한 번 더, 시각 전에 다시)는 **기기의 로컬 알림**으로 합니다: 공지를 받은 기기가 확인 전이면 스스로 알림을 예약합니다.
- 화면을 닫고 있을 때 받는 길(푸시)은 **이번에 넣지 않았습니다.** 이유와 설계안:
  - 지금 푸시 기기 토큰은 사용자마다의 `UserState`에 그 사용자의 키로 잠겨 있어, 다른 참여자가 공지를 올릴 때 서버가 꺼낼 수 없습니다. 방에서 보내려면 방이 참여 기기의 APNs 토큰을 **서버가 읽을 수 있게** 가져야 하고, 그러면 계정 없는 참여자를 기기 식별자로 방에 묶게 됩니다.
  - 설계안(대표 결정 뒤 구현): 참여자가 원할 때만 `PUT <방>/push`로 `{ token, env }`를 올림 → 방 DO가 Worker 비밀값에서 만든 키로 잠가(AAD = 방 id + 참여자 번호) 둠 → `notice`가 새로 생기면 올린 사람을 뺀 참여자에게 `{"aps":{"alert":{"loc-key":"PUSH_TRIP_NOTICE"},"sound":"default","content-available":1},"k":"notice"}`만 보냄(내용·방 id 없음) → 앱이 깨어나 열려 있는 방들을 따라잡음. 간격 제한(방마다 분당 몇 건), 나가기·내보내기·만료 때 토큰 삭제, APNs 비밀값이 없으면 아무것도 안 함(기존 `src/apns.js`의 `configured`·`sendPush` 재사용).
  - 그때까지는 화면이 열려 있을 때(소켓)와 앱을 열 때(따라잡기)만 공지를 받습니다.

## 12. 가계부·정산의 1차 기본값

- 인터넷이 없으면 보기만.
- 주인이 정산을 마감(`close`)하면 공유 지출 쓰기를 서버가 거절(423 `settlement_closed`). 마감 여부는 서버가 아는 방 상태입니다. 주인이 다시 열 수 있습니다.
- 예산은 공유 하나(`meta` 안).
- 앱 없는 일행은 주인이 이름만 더합니다(`meta` 안의 명단. 서버는 못 읽음).
- 정산 계산은 기기에서 공유 지출만으로 하고, 같은 입력이면 모두 같은 결과가 나오게 정렬 기준(항목 id 순)을 고정합니다. 「정산 안 함」 여행은 `meta`의 값입니다.

## 14. 만료와 지우기

- 방은 `expiresAt`(여행 끝 + 30일 권장)에 서버 알람으로 통째로 지워집니다. 기한이 지난 방은 알람이 늦어도 첫 요청에서 지워지고 404가 됩니다.
- 주인은 `POST <방>/expiry`로 늘리거나 줄일 수 있습니다(만든 때 + 400일까지).
- 주인의 `DELETE <방>`은 바로 모든 것을 지웁니다. 지운 뒤에는 방이 있었다는 흔적도 남지 않습니다(그래서 404).
- 기기는 404를 「지워졌거나 기한이 지난 방」으로 보고 여행을 공유 안 함 상태로 돌립니다. 여행이 끝나면 각자 일정과 공유 가계부를 자기 앱에 저장해 두므로(앱 단계) 방이 사라져도 잃는 것이 없어야 합니다.
- 주인 열쇠를 잃으면(주인 기기 분실·삭제) 지우기·내보내기·비밀번호 바꾸기를 못 하고, 방은 기한에 지워집니다.

## 15. 비밀번호 바꾸기 = 키 교체

주인 기기:

1. 따라잡기를 끝까지 해서 모든 살아 있는 항목을 가지고, 방의 `rev`를 적어 둡니다.
2. 새 비밀번호(원하면 새 `linkSecret`도)로 3절대로 새 `encKey`·`proof`를 만듭니다.
3. 살아 있는 **모든** 항목을 새 키와 새 세대(`epoch + 1`)의 AAD로 다시 잠급니다. 날 묶음 이름(8절, 키로 만든 HMAC)을 쓰는 항목은 새 키로 이름을 다시 만들어 `group`에 넣습니다(TSR1117A01).
4. `POST <방>/rotate` `{ "rev": <1의 rev>, "proof": <새 증명>, "items": [ { "id", "cipher", "group"? } … ] }`. `group`(선택, 8절의 모양)이 있으면 서버가 그 항목의 묶음 이름을 바꾸고, 없으면 그대로 둡니다(이 칸을 모르는 서버는 무시하므로 이름이 옛 키에 남습니다).
   - 409 `conflict`(`rev`): 그 사이 누가 썼음 → 1부터 다시.
   - 422 `incomplete`(`missing`, `extra`): 살아 있는 항목과 목록이 맞지 않음. 422 `same_proof`: 비밀번호가 그대로임.
5. 200 `{ "epoch", "rev" }`. 서버가 한 번에 바꿉니다: 모든 항목의 암호문·세대, 입장 검증값, 세대 +1, 모든 잠금 해제, 입장 실패 수 초기화. 항목마다 `rev`·`seq`가 새로 매겨지고 만든 사람·확인 기록은 그대로입니다.
6. 새 비밀번호를 일행에게 알립니다(새 `linkSecret`을 썼다면 새 링크도).

다른 참여자:

- 연결이 4001로 닫히거나 요청이 409 `rekey_required`를 받습니다. 「비밀번호가 바뀌었어요」 화면에서 새 비밀번호를 받아 키를 다시 만들고 `POST <방>/rekey`. 성공하면 `cursor = 0`으로 처음부터 따라잡습니다(모든 암호문이 바뀌었으므로).
- 내보내진 사람은 `rekey`도 못 합니다(토큰이 403 `removed`). 새 비밀번호를 모르면 다시 입장하지도, 이후 내용을 풀지도 못합니다.

## 16. 위협 모델 — 서버가 아는 것과 모르는 것

서버가 **모르는 것**: 계획·지출·공지의 내용, 닉네임, 누가 얼마를 썼는지, 날짜(묶음 이름을 권한 대로 만들면), 링크 비밀 값, 비밀번호, 암호화 키, 주인 열쇠·참여 토큰·입장 증명의 원래 값(요청을 처리하는 순간에만 메모리에 있고 SHA-256만 저장), 방을 만든 앱 등록 키가 어느 방의 주인인지.

서버가 **아는 것**: 방 id, 만든 때·기한, 참여자 번호와 수·입장 시각·연결 여부, 항목 id·kind·묶음 이름·암호문 크기·`rev`/`seq`·고친 시각·고친 참여자 번호·만든 참여자 번호, 잠금(누가 어느 이름을), 공지 확인(누가 어느 공지를 언제), 마감 여부, 세대, 입장 실패 수. 요청의 IP는 Cloudflare가 보지만 방에 저장하지 않습니다(IP 하루 수는 해시된 이름의 별도 카운터). 서버 코드는 로그를 쓰지 않습니다.

막는 것:

- 서버 저장소가 새어도 내용은 못 읽고, 검증값만으로는 입장·주인 행세를 못 합니다.
- 링크만 얻은 사람: 비밀번호가 필요합니다. 온라인 대입은 방 단위 5번/15분 + IP 하루 60번으로 막고, 오프라인 대입은 서버에서 `proof`의 해시를 훔쳐야만 가능하며 그 경우에도 링크 비밀 값(256비트)이 없으면 못 합니다. 링크**와** 서버 저장소를 함께 얻은 공격자에게는 PBKDF2 60만 번이 남은 방어입니다.
- 참여자의 권한 밖 쓰기(남의 개인 지출·남의 카드·meta·마감 뒤 공유 지출)는 서버가 거절합니다.
- 암호문을 다른 항목·종류·세대·방으로 옮기는 것은 AAD로 드러납니다.

막지 못하는 것(받아들인 위험):

- **참여자는 내용을 모두 읽습니다.** 내보내도 이미 본 것은 되돌릴 수 없고, 비밀번호를 바꾸기 전에는 링크와 비밀번호로 다시 들어올 수 있습니다.
- 참여자가 계획·공유 지출을 망가뜨리는 것(권한 안의 쓰기). 서버는 고친 참여자 번호만 남깁니다.
- 악의적인 서버는 항목을 숨기거나, 예전 암호문을 다시 주거나, 순서·확인 기록·잠금을 속일 수 있습니다(읽거나 새 내용을 지어낼 수는 없음). 누가 썼는지(`by`)도 서버가 붙이는 값입니다. 암호문 안에도 쓴 사람의 참여자 번호를 넣어 두면 앱이 어긋남을 알아챌 수 있습니다.
- 링크를 아는 사람은 틀린 증명을 반복해 입장을 15분씩 잠글 수 있습니다(이미 들어온 사람은 영향 없음).
- 크기·시각·횟수로 활동을 짐작하는 것.

## 17. 무료 요금제에서 드는 양(어림)

Cloudflare 문서(2026-11 확인): Durable Objects 무료 요금제는 요청 하루 10만, SQLite 행 쓰기 하루 10만·읽기 하루 500만. 들어오는 WebSocket 메시지는 20건을 요청 1건으로 셉니다. 잠든(hibernation) 연결은 시간 요금이 없고, `ping`→`pong` 자동 응답은 과금되지 않습니다.

- HTTP 요청 하나 = 방 DO 요청 1(입장·rekey는 IP 카운터 +1, 방 만들기는 기존 인증 1 + 카운터 2 + 방 1).
- 소켓 연결 1번 = 요청 1. 소켓 메시지 20건 = 요청 1.
- 행 쓰기: 항목 쓰기 1건 ≈ 4행(항목, 순번 색인 넣기·빼기, 방 상태). 잠금 잡기·풀기 = 1행. 공지 확인 = 4행.
- 어림: 10명이 하루에 화면을 20번씩 열고(연결 200 + 따라잡기 200), 300건을 고치면(잠금·쓰기·풀기 900메시지 ≈ 요청 45, 행 약 1,800) **방 하나에 하루 요청 약 450, 행 쓰기 약 2,000**.
- 그래서 무료 한도에서 빠듯한 쪽은 행 쓰기입니다: 이 정도로 활발한 방이 **하루 약 50개**면 10만 행에 닿습니다(기존 기능이 쓰는 몫은 별도). 요청은 약 200개 방까지. 쓰는 방이 그보다 늘면 유료 전환이 필요합니다.
- 앱이 지킬 것: 고치기는 소켓으로(HTTP보다 20배 쌈), 잠금 연장은 60초에 한 번, 글자를 칠 때마다 쓰지 말고 칸 편집을 마칠 때 한 번 쓰기.

## 19. 앱 구현 체크리스트

키·저장

- [ ] `roomId`(16바이트)·`linkSecret`(32바이트)·`ownerKey`(32바이트)를 `SecRandomCopyBytes`로 만든다.
- [ ] 3절의 유도를 구현하고 `share-vectors.json`의 두 벡터(root·encKey·authKey·proof·cipher)를 단위 시험으로 맞춘다. 비밀번호는 NFC로 정규화한다.
- [ ] `root`(또는 `encKey`)·`token`·`ownerKey`·`linkSecret`은 키체인(이 기기에서만)에. 비밀번호 자체는 저장하지 않는다.
- [ ] 암호문: 버전 바이트 0x01, 무작위 nonce, AAD(방·항목·종류·세대), 평문 JSON `"v":1` + 64바이트 배수 패딩. 풀리지 않는 항목은 버린다.

흐름

- [ ] 만들기: 앱 등록 키로 `POST /share/rooms` → 토큰 저장 → 자기 카드(`member-1`)와 `meta` 올림 → 링크(`#roomId.linkSecret`) 공유, 비밀번호는 따로.
- [ ] 입장: 링크 열기 → 비밀번호 입력 → `join` → 403 `remaining`·429 `retryAfter`·409 `room_full`(「인원이 찼어요」)를 각각 보여 줌 → 닉네임 입력 → `member-<번호>` 카드 올림.
- [ ] 참여한 여행에는 「공유 만들기」를 내지 않는다(참여자는 다시 공유하지 못함).
- [ ] 화면을 열면 소켓 연결 + 따라잡기(9절), 닫으면 내 잠금을 풀고 연결을 닫는다. 30~60초마다 ping.
- [ ] 칸을 고치기 시작할 때 `lock` → 60초마다 연장 → 끝나면 `write` 뒤 `release`. 423 `locked`면 「○○가 고치는 중」.
- [ ] 순서 바꾸기: 그 날의 `g:` 잠금을 잡고 바뀐 항목들을 한 번의 `write`로(전부 되거나 전부 안 됨).
- [ ] 409 `conflict`: `current`를 풀어 화면을 바꾸고 사용자가 다시 고치게.
- [ ] 다른 사람의 잠금·연결 상태·입퇴장을 방송(`locks`·`member`)으로 그린다. `until`이 지난 잠금은 풀린 것으로.
- [ ] 공지: 받으면 확인 버튼 → `ack`. 확인 전이면 로컬 알림 예약. 보낸 사람 화면에 확인한 사람·아직인 사람.
- [ ] 가계부: 공유는 `expense-shared`, 개인(공개)은 `expense-own`, 비공개는 올리지 않음. 마감(`closed`)이면 공유 지출 입력을 막고 423도 처리.
- [ ] 주인: 내보내기 → 「비밀번호를 바꿀까요?」 → 15절. 정산 마감·다시 열기. 기한 늘리기. 방 지우기(되돌릴 수 없음 확인).
- [ ] 4001·409 `rekey_required`: 새 비밀번호 입력 → `rekey` → 처음부터 따라잡기.
- [ ] 403 `removed`·404: 공유가 끝났음을 알리고 로컬 사본은 남긴다.
- [ ] 인터넷이 없으면 보기만.
- [ ] 429는 `retryAfter` 뒤에만 다시. 503 `unavailable`이면 공유 기능을 숨긴다.
- [ ] 로그·분석에 링크·비밀번호·토큰·닉네임을 남기지 않는다.

### 기기 쪽 패키지를 만들며 정한 것 (2026-11-15)
- 소켓에서 모르는 `op`는 `400 unknown_op`입니다(5절 표에 더해 읽습니다).
- `meta` 항목의 id는 `trip-meta` 하나입니다.
- 정산은 지출의 원화 환산 칸(`amountKRW`)이 있으면 그 값으로, 없으면 원래 금액·통화로 계산합니다. 나눌 사람(`split`)은 만들 때의 사람을 명시하고, 비어 있으면 낸 사람 혼자의 몫입니다. 나머지 1원은 항목 id 순·사람 순(참여자 번호 → 앱 없는 일행)으로 나눕니다.
- 키 교체 응답이 끊기면 주인 기기는 `GET <방>`의 세대로 됐는지 확인합니다(새 뿌리 키는 부르기 전에 임시로 저장).
- 키 교체의 성공 기준은 서버가 받아 준 것(`rotate` 200 또는 확인한 세대)입니다. 그 뒤의 따라잡기가 끊겨도 성공이고, 따라잡기는 연결 고리가 처음부터 다시 합니다(TSR1117A01, 설계 `docs/reviews/REV1117A01.md`).
- HTTP만 되는 참여자는 키 교체를 다음 요청의 `409 rekey_required`로 압니다.
- 정할 것: 주인 기기가 풀지 못한 항목이 있을 때의 키 교체. 지금 패키지는 멈추고(`unreadableItems`), 주인이 고르면 받은 암호문을 그대로 다시 올려 자리만 지킵니다.

## 20. 배포 메모

- 새 Durable Object 클래스 `ShareRoom`(바인딩 `SHARE_ROOM`, migration 태그 `v2-share-room`)이 `server/trip-relay/wrangler.toml`에 들어 있습니다. 저장소에 없는 `wrangler.local.toml`에도 같은 줄을 더해야 배포됩니다. 바인딩이 없으면 `/share/…`는 503 `unavailable`이고 기존 경로는 그대로입니다.
- 기존 경로·`UserState`는 바뀌지 않았습니다(방 만들기 수를 세는 데 기존 `countDaily`만 씀).
- 새 비밀값은 없습니다.
- 확인한 것(2026-11-14): `npm test`(가짜 저장소·가짜 소켓으로 핸들러 직접 호출)와, 로컬 Workers 런타임(`npx wrangler dev`, wrangler 4.162.0)에서 실제 WebSocket으로 만들기·입장·`hello`·`ping`/`pong`·소켓 쓰기와 방송·잠금과 거절·HTTP 쓰기의 방송·끊김 때 잠금 해제·따라잡기·키 교체·지우기(4002로 닫힘)·20초 쉰 뒤의 요청. 확인하지 못한 것: 운영 환경 배포, 실제 알람 발화(기한 삭제는 시험에서 `alarm()`을 직접 부름), iOS `URLSessionWebSocketTask`와의 왕복.

## 21. 여행 중 동행 위치 (LOC1116S01)

설계와 이유는 `docs/TRIP_LIVE_LOCATION_PLAN.md`. 이 절은 통신 형식의 정본입니다. **서버는 좌표를 읽지 못합니다**(방 키로 종단 암호화). 이력을 쌓지 않고, 암호화된 마지막 1건만 짧게 둡니다.

### 21.1 암호문

4절과 같은 형식. AAD만 다릅니다.

```
AAD = UTF8("taption-share-v1|" + roomId + "|loc-" + 참여자 번호 + "|loc|" + epoch)
키  = encKey
```

평문(UTF-8 JSON, 64바이트 배수 공백 패딩):

```json
{ "v": 1, "s": "ok", "lat": 37.5, "lon": 127.25, "acc": 10, "at": 1765000000000 }
```

| 칸 | 뜻 |
|---|---|
| `s` | `ok`(공유 중) · `hide`(잠깐 숨김) · `help`(도와주세요) · `off`(끔). `hide`·`off`에는 좌표가 **없어야** 하고 `ok`·`help`에는 있어야 합니다 |
| `lat`·`lon` | 도(°). 위도 −90~90, 경도 −180~180 |
| `acc` | 수평 정확도(m, 0 이상) |
| `at` | 측정 시각(보낸 기기 시계, ms). 「몇 분 전」은 서버가 받은 시각으로 잽니다 |
| `note` | `help`에만, 40자까지 |

경로·속도·활동·건강·배터리는 싣지 않습니다. 암호문 상한 **512바이트**. 풀리지 않거나 모양·범위가 틀리면 버립니다.

### 21.2 기간 창

주인이 `POST <방>/locwindow` `{ "from", "until" }`(ms, 서버 시각, `until − from` ≤ 40일, `until` > 지금, 주인 열쇠 필요)로 위치를 보낼 수 있는 기간을 올립니다. 앱은 기본으로 **여행 시작일 0시 ~ 종료일 24시(여행지 시간대)**를 올리고 주인이 바꿀 수 있습니다. **창이 없거나 창 밖이면 서버는 위치를 모두 거절합니다**(403 `loc_closed` + `locWindow`). 창을 지금이 아닌 쪽으로 바꾸면 저장된 위치를 모두 지우고 `{ "t": "loc", "off": true, "all": true }`를 방송합니다. 창은 `GET <방>`의 `locWindow`, `hello`, `room` 방송에 실립니다(없으면 `null`). 서버가 여행 날짜 두 개를 알게 되지만 방의 `expiresAt`(여행 끝 + 30일 권장)으로 이미 대략 알려진 값입니다.

### 21.3 보내기

| 경로 | 본문 | 응답 |
|---|---|---|
| `PUT <방>/loc` | `{ "epoch", "cipher", "help": false }` | 200 `{ "now" }` |
| 소켓 `{ "id", "op": "loc", "epoch", "cipher", "help" }` | 같음 | `{ "t": "res", "status": 200, "now" }` |
| `DELETE <방>/loc` | 없음 | 204. 내 저장된 위치를 지우고 `{ "t": "loc", "by", "off": true }` 방송 |
| `GET <방>/loc` | 없음 | 200 `{ "locs": [ { "by", "cipher", "epoch", "at", "help"? } ], "locWindow", "now" }` |

오류: 403 `loc_closed`, 409 `epoch_mismatch`, 413 `item_too_large`, 422 `bad_cipher`·`bad_request`, 429 `loc_rate`(+`retryAfter`).

한도: 참여자마다 **5초에 1건**(도움 요청 제외)·분당 20건. 위치는 방 `rev`·`seq`·잠금·따라잡기에 섞이지 않습니다.

### 21.4 받기

- 방송 `{ "t": "loc", "by", "cipher", "epoch", "at", "help"? }`: `at`은 서버가 받은 시각. 보낸 소켓에는 가지 않습니다. 끔·지움은 `{ "t": "loc", "by", "off": true }`.
- `hello`에 `"locs": [ … ]`(21.3의 `GET`과 같은 모양)와 `"locWindow"`가 실립니다. 서버가 둔 동행의 마지막 위치를 열자마자 받습니다.
- 받은 위치는 **메모리에만** 둡니다(저장·이력 없음). 5분 넘으면 흐리게, 15분 넘으면 「오래전 위치」, 30분 넘으면 「연락 끊김?」으로 보입니다.

### 21.5 서버의 보관

참여자마다 암호문 **1건**을 덮어씁니다: 일반 10분, 도움 요청(`help: true`)은 24시간 또는 그 사람이 보통 위치를 보낼 때까지. 저장은 사람마다 90초에 한 번(방송은 매번)만 합니다. 기한이 지난 행은 읽을 때와 함께, 아무도 접속하지 않아도 그 기한에 맞춘 서버 알람으로 지웁니다(TSR1117A01). 나가기·내보내기·키 교체·기간 창 변경·방 지우기·만료 때, 그리고 `DELETE`로 지웁니다. 키 교체 뒤에는 옛 키로 잠근 위치를 버립니다. 서버가 아는 것: 누가 언제 위치 메시지를 보냈는지(번호·시각·크기), `help` 여부(불리언), 기간 창. `SHARE.locKeep`을 `false`로 하면 저장 없이 전달만 합니다.

### 21.6 모이는 곳 (`meet`)

항목 종류 `meet`, id는 **`meet-point` 하나**. 누구나 만들고 고칠 수 있고(충돌은 `baseRev`로 6.6과 같이), **지우지 못합니다**(지운 id는 다시 못 쓰므로 「해제」 내용으로 덮어씀). 위치 기간 창 안에서만 올릴 수 있습니다(403 `loc_closed`). 평문: `{ "v": 1, "on": true, "name": "…", "lat", "lon", "at": 모이는 시각(ms, 선택) }`. 잠금은 보지 않습니다.

**기간이 끝나면 서버가 거둡니다**(REV1117A01, 대표 결정 2026-11-17). 위치 기간 창의 끝(`locWindow.until`)이 지나면 서버가 `meet-point`를 묘비(`deleted`)로 바꾸고 암호문을 지웁니다. 기간마다 한 번이고, 알람을 창 끝에 맞춰 두어 아무도 접속하지 않아도 거두며(`nextAlarm`), 알람보다 요청이 먼저 오면 그 요청이 거둡니다. 묘비는 `items` 방송과 `changes`(`since` > 0)로 동행에게 가고, 동행 앱은 평소 삭제처럼 지도에서 지웁니다. 지운 `meet-point`는 **새 기간 창 안에서 `baseRev: 0`으로 다시 만들 수 있습니다**(다른 id와 달리 이 id만 허용, id 개수는 다시 세지 않음). 앱의 「해제」(`on: false`)는 좌표·이름·시각을 비운 내용(`ShareMeetContent.cleared`)으로 덮어씁니다.

### 21.7 시험 벡터

`server/trip-relay/test/fixtures/share-loc-vector.json`(Swift `ShareLocationTests.testSealedLocationMatchesTheFixedVector`가 만든 값을 Node `share-loc-vector.test.mjs`가 같은 AAD로 풀어 견줌). 서버는 암호문을 풀지 않으므로 서버 시험은 모양·한도·기간 창·보관·삭제를 봅니다.

### 21.8 배포 메모

새 Durable Object·비밀값 없음. 기존 `ShareRoom`에 경로·소켓 op·kind `meet`가 더해집니다. 옛 앱은 `loc`·`meet`를 모르고 무시합니다(`meet`는 `unsupported`). 푸시(도움 요청·끊김 알림)는 APNs 키와 11절의 기기 토큰 저장이 있어야 하며 이번에 넣지 않았습니다.
