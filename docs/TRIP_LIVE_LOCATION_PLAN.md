# 여행 중 동행 실시간 위치 공유 설계 (LOC1116S01)

대표 생각(2026-11-16): 친구들이 같은 여행을 함께 고치고 지출·정산을 나누는 데 더해, **각자 자유 시간을 보낸 뒤 모일 때 서로의 현재 위치를 보고, 불의의 사건·사고에 대비하는 것**. 그리고 「딱 여행 갔을 때만」.

이 문서는 설계입니다. 통신 형식의 정본은 구현 뒤 `docs/TRIP_SHARE_PROTOCOL.md` 21절에 옮깁니다. 상태: **구현 완료(서버·패키지·앱), 서버 배포 전, 실기기 확인 전**. 서버 배포 전, 실기기 두 대 확인 전.

## 1. 현재 상태 조사 (2026-11-16, 코드 기준)

### 1.1 여행 공유가 어디까지 되어 있나

| 층 | 있는 것 | 위치 |
|---|---|---|
| 규약 | 방·키 유도(PBKDF2→HKDF)·AES-GCM 암호문(AAD = 방·항목 id·kind·세대)·HTTP·WebSocket·권한 표·한도·키 교체 | `docs/TRIP_SHARE_PROTOCOL.md` 1~20절 |
| 서버 | Durable Object `ShareRoom`. 항목(kind: plan·expense-shared·expense-own·notice·member·meta)·잠금·공지 확인·참여자·키 교체·만료 알람. 소켓은 hibernation(`acceptWebSocket`)이고 방송은 `broadcast()` | `server/trip-relay/src/share.js` |
| 패키지 | 키·암호문·전송·세션(소켓+따라잡기)·내용 모양(`ShareContent`)·정산 | `Packages/TaptionTripShare` |
| 앱 | 창구 `TripShareStore`, 키체인 `TripShareKeychain`, 곁 파일, 화면(만들기·입장·참여자·공지·정산·상태 띠) | `TaptionPlan/Core/TripShare*.swift`, `TaptionPlan/UI/TripShare*.swift` |
| 배포 | 서버 배포·빌드 344 업로드까지 끝남(`temp.md` TSH1114A26 진행). 두 기기 실기기 확인은 남음 | |

- **위치는 없음**: 규약 18절 「하지 않은 것」에 친구 위치 공유가 있고, 서버는 모르는 kind를 거절한다. 장소는 이름만 올리고 좌표는 올리지 않는다(대표 결정 2026-11-15).
- **앱이 백그라운드일 때**: 소켓은 화면이 열려 있는 동안만 유지(규약 9절)하고, 화면을 닫으면 끊긴다. 푸시가 꺼져 있어 닫힌 동안의 알림은 다음에 앱을 열 때까지 늦다(규약 11절). 서버 쪽 APNs 코드(`src/apns.js`)는 있으나 **비밀값 `APNS_KEY_P8`·`APNS_KEY_ID`·`APNS_TEAM_ID`가 아직 설정되지 않았다**(`temp.md` PSH1114A06: P6 전에 APNs 키). 설정 전에는 `sendPush`가 아무것도 보내지 않는다. 방의 참여 기기 토큰 저장(규약 11절 설계안 `PUT <방>/push`)은 구현되지 않았다.
- 여행 정보 `meta`(주인이 올림)에 `startDay`·`endDay`(날짜 글자)·`timeZone`(IANA)이 있다 → 여행 기간 판단에 쓴다.
- 참여자 카드 `member-<번호>`에 닉네임과 색이 있다 → 지도 표시의 머리글자·색에 쓴다.

### 1.2 앱이 위치를 받는 방식

- `UIBackgroundModes`에 `location`·`fetch`·`remote-notification`이 이미 있고, 위치 권한은 「항상 허용」을 요청한다(`AppleSensorCollector.swift`: `requestAlwaysAuthorization`). **새 권한 창은 만들지 않는다.**
- 수집은 하나의 `CLLocationManager`(`AppleSensorCollector`)가 맡는다. 앞 화면 실시간 모드는 거리 필터 5~15m·정확도 Best/10m(`ForegroundLiveLocationPolicy`), 기록 중에는 활성 거리 필터, 평소(균형)는 움직이면 10m·멈추면 50m·`pausesLocationUpdatesAutomatically`, 절전은 500m. 큰 폭 이동(`startMonitoringSignificantLocationChanges`)도 쓴다. 최신 한 점은 `latestLocation`.
- 결론: **위치 공유를 위해 새 GPS 세션을 켜지 않는다.** 수집기가 이미 받는 위치를 한 점씩 받아 보내기만 한다. 그래서 배터리 추가분은 통신뿐이다.

### 1.3 여행 지도에 사람 표시를 얹을 자리

- `TravelStreetMap`(`UIViewRepresentable`, MapLibre `MLNMapView`)은 `pins`·`route`·`actor`(화랑이)를 받아 `MLNAnnotation`으로 그린다. 호출은 `TravelModeView.streetMap(_:_:)` 한 곳.
- 얹는 방법: `TravelStreetMap`에 `companions: [TravelCompanionMark] = []`·`meetPoint`를 **기본값이 있는 매개변수**로 더하고, 그림은 새 파일 `TravelCompanionLayer.swift`(주석 클래스·뷰 만들기·갱신)가 맡는다. `TravelStreetMap.swift`와 `TravelModeView.swift`에는 연결 몇 줄만 넣는다(다른 세션이 이 파일들을 고치는 중).
- 상태 띠 자리: `TravelModeView`의 `TripShareStatusBand`·`TripShareNoticeBand` 옆(794줄 근처)에 「위치 공유 중」 띠를 같은 방식으로 더한다.

## 2. 범위와 원칙

1. **누구에게**: 같은 공유 여행(방)의 구성원에게만. 방 밖에는 어떤 경로로도 좌표가 가지 않는다.
2. **언제**: 그 여행의 시작일 0시 ~ 종료일 24시(**여행지 시간대**, `meta.timeZone`)에만. 끝나면 자동으로 꺼진다. 대표 결정으로 앞뒤 여유 없음(14절).
3. **누가 켜나**: 여행마다·사람마다 **본인이** 켠다. 주인도 남의 것을 켤 수 없다.
4. **무엇을**: 위도·경도·정확도(m)·측정 시각·상태(공유·숨김·도움 요청)만. **경로 이력·속도·활동 분류·건강 자료·배터리는 보내지 않는다.**
5. **서버는 읽지 못한다**: 좌표는 기존 방 키(`encKey`)로 종단 암호화한 덩어리로만 간다.
6. **여행 밖에서는 아무것도 안 나간다**: 기기가 기간 밖이면 보내지 않고(1차 방어), 서버도 주인이 알려 준 기간 창 밖의 위치 메시지를 거절한다(2차 방어, 4.3).
7. **앱이 약속하는 것은 iOS가 실제로 허용한 만큼**: 앱이 꺼졌거나 iOS가 위치 갱신을 안 주면 갱신되지 않는다. 안 되는 것을 되는 것처럼 보이지 않는다(4.4·6.3).

## 3. 동의와 화면 표시

- 상태: `꺼짐 / 켜짐 / 잠깐 숨김(until)`. 여행마다·기기마다 로컬(곁 파일)에 저장한다. 서버·동행에게 「켜짐」 여부 자체를 따로 올리지 않는다(켜면 위치가 가므로 그 자체가 신호).
- **기본값**: 대표 결정: 꺼짐(14절). 어느 쪽이든 최초 켤 때 한 번 **동의 시트**를 띄운다: 누구에게 보이는지(이 여행 동행 N명), 언제까지(여행 마지막 날 끝), 무엇이 가는지(현재 위치·정확도), 서버는 못 읽음, 언제든 끌 수 있음. 위치기반서비스 약관 동의 화면은 신고 뒤에 이 시트에 붙인다(11절).
- **멈춤**: 여행 화면의 띠에서 한 번에: 「끄기」, 「1시간 숨기기」, 「이 여행 끝날 때까지 숨기기」. 숨기는 동안은 **좌표를 보내지 않고** 서버의 내 마지막 위치도 지운다. 동행 화면에서는 끈 것과 같이 내 표시가 사라진다(숨김과 끔을 서로 구분해 알리지 않는다). 끄기·숨기기는 서버에 저장된 내 마지막 위치도 지운다(`DELETE`, 4.2).
- **항상 보이는 표시**: 공유 중이면 여행 화면 위쪽 띠에 「내 위치 공유 중 · 동행 N명에게 · 끄기」. 지도의 내 점 옆에도 작은 표시. 홈·잠금 화면 표시(Live Activity)는 이번에 넣지 않는다.
- 여행이 끝나면(기간 창 종료) 앱이 열려 있든 아니든 다음 틱에서 꺼짐으로 돌리고, 「위치 공유가 끝났어요」를 한 번 보인다.

## 4. 통신 설계

### 4.1 서버에 마지막 위치를 둘지 — 두 안과 권고

| | A. 전달만(아무것도 안 둠) | B. 암호화된 마지막 위치만 짧게 둠 |
|---|---|---|
| 저장 | 없음. 지금 소켓이 붙은 동행에게만 방송 | 참여자마다 암호문 1건을 덮어씀(지난 것은 남지 않음). 만료 10분, 도움 요청은 24시간 또는 해제 때까지 |
| 새로 연 동행 화면 | **빈 지도.** 상대가 다음에 보낼 때까지 모름 | `hello`에 실려 와 **열자마자 「3분 전」 위치가 보임** |
| 앱이 닫힌 동행 | 그 사람이 보낸 위치가 사라짐 | 마지막 위치가 남아 있어 「어디서 끊겼는지」 확인 가능 |
| 도움 요청 | 그때 연결된 사람만 받음. 놓치면 끝 | 나중에 연 사람도 받음 |
| 서버가 아는 것 | 위치 메시지가 오가는 시각·크기·보낸 번호 | 위에 더해 **암호문이 얼마나 오래 남는지**. 내용은 못 읽음 |
| 비용 | 행 쓰기 0 | 행 쓰기가 늘어남(아래) |
| 법적 위험 | 중계도 신고 대상으로 봄(`AI_RELAY_PLAN.md` 위치정보법 검토) → **두 안 같음** | 같음 |

권고: **B**. 이유: 대표가 든 두 쓰임(모일 때 다들 어디쯤인지, 사건·사고 대비)이 모두 「내가 화면을 연 순간에 이미 와 있는 값」을 필요로 한다. A에서는 상대 앱이 백그라운드여서 보내지 못하면 아무것도 안 보이고, 사고 때의 마지막 위치는 남지 않는다. 서버가 암호문 하나를 덮어쓰며 짧게 두는 것은 좌표를 읽을 수 없다는 점에서 A와 읽기 가능성이 같고, 이력은 쌓이지 않는다. B의 비용은 행 쓰기: 한 사람이 90초에 한 번만 저장(방송은 매번)하게 하면 10명이 12시간 쓸 때 방 하나에 하루 약 4,800행이다. 무료 하루 10만 행이면 활발한 방 약 20개까지 — 여행은 드문 이벤트라 우선 무료로 가고, 넘으면 유료 전환(규약 17절과 같은 방식).
A로 가야 하는 이유가 생기면(예: 법무 검토에서 「저장」이 걸림) 서버 코드의 저장 줄 하나만 끄면 된다(소켓 방송은 같고, `hello`의 `locs`만 빈다). 그래서 구현은 B를 켜고 끄는 스위치(`SHARE.locKeep`)로 둔다.

### 4.2 새 메시지 (규약 21절로 옮길 초안)

암호문 형식은 규약 4절과 같다. AAD만 다르다.

```
AAD = "taption-share-v1|<roomId>|loc-<참여자 번호>|loc|<epoch>"
```

평문(UTF-8 JSON, 64바이트 배수 공백 패딩):

```json
{ "v": 1, "s": "ok", "lat": 0.0, "lon": 0.0, "acc": 12, "at": 1765000000000, "note": "<도움 요청만, 40자 이내>" }
```

- `s`: `ok`(공유 중) · `hide`(잠깐 숨김, 좌표 없음) · `help`(도와주세요, 좌표 있음) · `off`(끔, 좌표 없음)
- `at`: **측정 시각**(기기 시계, 밀리초). 받는 쪽이 서버 `now`로 보정해 「몇 분 전」을 계산한다.
- 암호문 상한 **512바이트**.

HTTP (인증은 규약 5절의 참여 토큰):

| 경로 | 본문 | 응답 |
|---|---|---|
| `PUT <방>/loc` | `{ "epoch": 1, "cipher": "A…", "keep": true }` | 200 `{ "now" }` · 403 `loc_closed`(기간 창 밖) · 409 `epoch_mismatch` · 413 `item_too_large` · 429 `loc_rate` |
| `DELETE <방>/loc` | 없음 | 204. 내 저장된 위치를 지우고 `loc` 방송(`off`) |
| `POST <방>/locwindow` (주인만) | `{ "from": 0, "until": 0 }` (밀리초, `until - from` ≤ 40일) | 200 `{ "from", "until" }`. 기간 창 설정 |

WebSocket:

- 기기 → 서버: `{ "id": 5, "op": "loc", "epoch": 1, "cipher": "A…" }` → 응답 `{ "t": "res", "id": 5, "status": 200, "now": 0 }`. 소켓에서는 `keep`을 서버가 정한다(마지막 저장이 90초 전보다 오래되었거나 `s`가 `help`일 때, 서버는 `s`를 읽을 수 없으므로 **`keep` 칸을 기기가 정하고** 서버는 최소 간격 90초만 강제한다 — 도움 요청은 `help: true` 칸을 별도로 둬 90초 간격에서 제외).
- 서버 → 기기: `{ "t": "loc", "by": 2, "cipher": "A…", "epoch": 1, "at": 0 }` (`at`은 서버 시각). 보낸 소켓은 제외, 같은 참여자의 다른 소켓에도 보낸다. `hello`에 `"locs": [ { "by", "cipher", "epoch", "at", "help" } ]`를 더한다(B안). `DELETE`·내보내기·나가기·키 교체 때는 `{ "t": "loc", "by": 2, "off": true }`.
- 서버가 알게 되는 것: 누가 언제 위치 메시지를 보냈는지(횟수·시각·크기), 도움 요청 여부(`help` 칸은 평문 불리언이라 서버가 안다. 이유는 푸시·보관 시간 구분을 서버가 해야 해서), 기간 창. 내용(좌표·정확도·상태·메모)은 못 읽음.

### 4.3 서버 검사 (2차 방어)

- 주인이 `locwindow`를 올리기 전에는 `loc` 메시지를 **모두 거절**한다(`403 loc_closed`). 기본값이 「닫힘」이어서, 위치 기능이 없는 옛 앱·옛 방은 영향이 없다.
- 창 밖 거절. 창은 `meta`의 기간(시작일 0시~종료일 24시, 여행지 시간대)으로 주인 기기가 계산해 올리고, 여행 날짜를 바꾸면 다시 올린다. 서버가 여행 날짜를 알게 되는 셈이지만 방의 `expiresAt`(여행 끝 + 30일 권장)으로 이미 대략 알려진 정보이고 창은 시각 두 개뿐이다. 문서에 적는다.
- 한도: 참여자마다 **5초에 1건**·분당 20건(위치 전용 카운터, 기존 분당 240건 한도와 별개로 둠), 암호문 512바이트, 방당 저장 10건, 도움 요청 메모 포함 같은 한도. 규약 13절에 더한다.
- 내보내기·나가기·키 교체(`rotate`)·방 지우기·만료 알람: 저장된 위치를 모두 지운다. **키 교체 뒤에는 옛 키로 잠근 위치를 새 키로 다시 잠글 수 없으므로 버린다** (다음 보내기에 채워짐).
- 위치 암호문은 항목(`items`)이 아니므로 방 `rev`·`seq`·잠금·정산·따라잡기에 섞이지 않는다.

### 4.4 보내기 주기와 배터리

수집기가 이미 주는 위치 한 점을 받아 아래 조건일 때만 보낸다(`TripLiveLocationPolicy`, 순수 함수로 시험).

| 상황 | 보내는 조건 |
|---|---|
| 앞 화면, 움직임 | 앞 전송에서 **20m 이상 움직이고 15초 이상** 지남 |
| 앞 화면, 멈춤 | 5분마다 「아직 여기」 한 번 |
| 뒤(백그라운드), 움직임 | iOS가 위치를 줄 때만. **60초 이상, 50m 이상** |
| 뒤, 멈춤 | iOS가 주는 갱신이 없으면 안 보냄 |
| 정확도가 나쁨(`acc` > 200m) | 보내지 않음(마지막 값 유지, 받는 쪽에서 오래됨으로 보임) |
| 기간 밖·꺼짐·숨김 | 보내지 않음 |

- 앞 화면은 소켓으로, 소켓이 없거나 백그라운드는 HTTP `PUT <방>/loc`(위치 갱신을 받은 짧은 실행 시간 안에 끝냄, 실패하면 버리고 다음 값으로 — 지난 좌표를 쌓아 두지 않음).
- 앞 화면 15~30초 간격은 대표 요청 범위이고 정확한 값은 기기 확인 후 조정한다.
- **iOS가 허용하는 것**: 「항상 허용」+`location` 백그라운드 모드에서 위치 갱신 이벤트가 오면 앱이 잠깐 실행된다. iOS가 `pausesLocationUpdatesAutomatically`로 멈추거나 사용자가 앱을 강제 종료하면 이벤트가 끊길 수 있다(큰 폭 이동 모니터링으로 되살아나는 경우만 예외이고 기기 확인 필요). 그래서 「뒤에서도 계속」이 아니라 **「iOS가 위치를 줄 때 보냅니다」**라고만 쓴다.

### 4.5 받는 쪽

- 복호화 실패(키·세대 불일치)·`at`이 미래(+2분 초과)·좌표 범위 밖·여행 기간 창 밖인 것은 버린다.
- 표시: 「3분 전」(서버 시계로 보정한 `at`), 정확도 원(`acc`), **5분 넘게 없으면 흐리게**, **15분 넘으면 「오래전 위치」 회색 + 시각**, 도움 요청은 빨강.
- 받은 위치는 **메모리에만** 둔다(앱을 닫으면 사라짐, 디스크·SQLite에 쓰지 않음). 이력을 만들지 않고 줄을 이어 그리지 않는다.
- 내 위치는 서버로 갔다 오지 않고 수집기의 값을 그대로 쓴다.

## 5. 지도 화면

- **동행 표시**: 머리글자(닉네임 첫 글자) 원 + 참여자 카드의 색, 아래에 「3분 전」. 눌러서 「거리 · 방향」 한 줄과 상세(정확도).
- **모이는 곳 핀**: 누구나 지도에서 길게 눌러 「여기서 모여요」로 정하고 시각을 붙일 수 있다(한 여행에 하나, 나중에 정한 것이 이긴다). 새 항목 종류 `meet`(평문: 이름·좌표·시각·정한 사람)로 **암호화해 방에 저장**(항목이라 따라잡기·묘비·권한 표를 그대로 씀. 정한 사람과 주인만 지움). 이것은 이 기능이 처음 올리는 「좌표가 든 항목」이므로 여행 기간 규칙의 적용 대상이다(기간 창 밖에는 못 올림, 끝나면 자동 소멸).
- 각 동행 카드: **직선 거리**와 **걸어서 대략 몇 분**(직선 거리 ÷ 도보 4.5km/h, 「대략」 표기). 길찾기 서비스에 좌표를 보내지 않는다.
- 오래 갱신 없는 사람: 5분 넘으면 흐리게, 15분 넘으면 회색 + 「마지막 확인 12:41」, 30분 넘으면 「연락 끊김?」 표지(도움 요청 흐름은 6절).
- 「모두 보이게」 단추: 동행들과 내 위치가 다 들어오게 지도를 맞춤(기존 `fitKey`에 동행 수를 더함).

## 6. 사건·사고 대비

### 6.1 「도와주세요」 단추

- 여행 화면에서 **두 번 눌러야** 가는 단추(오발 방지: 누르고 3초 취소 가능). 누르면 현재 위치를 `s: "help"`로 보내고 B안이면 서버가 24시간(해제 때까지) 둔다. 동행 화면에는 빨간 띠로 「○○님이 도움을 요청했어요 · 3분 전 · 지도에서 보기」와 현재 위치.
- 켜 놓지 않았거나 기간 밖이어도 도움 요청은 **여행 중에는 항상 보낼 수 있음**(공유가 꺼져 있는 사람이 급할 때 쓰는 것이므로, 누를 때 「이 위치를 동행 N명에게 보냅니다」를 한 번 확인). 기간 밖에는 못 보냄.
- 해제: 보낸 사람이 「괜찮아졌어요」를 누르면 지움·방송.

### 6.2 끊김 알림

- 기기 쪽(1차 가능): 앱이 열려 있는 동안, 공유 중이던 동행의 마지막 위치가 30분 넘게 갱신이 없으면 지도에 「연락 끊김?」 띠(알림음 없음).
- 서버 쪽(**푸시 필요**): 앱이 닫혀 있어도 알리려면 서버가 마지막 수신 시각을 보고 알람을 울려 APNs 푸시를 보내야 한다.

### 6.3 안 되는 것 — 분명히 적는다

- **앱이 완전히 꺼졌거나, iOS가 위치 갱신을 멈췄거나, 통신이 없으면 위치는 오지 않는다.** 마지막으로 닿은 위치만 남는다.
- **푸시가 아직 켜지지 않았다**(APNs 키 미설정). 그래서 지금은 **동행이 앱을 열었을 때만** 도움 요청이 보인다. 닫혀 있는 동행의 폰은 울리지 않는다. 서버 쪽 끊김 알림도 못 한다. 푸시를 켜려면 ① APNs 키(대표) ② 방의 기기 토큰 저장(`PUT <방>/push`, 규약 11절 설계안, 사용자 계정 없는 참여자를 기기 식별자로 방에 묶는 것이 걸림) ③ 알림 문구 번역이 필요하다. 이번 구현에는 넣지 않는다(대표 결정 전).
- **긴급 신고(112·119·현지 번호)를 대신하지 못한다.** 앱 안에 이 문구를 도움 요청 단추 아래와 동의 시트에 상시 표시한다. 단추는 동행에게 알리는 것이지 구조 기관에 연락하는 것이 아니다.
- 서버가 중단되거나 방이 지워지면(주인이 지움·만료) 공유는 끝난다.

## 7. 보안·개인정보 정리

- 위협 모델은 규약 16절과 같다. 더해지는 것: **동행은 서로의 현재 위치를 안다**(그것이 기능). 공유를 끈 뒤에도 이미 본 것은 되돌릴 수 없다. 내보낸 사람은 새 키가 되면 이후 위치를 못 푼다(비밀번호 교체 권고는 기존 그대로).
- 서버 저장소가 새어도 위치 암호문은 못 읽는다. 서버는 「누가 몇 시에 위치를 보냈는가」(참여자 번호·시각)는 안다. IP는 기존처럼 저장하지 않는다.
- 로그·분석에 좌표·닉네임을 남기지 않는다. 진단 기록에는 「위치 공유 켜짐/꺼짐」 횟수만(좌표·여행 이름 없음).
- 위치는 `latestLocation`과 별개의 변수에 복사하지 않는다(보낼 때만 읽음). 받은 위치는 메모리에만.
- **자동 센서 원본·provenance 보존 원칙과의 관계**: 동행에게 보내는 위치는 기록 데이터가 아니라 일회성 전달이다. 수집기의 원본 저장 경로(SQLite·provenance)는 바꾸지 않는다. 받은 동행 위치는 기록하지 않는다.

## 11. 약관·개인정보처리방침 문구 초안

> 이 절은 `PRIVACY.md`·`TERMS.md`(다른 작업이 수정 중)와 충돌하지 않게 초안으로만 둔다. 법적 판단이 아니며 **위치정보법·개인정보 보호법 검토가 필요**하다(AI_RELAY_PLAN의 검토 메모: 중계만 해도 위치기반서비스사업 신고 대상으로 본다는 전달 내용이 있고, 신고 전에는 이 기능을 켜지 않는다. 조문은 이 저장소에서 확인한 것이 아니다).

**수집 항목**: 여행 동행 위치 공유를 켠 경우에 한해, 이 기기의 현재 위치(위도·경도), 위치의 정확도, 측정 시각, 공유 상태(공유 중·숨김·도움 요청).

**누구에게 보이는가**: 같은 공유 여행에 참여 중인 동행에게만. 앱 개발자·서버 운영자는 내용을 읽을 수 없습니다(기기에서 암호화되어 전달되며 서버에는 해독 키가 없습니다).

**언제**: 본인이 여행마다 켠 동안, 그 여행의 시작일부터 종료일까지(여행지 시간대)에만. 종료 시 자동으로 꺼집니다.

**보관**: 서버는 동행에게 전달하기 위해 암호화된 마지막 위치 1건을 최대 10분(도움 요청은 최대 24시간) 보관하고 덮어쓰며, 이력은 남기지 않습니다. 끄기·나가기·방 삭제·여행 종료 시 즉시 삭제합니다. 앱은 받은 동행 위치를 기기 메모리에만 두고 저장하지 않습니다.

**끄는 법**: 여행 화면의 「내 위치 공유 중」 띠에서 끄기·1시간 숨기기. 위치 권한을 끄거나 동행에서 나가도 중단됩니다.

**한계**: 앱·통신 상태에 따라 위치가 늦거나 오지 않을 수 있고, 긴급 신고를 대신하지 않습니다.

**위치정보 이용·제공 사실 기록**(법 검토 후 확정): 누가·누구에게(그 여행 참여자 수)·언제 제공했는지의 시각·횟수만 서버에 남기고 좌표는 남기지 않는다는 설계는 `AI_RELAY_PLAN.md`에 있음. 이번 구현에는 서버가 이미 아는 값(참여자 번호·시각)을 넘는 별도 기록을 만들지 않았다 — 법 검토에서 필요하다고 하면 추가.
