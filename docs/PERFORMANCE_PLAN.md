# 성능 측정·개선 계획 (PRF1116A01)

대표 지시(2026-11-16): 「성능관점에서 최적화 진행하자. 아이폰 11로 성능 테스트 및 벤치마킹 진행.」

앱이 느린 곳을 아이폰 11 Pro에서 수치로 재고, 영향이 큰 것부터 고치고, 전후를 같은 방법으로 다시 잰다. 동작·화면 모습·저장 형식·백업 형식은 바꾸지 않는다. 구조 쪽 이전 수치는 `docs/STRUCTURE_PERFORMANCE.md`, 저장소 쪽은 `docs/DATA_PIPELINE.md`에 있다.

## 측정 조건

| 항목 | 값 |
| --- | --- |
| 기기 | 아이폰 11 Pro(60Hz 화면), USB 연결, 대표의 실제 기록이 들어 있는 상태 그대로 |
| 판 | Release(최적화 켬, whole-module) + `-D BENCH`(측정 훅만 켬), 개발 서명, `xcrun devicectl`로 설치·실행 |
| 실행 | `devicectl device process launch --console --terminate-existing com.taption.plan -- <인자>` — 앱이 찍는 `PRFBENCH` 줄(숫자만)을 받는다 |
| 횟수 | 항목마다 3회 이상. 가운데 값과 범위(최소~최대)를 적는다 |
| 개인 정보 | 기록 내용·좌표·장소 이름은 로그·문서에 남기지 않는다. 행 수와 시간만 남긴다 |
| 섞지 않는 것 | 시뮬레이터·Debug 수치는 기기·Release 수치와 같은 표에 넣지 않는다 |

측정 도구: `MapHomePerfBench`(`TaptionPlan/UI/MapHomeInteractionMonitor.swift`, `#if DEBUG || BENCH`). 화면 틱 간격은 기존 `MapHomeInteractionMonitor`(표시 링크, 측정 중에만 돎)로, CPU는 스레드·프로세스 CPU 시계로, 메모리는 `task_vm_info`의 `phys_footprint`와 최고치로 잰다. 받는 스크립트는 `scripts/perf-bench.sh`.

XCTest 성능 지표(`XCTApplicationLaunchMetric` 등)와 `xctrace`는 쓰지 않았다. 앱에 이미 손짓별 틱 계측과 자동 실행 훅이 있어 같은 수단으로 이전 기록(`LGS1115A01`, `PRF1030A02`)과 이어 볼 수 있고, 화면 시험 실행기를 기기에 따로 올리지 않아도 되기 때문이다. 함수별 원인을 볼 때만 `xctrace`(Time Profiler)를 쓴다.

## 잴 항목과 합격선

60Hz 화면이라 한 프레임은 16.7ms다. 「끊긴 프레임」은 틱 간격이 20ms를 넘은 것(한 프레임 이상 놓침), 「크게 끊긴 프레임」은 40ms를 넘은 것이다.

| # | 항목 | 방법 (`PRFBENCH` 이름) | 합격선(가운데 값) |
| --- | --- | --- | --- |
| 1 | 콜드 실행 → 홈 첫 화면 | 프로세스 시작 시각(`sysctl`)부터 홈이 「준비됨」을 알릴 때까지(`launch ready_ms`), 오늘 하루 자료가 다 읽힐 때까지(`launch day_loaded_ms`). 실행마다 앱을 끝내고 다시 띄운다 | 준비 3,000ms 이하 |
| 2 | 대기 상태 CPU | 첫 화면 뒤 25초 기다린 다음 10초씩 3번, 손대지 않고 프로세스 전체·메인 스레드 CPU 시간(`idle`) | 전체 CPU 10초에 1,500ms(15%) 이하 |
| 3 | 날짜 바꾸기 | 어제·그제·그끄제를 차례로 고르고(처음), 같은 세 날을 다시 고른다(다시). 고른 순간부터 그날 자료가 「읽음」이 될 때까지(`date_cold`·`date_warm`의 `loaded_ms`), 4초 동안 메인 CPU, 3초 동안 틱 간격(`bench_date_*`) | 처음 1,000ms, 다시 300ms 이하. 크게 끊긴 프레임 3 이하 |
| 4 | 시간 끌기 | 어제를 고른 채 화면 틱마다 고른 분을 옮긴다(3초에 하루 왕복, 6초씩 3번, `bench_scrub`). 사이드바의 손짓 판정은 거치지 않고 그 뒤 화면 갱신만 잰다 | 6초에 342프레임(95%) 이상, 크게 끊긴 프레임 0 |
| 5 | 지도 끌기 | 기존 `-autoBenchMapPan`(프레임마다 지도를 좌우로 밀기, 12초씩 3번, `bench_pan`). 기기에 저장된 지도 스타일 그대로 | 12초에 648프레임(90%) 이상, 크게 끊긴 프레임 2 이하 |
| 6 | 가계부·여행 화면 열기 | 화면을 4번씩 여닫는다. 연 순간부터 첫 틱까지(`first_ms`), 1.5초 동안 최대 틱 간격·메인 CPU(`bench_open_ledger_*`, `bench_open_travel_*`). 처음(cold)과 다시(warm)를 나눈다 | 다시 열기: 최대 간격 50ms 이하, 끊긴 프레임 3 이하 |
| 7 | 하루 재생 | 기존 `-autoStartDayPlayback -autoPlaybackYesterday`(`playback_frame_stats`: 틱 수, 20ms 넘는 틱, 최대) | 20ms 넘는 틱 5% 이하 |
| 8 | 메모리 | 위 순서를 다 돈 뒤 `phys_footprint`와 최고치(`memory`) | 최고치 500MB 이하 |
| 9 | 기록이 많은 날의 시간표 계산 | 3번의 날짜별 행 수(`rows`)와 `main_cpu_4s_ms`. 행 수가 가장 많은 날을 본다 | 4초 동안 메인 CPU 1,200ms 이하 |

못 재는 것: 손가락 핀치 줌(자동 줌 훅이 Apple 지도 집 근처 단계 축소뿐이라 일반 줌은 재지 않음), 사이드바 손짓 판정 자체, 120Hz 동작(이 기기는 60Hz), 이동 중 GPS가 들어오는 상태.

## 분석

### 1차 측정(2026-11-16 07:45~08:03, 참고용)

기준 커밋 `4a9ecb26`의 Release + BENCH 판으로 종합 측정 2회(첫 회차는 다른 실행과 겹쳐 받지 못함)와 재생 3회를 쟀다. 이때 Mac 부하가 높아 메인 세션 공지에 따라 기준값으로 쓰지 않고 재개 뒤 다시 잰다. 그래도 어디가 느린지는 분명하다(가운데 값).

- **시간 끌기 측정을 고쳤다.** 1차 측정은 「끄는 중」(`isTimelineInteractionActive`)을 켜지 않고 8ms마다 분을 바꿨다. 실제 손짓은 끄는 동안 지도 이동을 60Hz로 묶는 경로를 타는데, 측정은 한 번 누를 때의 경로(`refreshSelectedTimelineMapPosition`)를 프레임마다 두 번씩 돌렸다. 손짓의 `onInteractionChanged`와 같은 일을 하는 `setScrubbing`을 넣고 화면 틱(16ms)마다 바뀔 때만 분을 쓰게 했다. 고친 측정도 154프레임으로 1차(149)와 비슷해, 시간 끌기가 실제로 느린 것이다.
- **Time Profiler는 못 썼다.** `xctrace record --device`가 「기기 부팅 대기 시간 초과」로 끝났고, `xctrace list devices`가 아이폰 11 Pro를 오프라인으로 본다(`devicectl` 설치·실행은 정상). 대신 화면 조각을 하나씩 빼는 측정(`-benchHide=`)과 본문 계산 횟수(`body_<이름>`)로 갈랐다.

### 조각 빼기 측정(기준 판, 각 3회)

| 뺀 것 | 대기 메인 CPU(10초) | 시간 끌기 프레임 | 지도 끌기 프레임 |
| --- | --- | --- | --- |
| 없음(기준) | 3,556ms | 154 | 367 |
| 지도 위 표지 층(overlay) | 160~228ms | 256~269 | 457~462 |
| 오른쪽 줄 전체(rails) | 3,000~3,700ms | 339~350 | 717~718 |
| 시간 막대(timebar)만 | 그대로 | 287~308 | 714~719 |
| 날씨·단추·왼쪽 위 | 그대로 | 187~198 | 381~403 |
| 모두 | 약 160ms | 355~356 | 721~737 |
| 시간 막대 유리 면(glass)만 · 구간(segments)만 · 눈금 글자(labels)만 | 그대로 | 132~156 | 354~376 |

- **대기 CPU는 지도 위 표지 층이 95%다.** 그 안에서 계속 움직이는 것은 화랑이(30Hz Canvas + CGContext), 집 고양이(24Hz), 집 하늘(24Hz)이다. Canvas를 메인 스레드에서 CPU로 그리는 몫을 줄이려 지도 위 표지만 비동기로 그리게 했다(고침 2).
- **지도 끌기는 CPU가 아니라 합성 쪽이다.** 기준에서 프레임당 메인 CPU는 약 10ms(3,534ms/367)인데 프레임 간격은 약 33ms다. 지도 끄는 12초 동안 시간 막대 본문은 1~4번만 계산된다(`body_timerail`). 그런데도 시간 막대를 빼면 60fps가 된다. 막대 안의 유리 면·구간·글자를 하나씩 빼서는 바뀌지 않아, 막대 전체가 MapLibre 위에 겹쳐 합성되는 비용으로 본다(추측: 표본 없음).
- **시간 끌기는 메인 CPU가 막힌다.** 6초에 메인 CPU 약 4,950ms(83%). 홈 본문(`MapHomeView.body`)이 6초에 약 200번, 시간 막대 줄이 약 390번 다시 계산된다. 홈 본문은 분을 직접 읽지 않는다(`MapHomePlaybackProbe` 분 읽기 위치 0건). 끄는 동안 분이 바뀔 때마다 `focusMap`이 홈의 `@State`(`mapPosition`·`mapCameraRevision`·`appleViewportCommand`)를 쓰고 카메라 명령 진단 기록을 한 줄씩 남기는 것이 후보였다. 그 호출만 빼는 측정(`focus`)에서 홈 본문 200→14~17번, 프레임 154→222~250, 메인 CPU 약 5,000→3,000ms가 됐고, 진단 기록만 빼는 측정(`camlog`)은 차이가 없었다. 그래서 끄는 동안의 카메라를 홈 상태 없이 벡터 지도에 바로 놓게 했다(고침 3).

## 콜드 실행 (PRF1117A01, 2026-11-17 새벽)

대표 지시 「다 끝나면 합치고 성능 작업 진행해」. 판: main `4aa16489`(빌드 349) + 측정 도구, Release + BENCH, 아이폰 11 Pro. 같은 판에서 실행 인자로 번갈아 쟀다. 결과 `build/validation/PRF1117A01/`(git 무시 대상).

### 측정 도구

- `scripts/perf-launch.sh <UDID> <폴더> <회차> <이름=인자>...`: 콜드 실행만 잰다(`-autoBenchPerf -benchLaunchOnly`). 이름들을 회차마다 번갈아 돌리고 회차마다 맥 부하를 `load.txt`에 남긴다. 한 번에 약 10초.
- `PRFBENCH stage <단계>=<ms>`: 프로세스 시작부터 시작 게이트(`AppShellLaunchGateRecorder`)·앱 값 만들기·저장소 읽기·하루 자료 단계까지의 시각. `PRFBENCH repository`: 첫 읽기의 행 수·SQL 읽기·묶기·해석 ms·본문 MB와 종류별 행 수·KB(숫자만). `launch` 줄에 메인·전체 CPU와 열 상태도 남긴다.
- `-benchLaunchDaysAgo=1`: 어제를 고른 채 시작한다. 이른 아침에는 오늘 하루가 짧아(50~120행) 낮 측정(약 280행)과 비교가 안 돼, 어제(281행)로 맞췄다.
- 「설치 직후」: 설치하면 다음 한두 번의 첫 읽기가 디스크에서 읽혀 SQL 읽기가 270~470ms → 1,500~1,900ms로 늘었다. 오래 쉬었다 여는 실제 콜드 실행에 가까워 설치→실행을 한 회차로 따로 쟀다. 그 밖의 회차는 「연속」이다.

## 시즌 팩 콜드 실행 (LAG1120A01, 2026-11-20)

대표 신고: 시즌(산타) 팩이 적용된 뒤 앱을 켜면 많이 버벅인다. 아이폰 11 Pro, Release+BENCH 개발 서명 판(TestFlight 아님)으로 같은 판에서 팩 켬/끔을 번갈아 쟀다. 팩 켬 경로는 서버 카탈로그 일정(자연 날짜)이고, 시험용 날짜 인자는 켬 쪽에 쓰지 않았다.

| 항목 | 팩 끔 | 팩 켬(수정 전) | 팩 켬(수정 후) |
|---|---|---|---|
| 콜드 실행(ms, 같은 판 번갈아) | 약 2,400 | 약 2,220 | 재지 않음(전에 차이 없음) |

- 원인: 눈꽃송이 층. 조각을 하나씩 빼 보면 눈꽃을 빼는 것만 끔 수준으로 내려가고, 화랑이·아이콘 층은 영향이 없었다. 매 프레임(24Hz) SwiftUI Canvas가 가지 18개짜리 송이를 전부 다시 그리고 있었다.

- 수정: 송이를 Core Animation 레이어로 옮겼다(떨어짐·흔들림·돌기를 반복 애니메이션으로 걸고 렌더 서버가 움직임). 그림은 크기 칸(0.5pt)별로 한 번만 만들어 나눠 쓴다. 모양·색·크기·떨어지는 식은 전과 같고(`track`이 식의 한 곳), 팩 날짜·첫 등장 시각은 바꾸지 않았다.
- 한계: ① 수정 전 값은 이전 실행 묶음, 수정 후 값은 다른 시각의 묶음이라 절대값(끔 1,700 → 2,774)이 기기 상태로 흔들렸다. 같은 묶음 안의 켬−끔 차이(수정 전 +1,000ms, 수정 후 −100ms)만 비교 근거다. ② 아이폰 18 Pro Max(120Hz)에서는 확인하지 못했다. ③ 지도를 끄는 동작의 끊김은 따로 번갈아 재지 않았다.
