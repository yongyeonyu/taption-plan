## 2. 발견 1 — 위젯 딥링크가 배포본에서 전부 죽어 있다

딥링크의 유일한 진입점은 `AppShellView.swift:77` 의 `onOpenURL` → `handleOpenURL` 이다. 그 함수의 첫 줄이 이렇다:

```swift
private func handleOpenURL(_ url: URL) {
    guard Self.legacyUIEnabled else { return }   // :574
    ...
}
```

`legacyUIEnabled` 는 `false` 다(`:7`). 즉 **URL이 들어오면 즉시 반환한다.** 알림 경로(`handlePlanNotification`, `:582`)도 같은 guard를 갖는다.

그런데 나머지는 전부 준비되어 있다:

| 요소 | 상태 |
|---|---|
| URL 스킴 등록 | `Info.plist:34` ✅ |
| 위젯이 보내는 링크 | `.widgetURL(taptionplan://…)` (`TaptionPlanWidget.swift:2425`, `:3791`), `Link(destination:)` (`:390`) ✅ |
| 링크 생성 헬퍼 | `deepLinkURL(payload:at:)` (`:324`) ✅ |
| 링크 처리 로직 | `AppModel.openDeepLink` (`:2861`) ✅ 이미 작성됨 |
| **연결** | **❌ guard 하나가 끊고 있다** |

**정확히 무슨 일이 일어났는가.** 이것은 "잊고 안 만든 기능"이 아니다. `legacyUIEnabled = false` 는 지도 우선으로 갈 때 **의도적으로** 넣은 스위치다. 그 스위치를 넣으면서, 그 스위치가 지키던 것 중 **딥링크 라우팅까지 같이 껐다.** 위젯은 계속 `taptionplan://` 를 쏘고, 앱은 계속 무시한다. 두 결정이 서로 모르는 채로 남아 있는 상태다.

**처방** guard를 실제 라우팅으로 교체한다. `taptionplan://today|sensor|cats|plan/<id>` 를 `MapHomeView` 가 이미 가진 상태(`isCalendarPresented` / `isDaySummaryPresented` / 섹션 선택 / `model.selectedDate`)로 매핑하면 된다. `AppModel.openDeepLink` 를 그대로 재사용한다. `handlePlanNotification` 도 같이.

**규모** 약 20줄. **선행 조건 없음.**

> 이 항목은 원래 문서에서 "흐름 D"로 분류되어 있었다. 그 분류가 이 결함의 무게를 크게 깎아 놓았다. **별도 항목으로 올린다.**

## 3. 발견 2 — 타이포그래피: 코드가 말하는 크기와 실제 크기가 다르다

`Theme.swift:17-21`:

```swift
static func taption(size: CGFloat, weight: Font.Weight = .regular) -> Font {
    .system(size: size + 2, weight: weight)   // 9를 쓰면 11이 된다
}
```

621곳이 이 함수를 쓴다. **코드를 읽는 사람은 실제 크기를 알 수 없다.** 우리 첫 기준선이 "27개 자간"이라고 적은 것도 이 때문이다 — 사람이 쓴 값 27종을 센 것이고, 실제로 렌더되는 값은 41종이다.

| 항목 | 실측 |
|---|---:|
| `.system(size:)` 호출 | 506 (리터럴 488 · 계산값 18) |
| `.taption(size:)` 호출 | 621 (리터럴 589 · 계산값 32) |
| **폰트 호출 합계** | **1,127** |
| **실제 렌더 자간** | **41종** |
| **11pt 미만 호출** | **300 (27.9%)** |
| Dynamic Type 지원 | **0** (`@ScaledMetric`·`relativeTo:` 전무) |

**처방** 41 → 12 토큰. 한글은 같은 크기에서 라틴보다 약 1.7배 넓으므로(음절 advance 0.865em) 한글에 10pt를 쓰지 않는다. 숫자 전용 토큰 3개를 따로 두어 `45m` / `6:12` 같은 라틴 숫자만 10pt를 허용한다.

**함정 (반드시 지킬 것):** 계산된 자간은 스크립트로 못 바꾼다. 총 50개 매칭 중 1개는 함수 정의 자체(`Theme.swift:21`)이고, **29개는 죽은 화면 안**이다. 실제로 손봐야 하는 것은 **활성 코드 20곳**이고, 그중 `MapHomeLocationPresentation.swift` 의 7곳(`size * 0.42` · `0.30` · `0.21` …)은 **이미 상대 스케일 체계**다. 리터럴만 일괄 치환하면 지도 라벨 위계가 조용히 평탄해지고, **테스트는 하나도 실패하지 않는다.**

## 4. 발견 3 — 대비: 본문 크기에서 기준 미달

WCAG 상대휘도로 재계산했다. **크기 조건을 함께 봐야 한다** — 14pt 이상 bold는 "large text"라 3:1 기준이 적용된다.

| 색 / 상황 | 대비 | 판정 |
|---|---:|---|
| `tpSecondary #7A6C50` on `tpBackground #F3EAD6` | **4.29** | ❌ 이미지·스크림과 무관하게 기본 바탕에서 미달 |
| `tpSecondary #6B5D43` (개정안) on `tpBackground` | 5.36 | ✅ |
| `tpAccent #C65D4D` 위 흰 글자, **13pt 이하** | **4.14** | ❌ |
| `tpAccent` 위 흰 글자, **14pt 이상 bold** | 4.14 | ✅ large text 3:1 통과 |
| NLE 헤더 `닫기` (`tpReferenceRose`) | **2.67** | ❌ |
| NLE 헤더 `적용` (흰 글자 on `tpReferenceBlue`) | **4.14** | ✅ (large text) / ❌ (본문) |

**정확히 말하면:** "모든 실底 버튼이 미달"은 과장이다. 14pt bold 이상은 통과한다. 미달하는 것은 **본문 크기의 흰 글자**이고, 실제 사례가 있다 — 클립 제목이 `MapHomeNLEClipEditor.swift:452` 에서 **9pt bold 흰 글자**로 포화된 클립 위에 얹힌다. 9pt는 large text가 아니므로 4.5가 적용되고, 통과하지 못한다.

`tpSecondary` 건은 **우리가 새로 발견한 것이 아니다.** `DESIGN_SYSTEM.md:68` 이 이미 `4.29` 를 적고 "on `tpBackground` 做正文 금지"로 못박아 뒀다. 본 보고서가 추가하는 것은 **범위**다: 이것이 공유 카드 이전에 앱 전역의 문제이고, 따라서 개정이 취향이 아니라 적합성 수정이라는 점.

**공유 카드 (`MapHomeCalendarSheet.swift:2509-2600`)** — 유일하게 **공개 게시되는** 면이라 편차가 영구적으로 남는다. 배경은 사용자 사진이 아니라 `Self.routeMap(points:)`(`:2782`)가 그린 **경로 지도 스냅샷**이고, 위에 `tpBackground` 72% 스크림을 덮는다. 지도가 어두우면(위성·야간 스타일):

| 지도 바탕 | 스크림 결과 | `tpInk` | `tpSecondary` (현행) |
|---|---|---:|---:|
| 순수 검정 | `#AFA89A` | 5.23 | **2.17** |
| 진회색 | `#BDB7A8` | 6.18 | **2.57** |
| 흰색 | `#F6F0E1` | 10.87 | 4.52 |

**스크림으로는 못 고친다** — alpha 1.00(지도를 완전히 덮음)에서도 4.29다. 그래서 규칙은 "스크림을 올린다"가 아니라 **"배경을 모르는 면에는 `tpSecondary`를 쓰지 않는다"** 가 된다.

## 5. 발견 4 — 내비게이션 모델이 없다

`MapHomeView.swift` 는 21,998줄이고, `.sheet(` 25개, `.fullScreenCover(` 2개를 포함해 모달 표시 상태가 **21개** 있다.

**"48개 병렬 상태"라는 우리의 첫 표현은 부풀리기였다.** `is*Presented` 19 + `is*Expanded` 11 + `selected*` 18 을 더한 값인데, 성격이 다른 세 종류다. 숫자를 크게 만들려고 합친 것이고, 그렇게 쓴 문서는 스스로 신뢰를 깎는다. 철회한다.

**정확한 진단은 숫자가 아니라 구조다:** 이 상태들은 서로 독립이고, 트리도 스택도 아니다. 그래서 세 가지가 관찰된다:

1. **"뒤로"의 의미가 없다.** 어떤 시트를 닫아도 지도로 돌아온다. 설정 → 데이터 보호 → 닫기 후 "방금 그 화면"으로 갈 방법이 없다.
2. **불가능한 상태에 도달할 수 있다.** `is*Presented` 두 개가 동시에 `true` 면 SwiftUI는 나중 것만 보여주고 앞의 것은 조용히 사라진다. assertion이 없다.
3. **모달이 모달을 띄운다.** `MapHomeCalendarSheet` 안에 `.sheet` 이 2개 더 있다. 닫기를 세 번 눌러야 지도로 오는데 세 번의 시각 피드백이 동일하다.

**하단 바 7개 버튼**: `메뉴 · 달력 · 현재 위치 · 집 · 재생 · 녹화 · 메모`. **이 중 "당신이 어디 있는가"를 바꾸는 것은 0개다.** 전부 현재 화면에 대한 조작이다. 드로어 4개 그룹(`기록 / 화면 / 연결 / 앱`)도 전부 설정이다 — **드로어는 내비게이터가 아니라 설정 패널**이다.

**처방** `DayNavigator { mode, path: [DayRoute], selectedDate }` 하나. 하루를 세 개의 투영(지도 / 타임라인 / 기록)으로 보고, 모달은 스택 밖 전역 오버레이로 뺀다. `루틴`은 탭이 아니라 계획 레이어로 내린다(`GoalRepeatRule` 이 실제로 시작·끝 분 + 요일뿐이고, `PlanRecord` 는 `ScheduleView` 에서 60회, `GoalsView` 에서 24회 쓰인다).

## 6. 발견 5 — 죽은 20,811줄, 그리고 그 죽은 코드가 컴포넌트로 들어올 뻔했다

`legacyUIEnabled = false`(`AppShellView.swift:7`) 뒤에 런타임 도달 불가 코드가 있다:

| 파일 | 줄 수 |
|---|---:|
| `ScheduleView.swift` | 11,822 |
| `ReviewView.swift` | 4,817 |
| `SettingsView.swift` | 2,324 |
| `GoalsView.swift` | 1,848 |
| **합계** | **20,811** |

여기에 `AppDetail` 14개 케이스 전부가 더해진다.

**이번 디자인 시스템 작업에서 실제로 한 번 유입될 뻔했다.** `weekBars` 라는 컴포넌트가 초안 명세에 7열 주간 막대 + "이번 주가 아직 안 끝남" 상태로 들어왔는데, 그건 `ReviewView` 의 `reviewScale == .week` + `chartBuckets`(`ReviewView.swift:31`, `:391-495`) 전용이었다. 살아있는 화면에 7열 막대는 없다. **코드가 되기 전에 잡아서 삭제했다.**

같은 경로로 하나 더: 드로어 그룹이 `기록 / 루틴 / 화면 / 앱` 으로 적혀 있었는데, 실제(`MapHomeView.swift:8375-8400`)는 `기록 / 화면 / 연결 / 앱` 이다. **`루틴` 은 드로어에 없다** — `GoalsView` 의 개념이다.

**정확히 말하면:** 죽은 코드가 컴포넌트로 "유입됐다"가 아니라, **유입될 뻔했고 한 번 걸러졌다.** 걸러진 이유는 출처를 확인하는 절차가 있었기 때문이고, 그 절차가 없으면 다음엔 못 거른다. 그래서 규칙으로 고정했다:

> 모든 컴포넌트는 `TaptionPlan/UI` 의 실제 호출점을 적어야 한다. 못 적으면 싣지 않는다. 그리고 **죽은 화면 안의 구현은 출처로 인정하지 않는다** — 컴파일은 되지만 도달할 수 없다.

### 6.1 이 발견의 가장 비싼 얼굴 — 정원 성장의 입구

`MapHomeView.swift:2004-2006`:

```swift
static func qualifies(actualCount: Int, unconfirmedCount: Int) -> Bool {
    actualCount > 0 && unconfirmedCount == 0
}
```

**미확인이 하나라도 있으면 그날 정원이 자라지 않는다.** 그 미확인 구간을 지우는 주 경로가 "미확인 활동" 시트의 분류 칩이다(`MapHomeTimeSidebar.swift:2270-2318`). 그 칩의 실측:

| 항목 | 실측 | 기준 |
|---|---|---|
| 라벨 크기 | 11pt × `minimumScaleFactor(0.72)` = **7.92pt** | 11pt 하한 미달 |
| 터치 높이 | `minHeight: 36` | 44pt 미달 |
| `contentShape` | **없음** | 같은 파일에서 6곳(`:1261`, `:1353`, `:1574`, `:1605`, `:1783`, `:1809`)은 쓰고 있다 |

즉 **리텐션 루프의 유일한 입구가, 같은 파일이 여섯 번 쓴 패턴을 안 쓴 채로, 36pt에 7.9pt 라벨로 서 있다.** 그리고 이건 리뷰에서 "고칠 것 목록"에 없었다. `trimHandle`(9pt)은 잡았는데 이건 놓쳤다 — 화면에 보이는 결함이 아니라 **루프가 막히는 결함**이라 눈에 덜 띈다.

## 7. 발견 6 — 색이 네 벌이고, 같은 분류가 세 가지 색이다

`Theme.swift` 안에서 28줄 떨어진 두 팔레트가 같은 분류에 다른 값을 준다:

| `work` (업무) | `#2563EB` | `#2E6FDB` | `.tpProject` = `#BEDAE3` |

여기에 `RecordTimelinePalette`(29개 이상)까지 네 벌이다. 그리고 `MapHomePastelPalette` 라는 이름은 사실과 다르다 — 값은 완전 포화다.

`TaptionRadius` 는 **7~14 연속 정수에 이름 8개**, `TaptionSpacing` 은 **4~8에 이름 5개**다. 이름이 값의 동의어라 아무것도 줄이지 못했다. `Theme.swift:160` 의 주석이 스스로 인정한다: *"화면에서 실제로 쓰이던 값을 이름만 붙여 모았다."*

## 8. 실행 순서

각 단계는 독립 배포·독립 롤백 가능해야 한다.

| 단계 | 내용 | 근거 |
|---|---|---|
| **0a** | 위젯 딥링크 수정 (약 20줄) | 이미 약속한 동작이 지켜지지 않고 있다. 선행 조건 없음 |
| **0b** | 카운터 6개 + **2주 기준선** | 계측이 없으면 아래 kill criteria가 전부 연극이 된다 |
| **1** | `DayNavigator` 스택 도입 (UI 무변경) | 27개 모달을 스택 안으로. **순서를 뒤집으면 안 된다** |
| **2** | 3투영 모드 바 — **살아있는 표면을 승격** | `MapHomeTimeSidebar`(3,093) + `MapHomeCalendarSheet`(2,920)은 이미 살아있고 유지보수 중이다. `ScheduleView`+`ReviewView`(16,639)를 되살리는 게 아니다 |
| **3** | 권한을 인라인 상태로 | 첫 실행에서 늦은 모달 → "조용히 기다리는" 빈 상태로 끝난다 |
| **4** | **먼저 결정, 그다음 실행** — 삭제냐 재건이냐 | 20,811줄을 결정 없이 손대지 않는다 |

**코드 구조 로드맵과의 순서 충돌 하나:** `docs/ARCHITECTURE_ROADMAP.md` 의 Phase 2(도메인 모델 6개를 `TaptionPlanCore` 로 승격)는 **이 UX 마이그레이션 뒤로 미뤘다.** 같은 6개 타입의 호출부를 두 작업이 동시에 다시 쓰기 때문이다. 코드 Phase 1(순수 파일 이동)은 먼저 해도 된다 — `MapHomeView.swift` 가 21,998 → 약 9,000줄로 줄어 이 작업의 부담을 낮춘다.

## 9. Kill criteria — 이 계획을 폐기할 조건

계측 없이는 아무것도 반증할 수 없다. 그래서 **0b를 먼저** 한다. 세 기준은 `docs/UX_ARCHITECTURE.md §8.2` 에 **사전 등록**해 뒀다 — 사후에 정하면 그건 측정이 아니다.

| | 지표 | 폐기 조건 | 성공선 |
|---|---|---|---|
| **K1** | 하루 수정(correction) 건수 | 4주 내 +50% 미달 | +50% 이상 |
| **K2** | 세션당 모드 전환 수 | **0.5 미만** | 0.5 이상 |
| **K3** | `기록` 주간 활성 | 15% 미만 | 15% 이상 |

**K2를 가장 먼저 돌린다.** 가장 싸고, 가장 비싼 작업(§8의 2~4단계)을 취소할 수 있는 유일한 지표다.

여기에 계측이 필요 없는 검증을 하나 더 둔다 — **1주짜리 무계측 사용성 테스트**: 다섯 명에게 아무 안내 없이 "지난주 기록을 봐 달라"고 하고, 어디를 누르는지 본다. §8의 2단계가 옳은지 1주 안에 답이 나온다. 계측을 기다리지 않아도 되는 유일한 증거다.

## 10. 검증하지 못한 것 / 가정

정직하게 남긴다. 이 중 하나라도 틀리면 위 결론의 무게가 달라진다.

- **계측이 현재 0이다.** Firebase·Amplitude·Mixpanel·Sentry·PostHog 흔적 없음. 유일한 것은 `TaptionPlanDiagnosticsLogger`(`DiagnosticsLogSupport.swift:331`) — 1MB 로컬 롤링 파일, 수동 내보내기. 따라서 K1~K3는 **아직 측정 불가**이고, 0b가 그걸 만든다.
- **"위젯이 리텐션의 본체"라는 전제는 가정이다.** 근거는 이 앱이 수동 기록 앱이라는 구조적 관찰뿐이고, 데이터가 아니다. 이 전제가 틀리면 §2의 우선순위도 함께 약해진다. 0b에서 위젯 진입 세션 비중을 반드시 같이 잰다.
- **K1~K3의 임계값(+50% · 0.5 · 15%)은 근거 있는 추정이 아니라 우리가 정한 값이다.** 정한 근거는 "이 정도면 사용자가 실제로 행동을 바꿨다고 볼 수 있다"는 판단이다. 첫 2주 기준선이 나오면 다시 조정해야 한다.
- **사용자 행동에 대한 주장은 전부 가정이다.** §5~§7의 발견은 코드에서 확인한 사실이지만, "사용자가 세 투영을 원한다"는 검증되지 않았다. §9가 그걸 싸게 반증하기 위한 장치다.
- **다크 모드는 하지 않는다.** 이유는 측정했다: imageset 442개 중 **366개**가 `HomeEvolution001…366` 이고, 전부 `template` 미선언 SVG라 어두운 바탕에서 원색으로 붙는다. 재개 조건 3개를 `DESIGN_SYSTEM.md §8.1` 에 적었다.
- **디자인 시스템은 아직 코드가 아니다.** 토큰 모양과 타이포그래피 표현식까지 썼고, 컴포넌트 구현체는 쓰지 않았다.
