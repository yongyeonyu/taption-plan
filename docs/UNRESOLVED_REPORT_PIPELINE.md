# 판단 못 한 것 신고 파이프라인 (앱 → 서버 → 맥 대시보드)

요청 ID `RPT1121A01` · 2026-11-21 · 대표 지시 · **설계서(코드 변경 없음)**

앱의 규칙·알고리즘·AI가 판단하지 못한 경우를 사용자가 동의한 범위에서 자동으로 서버에 모으고, 요청이 많은 것부터 맥북 운영 페이지에서 보고 규칙으로 등록해, 다음 앱 버전·규칙 묶음으로 되돌려 주는 한 바퀴를 정의한다.

## 0. 이미 있는 것 (새로 만들지 않고 넓힌다)

| 조각 | 위치 | 역할 |
| --- | --- | --- |
| 오분류 교정 표본 | `server/trip-relay/src/classifier.js`, D1 `0002`, `POST/DELETE /classifier-samples`, `GET .../admin` | 활동 분류를 사용자가 고친 비식별 특징값 |
| 미분류 가맹점 이름 | `src/merchants.js`, D1 `0003`, `/merchants/unknown`, `/merchants/admin`, 앱 `LedgerMerchantCollector` | 이름·건수만, 켠 사람만 |
| 운영 페이지 | `tools/admin-console`(로컬 127.0.0.1, 키는 로컬 저장소) 「현황」 탭 | 서버 운영자 길로 읽어 표로 보임 |

문제는 종류마다 길이 따로라 **새 종류가 생길 때마다 앱·서버·운영 페이지를 세 번 고치는 것**이다. 그래서 공통 틀 하나(아래)를 두고 기존 둘을 그 틀의 종류로 편입한다. 기존 두 길은 호환을 위해 당분간 유지한다.

## 1. 신고 종류(kind)

종류마다 「무엇을 모르는가」와 「보내도 되는 최소 정보」를 고정한다. 목록에 없는 종류·열쇠는 서버가 버린다.

| kind | 모르는 것 | 보내는 것(허용 목록) | 절대 안 보내는 것 |
| --- | --- | --- | --- |
| `merchant_icon` | 가계부 가맹점 종류 | 정규화한 가게 이름 | 금액·시각·계정·카드 번호 |
| `payment_notice` | 가계부에 안 들어간 앱 알림 | 앱 번들 ID, 형식 지문(2절), 인식 실패 이유 코드 | 알림 원문, 금액, 가게 이름 |
| `sms_format` | 인식 못 한 문자(결제·항공·호텔·숙박·교통) | 발신 채널 종류(번호 대역 아님, 업체 코드), 형식 지문, 추정 분야(`travel_air/hotel/…`) | 원문, 예약번호, 이름, 날짜, 금액, 전화번호 |
| `activity_class` | 활동 분류가 낮은 확신 | 기존 `bokki-misclassification` v1 특징값 그대로 | 좌표·장소 이름·날짜 |
| `activity_detail` | 상세 활동 구분 실패 | 대분류 코드, 상세 코드 후보, 시간대(분 단위 구간), 길이 구간 | 장소·제목·메모 |
| `route_undefined` | 경로·이동 수단 정의 실패 | 이유 코드(`gap`, `low_accuracy`, `unknown_mode`, `no_transit_match`), 거리·속도·길이 **구간(버킷)**, 이동 수단 후보 | 좌표, 출발·도착 이름, 정확한 시각 |
| `bubble_schedule` | 말풍선·일정이 잘못 만들어짐 | 말풍선 종류 코드, 이유 코드, 규칙 버전 | 말풍선 글, 일정 제목, 장소 |
| `calendar_title` | 달력 일정 제목 활동 분류 실패 | 제목의 형식 지문만 | 제목 원문 |

좌표·정확한 시각·원문은 어느 종류에서도 서버로 가지 않는다(`AGENTS.md` 3절 좌표 규칙).

## 2. 형식 지문(fingerprint) — 원문 없이 「같은 모양」을 센다

글을 그대로 보내지 않고 기기에서 골격으로 바꾼 뒤 해시한다.

1. 숫자 연속 → `#`, 날짜·시각 꼴 → `D`/`T`, 금액 꼴 → `$`, URL → `U`, 한글·영문 고유 이름(사람·가게) 자리는 보존하지 않는다.
2. 업체가 고정으로 쓰는 앞뒤 문구(상용구)만 남긴다. 상용구 사전에 없는 단어는 `W`로 바꾼다.
3. 골격이 20자 미만이거나 `W` 비율이 50%를 넘으면 신고하지 않는다(알아볼 수 없는 글은 모을 가치가 없고 새 위험만 만든다).
4. 지문 = `SHA-256(골격)` 앞 16자. **골격 자체도 서버로 보내지 않는다**(지문과 채널 코드만). 규칙 등록을 하려면 「이 지문을 받은 사용자에게 골격을 한 번 더 보내도 되는지」를 앱이 다시 묻는 2단계(5절 B)를 쓴다.

> 이 규칙은 FLT1120A01 E·F의 「스켈레톤만 전송, 원문 즉시 폐기」와 같은 것이라 구현을 공유한다.

## 3. 전체 흐름

```
앱(기기)                               중계 서버(Cloudflare Worker + D1)            맥북(admin-console)
────────                               ───────────────────────────────            ───────────────────
판단 실패 지점 ──┐
 (분류·아이콘·알림·문자·경로)           POST /reports/unresolved
                ▼                        ├ 허용 목록 검사(kind별) ──불통과→ 버림
 UnresolvedReporter(단일 입구)           ├ 주인 키 해시(owner)
  ① 동의 확인(종류별 스위치)             ├ 하루 한도·본문 크기 한도
  ② 기기에서 정규화·지문·버킷화           ├ 집계: (kind, key) → hits, owners, first/last
  ③ 로컬 대기열(중복 제거, 6시간 간격)    └ 원본 표본은 저장하지 않는다(집계 행만)
  ④ 배치 전송(≤100건, 64KB)                                                          GET /reports/admin ◄── 현황 탭
                                                                                      (운영자 토큰, 로컬 키 저장소)
                ▲                        GET /rules/bundle ◄── 앱이 하루 1회 확인      │
   규칙 묶음 적용 ◄─ 서명 검증 ◄─────────  (서명된 규칙 묶음)  ◄───────────────────────┘ 요청 많은 것 → 「규칙 등록」
   다음 판단부터 해결됨                                                            상태: new → accepted → shipped / ignored
```

### 3.1 앱

- **단일 입구 `UnresolvedReporter`** 하나만 서버 전송 경로가 된다. 각 판단 지점은 `report(kind:, key:, reason:)`만 부른다. 네트워크·동의·정규화·대기열은 입구가 맡아, 새 종류를 넣어도 판단 지점 코드는 한 줄이다.
- **종류별 동의**: 데이터 보호 화면에 「판단 못 한 것 보내기」 하나의 스위치 아래 종류별 하위 스위치(가맹점 이름 / 문자·알림 형식 / 활동·경로). 모두 **기본 꺼짐**. 켠 종류만 대기열에 쌓는다.
- **로컬 대기열**: 이미 보낸 키는 다시 세지 않는다(현재 `ledgerMerchantReportedIDs` 방식 일반화). 6시간 간격, 켠 상태에서만, 가계부·여행 화면을 열 때 시도.
- **사용자 통제**: 「보낼 목록 보기」(무엇이 나갈지 앱에서 그대로 보임), 「보낸 것 지우기」(서버 `DELETE`), 끄면 대기열 폐기.
- **오프라인·실패**: 대기열에 남기고 다음 기회에. 서버 오류는 재시도하되 지수 간격.

### 3.2 서버

- 새 라우트 `POST /reports/unresolved`(주인 키), `DELETE /reports/unresolved`(내 것 지우기), `GET /reports/admin`(운영자 토큰 `CLASSIFIER_ADMIN_TOKEN` 재사용).
- **D1 `0004_unresolved_reports.sql`**: `unresolved_reports(kind, key, owner, hits, first_at, last_at, rule_version, PRIMARY KEY(kind, key, owner))` + 운영 상태 테이블 `report_triage(kind, key, status, note, rule_ref, updated_at)`. 기존 `unknown_merchants`는 `kind=merchant_icon` 행으로 이관하는 SQL을 같은 마이그레이션에 둔다(되돌림 불가라 배포는 대표 확인).
- **kind별 검사기**(`src/reports/<kind>.js`): 열쇠 정확히 일치·값 범위·정규식 허용 목록. 한 곳이라도 어긋나면 그 항목을 버린다(전체 거절이 아니라 항목 단위, 개수를 돌려줘 앱이 보고).
- 한도: 본문 64KB, 요청당 100항목, 하루 종류별 300 고유 키, 보관 1년(올릴 때마다 정리). 서버 로그에 본문을 남기지 않는다.
- **같은 모양 N명 이상일 때만 운영 페이지에 노출**(k-익명, 기본 N=2 — 베타 규모를 고려해 대표가 바꿀 수 있음). N 미만은 합계 건수만 보인다.

### 3.3 맥 대시보드(`tools/admin-console` 「현황」 탭 확장)

- 종류별 탭: 표 = 키(이름/지문/이유 조합), 요청 수, 보낸 사람 수, 처음·마지막 본 시각, 규칙 버전, 상태.
- 보기 보조: 최근 7일 추세 막대, 「앱 버전별」 분포(규칙 버전 기준), 이유 코드 분포(`route_undefined`는 이유별로 합산해 어느 로직이 약한지 보임).
- **분류 작업(triage)**: 행마다 `수락 / 무시 / 이미 등록됨`을 고르고 메모. 서버 `report_triage`에 저장되어 같은 키가 다시 올라와도 「무시」는 숨는다.
- **내보내기**: 상위 N개를 지금처럼 클립보드로 복사(규칙 작성용). 문자 형식은 지문만 있으므로 「골격 요청」(5절 B) 버튼으로 해당 지문을 받은 사용자에게만 2차 확인을 보낼 수 있게 한다(2단계, 별도 승인).
- 오프라인·미배포·토큰 없음은 지금처럼 이유를 화면에 알려 준다. 키는 응답에 절대 싣지 않는다.

### 3.4 되돌려 주는 길(루프를 닫는 부분)

신고를 모으기만 하면 의미가 없다. 대표가 「수락」한 항목이 **다음 버전 없이도** 앱에 닿는 길을 둔다.

1. 대표가 운영 페이지에서 키별 규칙(예: 가맹점 이름 → 아이콘 종류, 알림 앱 → 가계부 인식 패턴)을 만든다.
2. 서버가 서명된 **규칙 묶음**(`GET /rules/bundle`, 버전·서명)으로 낸다. 서명 개인 키는 오프라인 보관(FLT1120A01 G와 같은 것, 대표 몫).
3. 앱은 하루 한 번 묶음을 받아 서명을 검증하고 로컬 규칙표에 합친다. 실패하면 내장 규칙으로 계속 쓴다.
4. 규칙이 적용되면 같은 항목은 더 이상 신고되지 않고, 신고 수가 줄어드는 것이 **효과 측정**이 된다.

묶음에는 데이터만 들어간다(실행 코드 없음, 값은 앱이 아는 코드 집합 안에서만 유효). 앱이 모르는 코드는 무시한다.

## 4. 개인정보·안전 원칙 (공개 저장소)

- 종류별 허용 목록 + 열쇠 개수 일치 + 서버 이중 검사. 모르는 열쇠 하나면 그 항목 폐기.
- 원문·좌표·정확한 시각·계정·전화·예약번호는 어느 길로도 안 나간다. 문자·알림은 **지문만**.
- 기본 꺼짐, 종류별 동의, 「보낼 목록 보기」, 「보낸 것 지우기」.
- 주인 키 해시는 한도·삭제용이고 대시보드에는 「몇 명」으로만 보인다. 개인 단위 열람 화면은 만들지 않는다.
- 1년 보관, 지문·이름은 N명 미만이면 대시보드에 상세 숨김.
- 번호·이름이 섞인 가맹점 이름 거르기 규칙은 기존(`*`·숫자 4자리 이상·@·주소 꼴)을 공유한다.
- App Store Connect 개인정보 답변(구매 이력, 기타 사용자 콘텐츠 / 연결 안 됨 / 앱 기능)과 `PRIVACY.md`·`PrivacyInfo.xcprivacy`를 종류가 늘 때마다 같이 고친다.
- **`AGENTS.md` 4절 「가맹점 이름 수집」은 「다른 정보로 넓히지 않는다」고 못 박혀 있다.** 이 설계를 구현하려면 같은 항에 이 문서를 근거로 한 확장 결정(종류·범위·기본값)을 적어야 하므로, 구현 첫 커밋에서 한다.

## 5. 단계 (각 단계는 시험 통과 후 경로 지정 커밋)

| 단계 | 내용 | 서버 배포 필요 |
| --- | --- | --- |
| **A** 틀 | 앱 `UnresolvedReporter`·종류 프로토콜·대기열·동의 스위치, 서버 `/reports/*`·D1 `0004`·검사기 골격, 기존 가맹점·오분류를 새 틀에 연결(두 옛 길 유지) | 예(대표 확인) |
| **B** 문자·알림 | 형식 지문 생성기(기기), `payment_notice`·`sms_format` 검사기, 골격 2차 확인 흐름(별도 승인) | 예 |
| **C** 활동·경로 | `activity_detail`·`route_undefined`·`bubble_schedule` 이유 코드 정의, 판단 지점 연결(`PlaceZoneStayTracker`의 「빈 구간」, 경로 매칭 실패 등) | 예 |
| **D** 대시보드 | 종류별 탭, 추세, triage 상태, 내보내기 | 아니오(로컬) |
| **E** 루프 닫기 | 규칙 묶음 라우트·서명 검증·앱 합치기, 효과 측정 | 예 + 서명 키 |

권장 순서는 A → D → B → C → E. A·D만으로도 「요청이 몰리는 것을 맥에서 보는 것」은 이미 끝난다.

## 6. 시험

- 서버: 종류별 허용 목록(통과 1건·금지 열쇠 거절 각 종류), 항목 단위 폐기, 한도·보관, k-익명 숨김, triage 상태가 `GET`에 반영, 마이그레이션 이관, 로그에 본문이 없는지.
- 앱: 동의 꺼짐이면 0건, 종류별 켬/끔, 지문 생성기(같은 모양 → 같은 지문, 이름·숫자만 다른 글 → 같은 지문), 원문이 요청 본문에 없는지, 대기열 중복·간격, 오프라인 재시도.
- 운영 페이지: 오프라인·미배포·토큰 없음·성공, 키 미노출.
- 전 구간 계약 시험: 앱이 만든 본문 예시를 서버 검사기에 넣는 한 쌍(양쪽 허용 목록 어긋남 방지).

## 7. 대표 결정 필요

1. **범위 확장 승인**: `AGENTS.md` 4절에 종류 확장을 적어도 되는지(구현 전 필수).
2. **문자·알림**: 원문 없이 **지문만** 보내는 것으로 충분한지, 아니면 규칙 등록을 위해 골격 2차 확인(5절 B)까지 열지.
3. **기본값**: 종류별 스위치를 계속 꺼짐으로 둘지(권장), 베타 동안만 켜짐으로 할지.
