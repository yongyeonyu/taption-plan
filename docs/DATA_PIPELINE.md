## 1. 지금 파이프라인

```
수집(iOS)                저장(정본)                         파생                     보관
─────────                ──────────                        ────                     ────
CLLocation 1~15분  ─┐
DeviceMotion 요약   ├─→ SensorReading ─→ readings (60열) ─→ 하루 투영(메모리)  ─→ sealed_days
HealthKit 가져오기  │                     records (JSON body)   지도 캐시(메모리)     월 백업 파일
워치 스냅샷         └─→ raw_events (불변, payload TEXT)                          (암호화·청크)
```

| 단계 | 코드 | 비용 성격 |
| --- | --- | --- |
| 쓰기 | `TaptionStoreV2.appendImmutableReadings` → `TaptionReadingRowCodec.row(for:)` | 행마다 JSON 2통과 + 56열 펼치기 → **P1 이후 0통과** |
| 읽기 | `loadReadings` → `TaptionReadingRowCodec.reading(from:)` | 행마다 사전 재구성 + JSON 2통과 → **P1 이후 0통과, P2 이후 사전도 안 만든다** |
| 하루 투영 | 메모리 캐시(디스크 캐시 없음) | 하루 범위 조회 = 그날 행 전부 해독 |
| 확정 요약 | `sealed_days` (LZFSE 압축 BLOB) | 하루 1행, 읽기 드묾 |
| 백업 | `TaptionBackupEngine.export` → 하루씩 읽어 청크 암호화 | 스트리밍(메모리 상한 있음) + 검증 재읽기 1회 |

설계상 좋은 부분은 그대로 둔다. 백업은 이미 하루 단위 스트리밍이고, 원본(`raw_events`)과 사용자 편집(`records`)이 분리돼 있다. 센서 원본(`readings`)에는 톰스톤을 두지 않고 전체 삭제로만 지우며, 기록(`records`)은 `deleted` 열로 톰스톤을 쓴다 — 백업이 원본을 합집합으로 되살리는 규칙과 맞는 선택이다.

### 2-3. 코덱 (대리 측정)

`SensorReading`은 앱 target에 있어 단독 실행이 안 되므로, 같은 56필드 모양의 구조체로 `row(for:)`/`reading(from:)`과 같은 4단계 JSON 경로를 재현했다. **절대값이 아니라 단계 간 비중만 읽는다.**

| 단계 | 비용 |
| --- | ---: |
| 1 `JSONEncoder.encode` | 11.2µs/행 |
| 2 `JSONSerialization` 파싱 | **17.7µs/행** |
| 3 `JSONSerialization.data` | 13.7µs/행 |
| 4 `JSONDecoder.decode` | 13.5µs/행 |
| 쓰기 경로(1+2) | 31.0µs/행 |
| 왕복(1+2+3+4) | **35.9µs/행** |

`JSONSerialization` 두 통과(31.4µs)가 `Codable` 두 통과(24.7µs)보다 비싸다. 그리고 그 두 통과는 **오직 열로 펼치기 위해서만** 존재한다.

### 2-3-1. 코덱 실측 (P1 구현 후, 정정)

위 대리 측정은 **틀렸다.** 단계만 따로 재면 JSON 통과가 87%처럼 보이지만, 행 경로 전체를 재면 그 비중이 작다.
P1 구현 뒤 실제 `SensorReading` 1,000행으로 예전 경로와 새 경로를 같은 조건에서 쟀다
(`TaptionPlanTests/TaptionStoreColumnCodingTests.testColumnCodecIsFasterThanTheLegacyJSONPath`, 최소 3회).

| 경로 | 예전 | P1 | 배율 |
| --- | ---: | ---: | ---: |
| 쓰기 (`row(for:)`) | 164.6 / 130.1ms | **136.9 / 108.1ms** | **1.20× (두 번 모두)** |
| 읽기 (`reading(from:)`) | 133.3 / 97.4ms | 135.7 / 93.6ms | 0.98× / 1.04× = **잡음 범위** |

절대값은 실행마다 20~30% 흔들린다(시뮬레이터·캐시 상태). 그래서 읽는 것은 배수뿐이고,
**쓰기 1.20×는 두 번 다 같았고 읽기는 개선도 악화도 확인되지 않았다.**

읽기는 빨라지지 않았다. 이유는 남은 비용이 JSON이 아니기 때문이다:

- `take`/`put`이 **행마다 56번** `column.path.split(separator: ".")`로 문자열을 쪼갠다(두 경로 공통).
- 사전을 `[String: Any]`로 만들며 값을 복싱하고, 디코더는 다시 동적 캐스팅으로 꺼낸다(두 경로 공통).
- 읽기에서는 `extra` 파싱(`JSONSerialization.jsonObject`)이 그대로 남아 있다.

즉 **행 경로의 비용은 "JSON 4통과"가 아니라 "행마다 56열을 문자열 경로로 다루는 일"**이다.
이 발견이 P2의 근거를 바꾼다: 열 수를 줄이는 것(핫/콜드 분리)이 JSON을 줄이는 것보다 크게 듣는다.

### 2-3-2. 읽기 경로 분해 — 열당 비용을 먼저 없앴다

P2(핫/콜드 표 분리)에 들어가기 전에, 134.3ms가 어디로 가는지부터 쟀다
(`testReadPathBreakdown`, 1,000행, 최소 3회).

| 항목 | 비용 | 비중 |
| --- | ---: | ---: |
| `extra` 파싱(`JSONSerialization.jsonObject`) | 7.1ms | 5% |
| `put` + 사전 만들기 | 79.6ms | 59% |
| └ 그중 `column.path.split(separator: ".")` | **53.2ms** | **40%** |
| 디코더(컨테이너 순회 + 동적 캐스팅) | 47.6ms | 35% |

**경로 문자열을 쪼개는 일만 40%**였다. `columns`는 컴파일 시점에 고정인데도 `take`/`put`이
행마다 56번 `split`을 하고 있었다. 한 번만 쪼개 두도록 고쳤다(`columnParts`, 30줄).

| 경로 | 고치기 전 | 고친 뒤 | 배율 |
| --- | ---: | ---: | ---: |
| 읽기 1,000행(전체) | 134.3ms | **75.7~77.2ms** | **1.74~1.77×** |
| 쓰기 1,000행(예전 대비) | 1.20× | **1.27~1.49×** | — |
| 분해 | extra 7.1 + put 79.6 + 디코더 47.6 | extra 6.9 + put 29.5~34.0 + 디코더 36.3~39.3 | — |

읽기 배율은 `testReadPathBreakdown`의 **전체 값**으로 잰 것이다. `testColumnCodecIsFasterThanTheLegacyJSONPath`의
"예전 vs 새" 비교는 이제 두 쪽이 같은 `take`를 쓰므로 읽기에서 1.0×로 나온다(그 테스트는 P1의 JSON 제거만 본다).

**스키마를 바꾸지 않고 얻은 이득이다.** 남은 76ms는 `put`/사전 30~34ms(약 44%)와
디코더 36~39ms(약 47%)가 나눠 갖는다. 후보는 ① 중첩 열(`point.*` 등)의 사전 복사를 묶기
② 사전을 거치지 않고 행에서 바로 모델로 디코딩이었고, **②를 아래 2단계에서 했다**(①은 하지 않았다).

#### 2단계 — 사전을 거치지 않고 행에서 모델로

1단계 후 남은 76ms의 절반이 사전(`[String: Any]`) 만들기였다. 그 사전은 **읽는 쪽에서만**
쓰이고(쓰기는 여전히 사전을 거쳐 열로 펼친다), `SensorReading`은 열 값에서 바로 채울 수 있다.
그래서 사전을 아예 만들지 않는 디코더(`TaptionRowDecoder`)를 넣었다. `Codable`이 부르는
컨테이너만 구현하고, 키를 열 위치로 바꿔 곧장 꺼낸다.

| 항목 | 1단계 후 | 2단계 후 |
| --- | ---: | ---: |
| 사전 만들기(`put`) | 29.5~34.0ms | **없음** |
| 행→모델(디코딩) | 36.3~39.3ms | 55.1~61.7ms |
| 위 둘의 합 | 65.8~73.3ms | **55.1~61.7ms** |
| `extra` 파싱 | 6.9ms | 6.2~7.0ms |
| **전체** | **75.7~77.2ms** | **61.2~68.7ms** |

디코딩 자체는 36~39ms에서 55~62ms로 **늘었다**. 열 값을 꺼낼 때마다
`columnIndexByPath`/`nestedColumnIndex` 사전을 조회하는 비용이 붙었기 때문이다.
그래도 사전 만들기(30~34ms)가 통째로 사라져 합계는 줄었다 — 두 단계를 합치면
134.3 → 61.2~68.7ms(**1.95~2.19×**)다.

하루(1,440행)로 환산하면 코덱 193.4 → **88~99ms**이고 SQL 5.52ms는 그대로다.
즉 하루 조회가 약 199ms → 약 94~105ms가 된다(선형 환산값).

### 2-3-3. 최적화 빌드에서 다시 쟀다 — 앞의 수치는 전부 Debug였다

위의 모든 값은 **Debug(`-Onone`)** 빌드에서 잰 것이다. 그런데 사용자가 쓰는 앱은 `-O`로 컴파일된다.
`-Onone`에서는 인라이닝이 없고 제네릭·프로토콜 호출이 전부 실제 호출이라 행당 비용이 부풀려진다.
같은 테스트를 `SWIFT_OPTIMIZATION_LEVEL=-O SWIFT_COMPILATION_MODE=wholemodule`로 다시 돌렸다(1,000행, 3회).

| 항목 | Debug(`-Onone`) | 최적화(`-O`) | 배율 |
| --- | ---: | ---: | ---: |
| 전체 | 61.2~68.7ms | **37.3~37.8ms** | 1.6~1.8× |
| `extra` 파싱 | 6.2~7.0ms | 6.7~6.9ms | **1.0×** |
| 행→모델 | 55.1~61.7ms | 30.7~31.1ms | 1.8~2.0× |
| 표본 폭 | 7.5ms | **0.5ms** | — |

- **최적화 빌드에서는 폭이 0.5ms다.** Debug의 7.5ms 폭은 코드가 아니라 `-Onone`의 들쭉날쭉함이었다. 앞으로 판단은 `-O` 값으로 한다.
- **`extra` 파싱은 최적화로 줄지 않는다**(6.7~6.9ms). `JSONSerialization`이 시스템 라이브러리라 우리 컴파일 옵션과 무관하다. 그래서 최적화 빌드에서 `extra`가 읽기의 **18%**다(Debug에서는 10%).
- 하루(1,440행) 환산: 코덱 **54ms**(Debug 88~99ms) + SQL 5.52ms. 기본 5분 간격(288행)이면 **10.8ms**.
- **1.95~2.19×는 Debug 기준 배율이다.** P1 이전 134.3ms(Debug)와 37.5ms(`-O`)를 그대로 비교할 수는 없다. 정확한 배율은 같은 `-O`로 P1 이전 코드를 재측정해야 나온다(아직 안 했다).

### 2-3-4. 그래서 다음 최적화는 하지 않는다 (계산으로 판단)

"열 위치를 `CodingKey`에서 바로 얻기"(지금은 열마다 사전을 두 번 조회한다)를 하려다 계산부터 했다.
조회를 한 번으로 줄이면 56,000회(1,000행 × 56열)에서 아끼는 시간은 **약 0.8ms**다
(사전 조회 1회를 15ns로 가정한 **추정값**이고 측정값이 아니다). 행→모델 30.7ms의 **2.7%**다.
코드 중복과 회귀 위험을 감수할 크기가 아니다. **P2는 여기서 끝낸다.**

남은 30.7ms를 더 줄이려면 `Codable` 컨테이너를 거치지 않고 `init(from:)`을 손으로 쓰는 방법뿐인데,
56개 속성을 손으로 옮겨 적는 코드가 되어 모델이 바뀔 때 조용히 틀릴 위험이 크다. 얻는 것에 비해 비싸다.

### 2-4. 측정의 한계

1. 합성 데이터다. 실제 기기 데이터의 열 채움률·문자열 길이가 다르면 바이트/행이 달라진다.
2. `all_readings` 2,202ms는 Python이 60열을 튜플로 만드는 비용을 포함한다. Swift는 이 비용을 내지 않으므로 **과대**다. 이 값은 "전체 스캔은 초 단위"라는 크기로만 쓴다.
3. 2-3의 코덱 표는 대리 구조체 값이다. 실제 `SensorReading`으로 잰 값은 2-3-1에 있고, **둘이 다른 결론을 낸다**(2-3-1이 맞다).
4. 2-3-1은 시뮬레이터(iOS 27.0)에서 잰 값이다. 실기기 Instruments 측정이 남아 있다.
5. 2-3-2의 표본은 단계마다 3~4개다. 2단계 후의 폭(61.2~68.7ms)이 1단계 후(75.7~77.2ms)보다 넓은데, 시뮬레이터 스케줄링 잡음으로 보인다. 두 구간은 **겹치지 않으므로** 개선은 실재하지만, 배율은 1.10×~1.26×로만 말할 수 있다.
6. 2단계 측정 중 시뮬레이터가 부트스트랩 전에 SIGKILL로 죽은 실행이 2회 있었다(메모리 압박: 스왑 4.8GB/6.1GB). 그 실행들은 값을 내지 못해 표에 없다.
7. **2-3-3을 뺀 모든 표는 Debug(`-Onone`) 값이다.** 2-3-1·2-3-2의 수치도 마찬가지다. Debug 값과 `-O` 값을 섞어 배율을 만들면 안 된다. 실기기 Instruments 측정은 여전히 남아 있다.

## 3. 진단

### D1. 하루를 읽는 비용의 대부분이 행 변환이다

처음엔 하루 1,440행이면 코덱 51.7ms + SQL 5.52ms라고 쟀는데(2-3 대리 측정), 실제 `SensorReading`으로
다시 재니 코덱 193.4ms + SQL 5.52ms였다. **코덱이 97%**다. 원인은 JSON이 아니라 열 하나를 다루는
비용이었다(2-3-2). P2 2단계 후 코덱은 **88~99ms**이고, 기본 간격(5분, 288행)이면 18~20ms다.
실시간(1분)을 켠 사용자는 하루를 넘길 때마다 이 비용을 낸다.
근거: `TaptionStoreV2.swift:194-220`(쓰기), `:231-250`(읽기), `:607-611`(행마다 해독).

### D2. 60열 한 행이 499바이트다

1분 간격 1년 250MB, 5분 간격 1년 52.5MB. 여기에 `raw_events`의 JSON payload가 더 붙는다. 백업 파일은 이 본문을 압축하지만, **로컬 DB와 백업 검증 재읽기는 압축되지 않은 이 크기를 그대로 쓴다.**
같은 하루를 6열만 읽으면 0.83ms로 60열(5.52ms)의 **1/6.6**이다. 즉 열 폭이 읽기 비용을 그대로 결정한다.

### D3. 열 매핑 실패가 조용히 `extra`로 떨어진다

`convert`는 타입이 맞지 않으면 `nil`을 돌려주고(`TaptionStoreV2.swift:287-302`), 그 값은 `extra` JSON에 남는다. 왕복은 무손실이지만 **그 열은 이후 모든 행에서 NULL이 되고, 그 사실을 알려 주는 계수·경보가 없다.** 모델 필드 하나의 타입이 바뀌면(예: `motion`이 enum 직렬화로 바뀜) 과거 전체가 조용히 열 조회에서 빠진다.

### D4. 해독 실패는 개수가 없다 (충돌은 이미 드러난다)

- 해독 실패는 `failures`에 모여 `isComplete: false`가 되지만, 소비처는 `sensor_store_unreadable_rows` 로그 한 줄만 남긴다(`SensorDataServices.swift:489-495`). 몇 행이 사라졌는지 수가 없다.
- **충돌은 조용하지 않다.** 실제 수집 경로 `appendImmutableReadings`는 내용이 다르면 `readingConflict`를 던지고(`TaptionStoreV2.swift:476-477`, `:509-519`), 백업 합치기 경로 `mergeReadingsKeepingLocal`은 개수를 `RestoreSummary.readingConflicts`로 돌려준다(`TaptionBackupEngine.swift:521`). 조용히 버리던 `insertNewReadings`는 **호출부가 0곳인 죽은 코드**였다(P0에서 삭제).
- 정정: 이 문서의 첫 판은 "충돌이 집계되지 않는다"고 적었는데, 코드를 따라가 보니 살아 있는 두 경로 모두 드러난다. 틀린 진단이었다.

### D5. `day`는 쓰기 시점 달력의 파생값이다

`day` = `YYYYMMDD`를 열 때의 달력(`.autoupdatingCurrent`, `:326-330`)으로 계산해 저장한다(`:216`). 시간대를 옮기면 같은 순간이 다른 `day`로 들어가고, 기존 행은 옛 `day`로 남는다. `dayRanges()`는 이 열로 묶으므로(`:559`) 여행 후 백업 날짜 범위가 겹치거나 비게 된다. 읽기는 `ts` 기준이라 지도는 무사하지만, **파생값을 정본처럼 저장한 것이 원인**이다.

### D6. 호출부가 없는 데이터 경로가 있다

`allReadings()`와 `backupDateRanges()`는 **앱**에서 부르는 곳이 없다. `allReadingsForMigration()`은 보관 저장소 래퍼(`SensorDataServices.swift:941-943`)에서만 쓰인다. `day_ranges`의 5.08× 개선이 매력적으로 보이는 이유가 이 죽은 경로다.

**정정(2026-10-24) — "호출부 0곳"은 앱 기준이고, 둘 다 그냥 지우면 안 된다.**

| 함수 | 실제 호출부 | 지우면 |
| --- | --- | --- |
| `allReadings()` (`SensorDataServices.swift:435`) | 앱 0곳, **테스트 4곳**(`SensorDayStoreTests.swift:811·852·886·938`) | 테스트 4개를 다른 경로로 고쳐야 한다 |
| `backupDateRanges()` (`:428`) | **아무 데도 없음** | `store.dayRanges()`의 유일한 호출자가 사라져 **P0의 G4(`store_day_drift`) 계측이 죽는다** |

`backupDateRanges()`는 `store.dayRanges()`를 부르는 유일한 곳이다(`:430`). 그래서 `dayRanges()`에 넣어 둔
G4 계측은 지금 이 죽은 경로를 통해서만 실행된다. 삭제하려면 G4를 다른 살아 있는 경로로 옮기거나,
`dayRanges()`를 진단용으로만 남기고 `dayDrift()` 쪽으로 계측을 옮겨야 한다. **삭제는 보류한다.**

## 4. 설계

### 원칙

1. **정본은 좁게, 파생은 넓게.** 저장은 사실만, 넓은 표현은 파생 계층에서 만든다.
2. **조용한 손실 금지.** 버린 행·강등된 열·무시한 충돌은 전부 센다.
3. **한 번에 한 단계.** 스키마 무변경 → 코덱 → 표 분리 순으로, 각 단계가 독립적으로 되돌릴 수 있게.
4. **측정 없이 최적화하지 않는다.** 위 표에 없는 개선은 하지 않는다.

### 목표 구조

```
L0 raw_events      불변 수신 원본 (kind, id, ts, payload)          — 그대로 유지
L1 readings_hot    하루 조회·지도·재생이 쓰는 좁은 열 (약 12개)     — 신규
   readings_body   나머지 44열을 압축 BLOB 한 칸에                  — 신규
L2 projection      메모리 캐시, 언제든 폐기·재계산                   — 그대로
L3 sealed_days     확정 요약(LZFSE)                                 — 그대로
   backup          월 파일, 스트리밍·청크 암호화                     — 그대로
```

`readings_hot`은 **색인이 아니라 표 분리**로 만든다. 커버링 색인은 +76.5MB(30.6%)를 쓰고 하루 0.15ms를 아끼는 데 그쳤지만, 표를 나누면 그 열들이 원래 행에서 빠져 본문 자체가 줄어든다.

### 코덱 3단계

| 단계 | 방식 | 예상 | 위험 |
| --- | --- | ---: | --- |
| 0 | 현행 (encode → parse → 56열 → data → decode) | 35.9µs | — |
| 1 | `JSONSerialization` 두 통과 제거. `Codable` 합성 대신 `SensorReading`에 열 순서대로 읽고 쓰는 이니셜라이저를 두고, `extra`는 남은 키만 담는다 | ~24.7µs (−31%) | 중간. 왕복 동등성 테스트로 증명 가능 |
| 2 | 이진 컬럼 코덱. 고정 폭 열은 리틀엔디언으로, 가변 열은 길이+바이트. 첫 바이트에 포맷 버전 | 2~4µs (−90%) | 큼. 포맷 버전·폴백·백업 호환 입증 필요 |

1단계는 **스키마를 바꾸지 않는다.** 저장되는 바이트(열 값)가 같으므로 기존 파일·백업과 호환되고, 실패하면 그 함수만 되돌리면 된다. 그래서 1단계를 먼저 한다.

### 품질 게이트 4개

| 게이트 | 재는 것 | 드러나는 곳 | 임계 |
| --- | --- | --- | --- |
| G1 열 강등 | `extra`로 떨어진 열 이름·행 수 | 진단 로그 `store_column_demoted` | 1건이라도 나오면 경보 |
| G2 해독 실패 | 실패 행 수·사유 | `store_row_unreadable` + `sensor_store_unreadable_rows`의 `count` | >0 |
| G4 `day` 불일치 | 저장된 `day`와 현재 달력 기준 `day`가 다른 날·행 수 | `store_day_drift` | >0이면 재계산 안내 |

G3(쓰기 충돌)는 게이트를 만들지 않았다 — 살아 있는 두 경로가 이미 던지거나 세기 때문이다(D4 정정). 대신 조용히 버리던 `insertNewReadings`를 삭제했다.
G1·G2·G4는 모두 **스키마 무변경**이다. 세는 일만 더한다.

### 백업

지금 구조를 유지한다. 다만 L1/L2 분리 후에는 백업이 두 표를 합쳐 예전과 같은 JSON Lines를 만들어야 하므로, **백업 포맷은 바꾸지 않고 읽기 경로만 바뀐다.** 이게 P2의 유일한 호환성 조건이다.

### P1 — 코덱 1단계 (스키마 무변경) — **구현 완료 (2026-10-24)**

- `row(for:)`/`reading(from:)`에서 `JSONSerialization` 2통과를 없앴다. `Codable`이 부르는 컨테이너를 직접 구현해(`TaptionStoreColumnCoding.swift`) 같은 모양의 사전을 바로 만든다. 열 규칙(`take`/`put`)과 `extra` 규칙은 그대로다.

- **기대(−31%)는 실현되지 않았다.** 실측 쓰기 1.20×, 읽기 0.98× (2-3-1). 대리 측정이 JSON 단계만 따로 재서 행 경로의 나머지 비용을 놓쳤다.

- **결정(2026-10-24): 남긴다.** 쓰기 1.20×는 실재하고, 값이 정확해졌으며, P3의 발판이다. 읽기 이득이 없다는 사실은 아래 P2의 근거로 넘긴다.

### P2 — 열당 비용 제거 (스키마 무변경) — **2단계 완료 (2026-10-24)**

원래 P2는 `readings_hot` + `readings_body` 분리(스키마 3)였다. 그런데 2-3-2를 재보니
**표를 쪼개기 전에 없앨 수 있는 비용이 40%**였다. 그래서 순서를 바꿨다.

- **1단계**: `take`/`put`이 행마다 하던 `path.split`을 없애고, 열 경로를 `columnParts`로 한 번만 쪼개 둔다. → 읽기 134.3 → **75.7~77.2ms**.
- **2단계**: 읽기에서 사전(`[String: Any]`)을 아예 만들지 않는다. `Codable` 컨테이너를 직접 구현한 `TaptionRowDecoder`가 키를 열 위치로 바꿔 곧장 값을 꺼낸다. → 읽기 75.7~77.2 → **61.2~68.7ms**.
- **합계**: 읽기 134.3 → **61.2~68.7ms(1.95~2.19×)**. 스키마·파일 형식·백업 포맷 무변경. 쓰기는 2단계에서 손대지 않았다(1단계의 1.27~1.49× 그대로 — 쓰기는 여전히 사전을 거쳐 열로 펼친다).
- **디코딩은 오히려 느려졌다**(36.3~39.3 → 55.1~61.7ms). 열 값을 꺼낼 때마다 `columnIndexByPath`/`nestedColumnIndex` 사전을 조회하기 때문이다. 사전 만들기(30~34ms)가 통째로 사라져 합계는 줄었다. 다음 후보는 이 조회를 없애는 것 — 열 위치를 `CodingKey`에서 바로 얻으면 조회가 사라진다.
- **표 분리는 보류한다.** 근거: ① 지금 얻은 2배가 migration 없이 나왔다 ② 하루 조회가 실제로 몇 열을 쓰는지 아직 확인하지 않았다(융합 엔진은 `motion`·`speed`·`behavior`·`deviceMotion` 등 많은 열을 쓴다) ③ 스키마 변경은 백업 JSON Lines 바이트 동일성과 중단 재개까지 입증해야 한다.
- 표 분리를 다시 꺼낼 조건: 열당 비용을 다 없앤 뒤에도 하루 조회가 예산을 넘을 때. 그때는 "하루 투영이 실제로 읽는 열" 목록을 먼저 만든다.
- 되돌리기: 2단계는 `TaptionRowDecoder` 계열(약 250줄)을 지우고 `reading(from:)`을 사전 경로로 되돌리면 된다. `put`은 `TaptionStoreQuality.swift`에 다시 넣어야 한다.
- **검증**: 코덱 11 + 품질 10 + 저장소 127 = **148개 통과, 실패 0**. 앱 Debug 빌드 성공(`error:` 0·`warning:` 0), 테스트 타깃 컴파일 성공, 구조 게이트 통과.
  회귀 도중 `SQLitePlanRepositoryTests`가 **파일 이름**이라 `-only-testing`에 걸면 `Executed 0 tests`로 조용히 통과하던 것을 발견했다. 그 파일의 클래스 4개(29개)를 이번에 처음 돌렸고 모두 통과했다.
- **`-O`로 다시 쟀다(2-3-3)**: 읽기 61.2~68.7 → **37.3~37.8ms**, 표본 폭 7.5 → 0.5ms. 하루(1,440행) 코덱 **54ms**. `extra` 파싱은 최적화와 무관해 비중이 18%로 커졌다.

## 8. 2026-10-27 실기기 측정이 정정한 것 — 시작 시간의 병목은 `records` 표였다

이 문서의 측정 대상은 `readings`(센서 60열)였다. 그런데 실기기 시작 로그에서 시간을 잡아먹은 것은 같은 파일의 **`records` 표**였다.

| 항목 | 빌드 240 (수정 전) | 빌드 243 (수정 후) |
| --- | --- | --- |
| `repository_local_load` rows | 1,284,890 | **26,702** |
| 그중 `healthkit-sample` | 1,258,394 (**97.9%**) | 0 |
| read / decode | 9,369ms / 69ms | **634.5ms / 78.6ms** |
| `bootstrapped` | 9,944ms | **830ms** |

- `TaptionStoreRepository.load()`가 `allRecordRows()`로 `records` 전체를 읽고, 그중 97.9%를 "스냅샷 해독 목록 13종에 없다"는 이유로 버리고 있었다. 해독은 69ms인데 읽기가 9.4초 — 시간은 전부 SQL 읽기였다.
- `kind IN (…)`로 거르자(`records_kind_start` 색인) 26,702행 / 0.35~0.65초가 됐다. 스냅샷에 종류를 더할 때는 `TaptionStoreRepository.Kind`에도 넣어야 한다 — 빠뜨리면 그 행이 조용히 적재에서 사라진다.
- **교훈**: 시뮬레이터 벤치가 이 병목을 못 잡은 이유는 표본 DB에 `healthkit-sample`이 없었기 때문이다. 코덱·질의를 아무리 재도 **읽는 행 수가 실제와 다르면** 시작 시간은 보이지 않는다. 시작 시간을 판정할 때는 코덱 벤치가 아니라 실기기 `repository_local_load`의 `rows`·`read_ms`를 먼저 본다.
- 이 문서의 P1·P2 결론(행 하나를 싸게 만드는 일)은 그대로 유효하다. 다만 그것은 하루 조회·쓰기 경로의 이야기이고, **시작 시간의 지배 항은 읽는 행 수**였다.
